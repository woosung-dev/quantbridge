# ADR-033 — DB 호스팅은 self-host TimescaleDB CE 로 간다 (관리형 3안 기각)

- **Status:** Accepted (2026-08-16)
- **회차:** production-readiness
- **관련:** [BL-070](../backlog.md#deferred--trigger-미도래--의도적-부활-가능-구-_deferredmd-승격-2026-08-06) · [BL-071] · [BL-072] · [BL-767](../backlog-resolved.md#bl-767) · [BL-768](../backlog-resolved.md#bl-768) · [BL-736](../backlog.md#bl-736) · [ADR-026](026-documentation-ssot.md)

## Context

Beta 진입은 세 항목이다 — [BL-070] 도메인·DNS·Cloudflare · [BL-071] 백엔드 프로덕션 배포 ·
[BL-072] 이메일·Waitlist. 이 중 [BL-071] 이 「Cloud Run/Railway/Render + Postgres prod」를
전제로 적혀 있었다. 즉 **관리형 PaaS + 관리형 Postgres** 를 상정했다.

그런데 우리 스키마에는 `ts.ohlcv` hypertable 이 있다
(`apps/api/alembic/versions/20260416_1458_create_ohlcv_hypertable.py:56`). TimescaleDB 확장이
없는 Postgres 에서는 `alembic upgrade head` 가 **실패한다** — 「나중에 붙이면 된다」가 아니라
기동 자체가 안 된다. 그래서 배포 대상이 안 정해졌고, [BL-071] 이 멈췄고, 그 뒤 두 항목도 함께
멈췄다. 이것이 40 세션 넘게 이어진 blocker 의 실체다.

**이 결정이 「어느 클라우드가 좋은가」가 아닌 이유** — 관리형 Postgres 가 대부분 막힌 것은
업체의 사정이 아니라 **TimescaleDB 의 라이선스(TSL)** 다. Timescale 이 확장을 재라이선스했고
그 조건이 관리형 서비스의 재배포와 충돌한다. AWS RDS/Aurora 는 allow-list 에서 제외됐고,
Supabase 는 PG15 에는 남아 있으나 PG17 에서 deprecated 이며, Fly Managed Postgres 는 미지원이라
전용 이미지(`postgres-flex-timescaledb`)를 **unmanaged** 로 올려야 한다(Fly 문서 자신이 그 경로를
"This Is Not Managed Postgres" 라는 제목으로 경고한다). ⇒ 「관리형 + hypertable」 조합은 사실상
Timescale 자사 클라우드 하나뿐이다.

## Decision

**self-host TimescaleDB CE 를 유지한다.** 지금 서버(Oracle Always Free A1, 도쿄)에서 도는 그대로다.
[BL-070]/[BL-071]/[BL-072] 의 선행 조건은 이로써 해제된다.

단 **아래 조건 3종을 함께 확정한다.** self-host 를 고른 대가는 「백업과 가용성이 전적으로
우리 책임이 된다」 하나뿐이고, 그 대가를 안 치르면 이 결정은 성립하지 않는다.

## 근거 — 2026-08-15~16 실측

| 축                   | 값                                                            | 뜻                                                          |
| -------------------- | ------------------------------------------------------------- | ----------------------------------------------------------- |
| DB 전체 크기         | **24 MB**                                                     | 어느 플랜이든 최소 사양으로 남는다. 이관해도 덤프 한 번이다 |
| `ts.ohlcv`           | **12,937행** · 59 chunks                                      | hypertable 이 이득을 낼 규모가 아니다(수억 행용 도구다)     |
| 가장 큰 테이블       | `backtests` 1.98 MB                                           | 시계열이 아니라 **백테스트 결과**가 제일 크다               |
| hypertable 고유 기능 | `time_bucket`·continuous aggregate·compression **사용처 0건** | 코드가 TimescaleDB 를 사실상 안 쓴다                        |
| 서버                 | 디스크 40%(59G 여유) · RAM 7.6Gi · 2 vCPU                     | 현재 부하로는 여유가 크다                                   |

**성능은 판정 근거가 아니다** — 24MB·12,937행이 2 vCPU 위에서 이미 돈다.
**hypertable 은 ①②만 준다** — ③은 unmanaged 로만, ④는 포기하는 길이다.
**백업·HA 가 유일한 진짜 차이**이고, 관리형이 월 $30 에 파는 것이 정확히 그것이다.
그런데 백업은 절차로 붙일 수 있고(아래 조건 ⑴), HA 는 사용자가 붙기 전에는 다운타임이
«불편»이지 «손실»이 아니다.

**결정적인 이유는 따로 있다 — ①은 결정을 미룰 수 있게 해준다.** ②로 가면 hypertable 에 묶이고,
④로 가면 migration 을 먼저 써야 한다. ①은 **지금 아무 일도 하지 않고 Beta 를 시작하게** 하며,
데이터가 24MB 인 동안에는 언제 갈아타도 30초짜리 덤프다.

## 기각한 대안

| 안                                 | 기각 사유                                                                                                                                                                                                                                                                                                       |
| ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ② Tiger Cloud (구 Timescale Cloud) | 월 $30+ 가 사는 것은 백업·HA 하나뿐이고 그 둘을 지금 자력으로 붙일 수 있다. 이관 회차가 별도로 들고 hypertable 에 묶인다                                                                                                                                                                                        |
| ③ Fly Postgres                     | unmanaged 전용 이미지를 우리가 올려야 해 **백업은 여전히 우리 책임**인데 플랫폼 락인만 늘어난다. ① 대비 이득이 없다                                                                                                                                                                                             |
| ④ hypertable 포기 + 아무 관리형    | **진짜 선택지다** — 코드가 고유 기능을 안 쓰므로 일반 테이블로 바꿔도 쿼리는 그대로 돈다. 다만 지금 하면 migration + 회귀 검증 한 회차를 쓰고 얻는 것은 「관리형을 고를 자유」뿐이고, **그 자유는 ①을 유지하는 동안에도 언제든 살 수 있다.** ⇒ 지금 하지 않고, 관리형으로 옮기기로 결정하는 그 회차에 함께 한다 |

## 조건 — ①과 분리할 수 없다

1. **백업 자동화** ([BL-767]) — 도구(`mise run db-snapshot`/`db-restore`)는 이미 있었다. 없던 것은
   셋이다: ⑴ 스케줄 ⑵ 오프서버 보관 ⑶ **복원 실증**.
   ★**복원을 한 번 실제로 해 보기 전에는 백업이 있다고 말하지 않는다.** 이 레포는 「있다고
   여겨진 가드가 실제로는 그 경로를 안 지나던」 사례를 이미 겪었다([LESSON-087]·[LESSON-109]).
   ★★**TimescaleDB 절차에 대한 착수 전제가 절반 반증됐다.** 공식 문서는 복원을
   `timescaledb_pre_restore()` / `timescaledb_post_restore()` 로 감싸라고 하고(내부 훅을 끄는
   `timescaledb.restoring` GUC), 이 회차도 그것을 「절차의 핵심」으로 잡았다. 그런데 **이 스키마에서
   그 호출의 유무는 관측 가능한 차이를 하나도 만들지 않았다** — 양쪽 다 `pg_restore` rc=0 ·
   stderr 0줄 · chunk 59 · 21,649행 · 복원본 INSERT 가 새 chunk 로 라우팅 · `drop_chunks()` 정상.
   호출을 지워도 백업 하네스는 **39/39 초록**이다.
   [가정] hypertable 이 1개뿐이고 continuous aggregate·압축·정책이 0건이라 훅이 할 일이 없다 —
   위 근거표의 「고유 기능 사용처 0건」과 일치한다. ⇒ **호출은 유지한다**(문서가 정본이고 비용 0,
   그리고 전환 트리거 ④가 오면 상황이 달라진다). 단 **「테스트가 이 축을 지킨다」고 적지 마라** —
   지금 그 축에는 증거가 없다.
   ★**반면 버전 제약은 진짜다** — 덤프와 복원의 확장 버전이 다르면 catalog version mismatch 로
   죽는다. 로컬·서버가 같은 `timescale/timescaledb:2.14.2-pg15` 라 지금은 만족한다.
2. **디스크 80% 경보** ([BL-768]) — 2026-08-14T06:04Z 로컬 Docker VM 94% 에서 Redis AOF 쓰기가
   실패해 celery 가 통째로 정지했다([BL-736]). 그 사고는 로컬에서 났지만 **서버도 구조가 같다** —
   `quantbridge-redis` 는 `appendonly=yes` 이고 소크 스택·백업 덤프·다른 앱 셋이 디스크 한 벌을
   공유한다. 서버에서 나면 24시간 안정성 창이 통째로 날아간다.
3. **전환 트리거 명문화** (아래) — self-host 는 영구 결정이 아니라 **지금 자리**다. 언제 떠나는지를
   지금 적어 두지 않으면 「불편하지만 그럭저럭 도는 상태」가 무기한 이어진다.

## 전환 트리거 — 아래 중 하나가 오면 ② 또는 ④를 재판정한다

1. **외부 사용자 데이터가 들어오기 시작할 때** — 그 순간부터 유실은 «불편»이 아니라 «손실»이고,
   RPO/RTO 를 우리가 책임진다는 뜻이 달라진다.
2. **디스크 사용률 80%** — [BL-768] 경보가 발화하는 지점. 회수로 해결되지 않으면 이관 신호다.
3. **다운타임이 «불편»이 아니라 «손실»이 되는 첫 순간** — 단일 노드에 HA 가 없다는 사실이
   비용으로 바뀌는 때.
4. **`ts.ohlcv` 가 수천만 행에 접근할 때** — 그때는 hypertable 이 실제로 일을 하기 시작하므로
   ④(hypertable 포기)가 닫히고 ①↔② 2 택이 된다.

## 되돌리기

24MB 인 동안에는 `pg_dump -Fc` 한 번이면 어디로든 옮겨간다. [BL-767] 이 만든 덤프가 그대로
이관 산출물이 된다 — 즉 조건 ⑴을 짓는 것 자체가 이 결정의 되돌리기 비용을 낮춘다.
