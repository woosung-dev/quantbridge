## 배경 — 통과를 선언할 근거가 없었다

[BL-003](../backlog.md) 은 이 프로젝트의 유일한 P0 이고, 그 게이트는 코드가 아니라 달력 시간이다:

> **Trigger:** Bybit Demo 1주 안정 운영 후 + BL-004 완료 후

그런데 「1주 안정 운영」에 조작적 정의가 없었다. 그래서 두 문제가 동시에 있었다.

**첫째, 시계가 멈춰 있었다.** `docker-compose.isolated.yml:28-38` 이 `./backend/src` 를 mount 하고
celery 를 `watchfiles` 로 감싼다. `backend/src` 의 `.py` 를 **한 줄만 고쳐도** 소크 워커가
재적재된다(실측 105회). 그래서 개발과 소크가 물리적으로 배타적이었고, 08-01 이후 소크 종료
8건 중 **6건이 `user_stopped`** — 고장이 아니라 사람이 코드 작업하려고 멈춘 것이다.

**둘째, 168h 를 채워도 판정할 수 없었다.** 「역대 최장 15.3h = 9%」라는 서술이 있었지만,
그 15.3h 가 무엇을 증명하는지에 대한 술어가 없었다. 정의를 나중에 붙이면 168h 를 다 태운 뒤에
「그게 안정이었나」를 다시 묻게 된다.

## 결정

### 낱말은 셋 — PASS / FAIL / UNKNOWN

`scripts/soak-gate.sh` 가 낸다. 종료 코드는 **PASS 만 0**, FAIL 1, UNKNOWN 2.
★**UNKNOWN 을 PASS 로 접지 않는다.** 낱말이 셋뿐이라 UNKNOWN 은 사유 낱말로 두 갈래를 가른다 —
`진행중`(측정은 됐고 시간이 모자라다) vs `측정불가`(잴 수 없었다).

### 창(window) — 정의의 절반

**창** = 다음 넷을 **동시에** 만족하는 최대 구간이다.

| #   | 조건                         | 근거                                                                                                                                                        |
| --- | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ①   | 라이브 세션이 활성           | 판정은 **`deactivated_at`** 으로 한다. `is_active` 도 `deactivated_reason` 도 아니다 — 실측 25세션 중 12세션이 `is_active=false` 인데 reason 이 NULL 이었다 |
| ②   | **고정 커밋이 불변**         | 어느 커밋이 돌았는지 답할 수 없는 시간은 세지 않는다 (`.soak/pin-history.jsonl`)                                                                            |
| ③   | T0 이후                      | T0 = 마지막 실격 사건                                                                                                                                       |
| ④   | **phantom 관측이 덮은 구간** | 검증되지 않은 시간은 credit 하지 않는다                                                                                                                     |

★**④는 boolean 이 아니라 자르기다.** 워커 로그의 마지막 줄은 언제나 `now` 보다 수십 초 앞선다
(celery 가 매초 찍지 않는다). boolean 으로 두면 그 수십 초 때문에 **매 실행이 UNKNOWN** 이 되고,
허용 오차를 두면 그만큼이 **검증 없이 credit** 된다. 자르면 둘 다 안 생긴다.
**구조적 방어가 문턱보다 강하다.**

### 리셋 규칙

| 사건                                | 누적(C1)            | 연속(C2)        |
| ----------------------------------- | ------------------- | --------------- |
| **자동 사망 / phantom / tick 정체** | ★**T0 리셋 = 0**    | 끊김            |
| 재고정(`pin` 으로 커밋 변경)        | 이어감              | **끊김**        |
| 워커 재기동(커밋 불변)              | 이어감              | 이어감          |
| `user_stopped` · 세션 공백          | 이어감(공백 미계상) | 끊김            |
| 흡수(어둠) 구간                     | 이어감              | 이어감 (보고만) |
| **고정되지 않은 스택**              | ★**미계상**         | 미계상          |

★**리셋은 원인을 가리지 않는다.** 코드 결함이든 운영 사고든 같은 크기로 T0 를 되돌린다 —
면제를 만들자는 안은 §대안 (h) 로 기각했다. 실격의 **원인**은 §실격 귀속 원장이 따로 기록하며,
그 기록은 이 표를 한 칸도 바꾸지 않는다.

### 조건 C1~C5 (전부 AND)

| ID     | 조건           | 값                                                                                                                        |
| ------ | -------------- | ------------------------------------------------------------------------------------------------------------------------- |
| **C1** | 자격 창의 개수 | **≥ 3회** — 창 하나의 자격선은 C2 와 같은 24h (~~누적 clean ≥ 168h~~, 2026-08-11 [BL-701] 교체)                           |
| **C2** | 최장 연속 창   | **≥ 24h** — C1 이 세는 창과 **같은 단위**다(귀속 구간별 병합 interval)                                                    |
| **C3** | 실격 사건      | **0건**                                                                                                                   |
| **C4** | tick 연속성    | 표본 간격 ≤ 1h · 연속 두 표본에서 bar time 이 얼어붙지 않음                                                               |
| **C5** | 측정 무결성    | DB 응답 · 스택이 고정본 · phantom 아카이브 존재 · 어둠 비율 계산 성공 · **라벨 어휘 판독 가능** · **redis AOF 판독 가능** |

★**C5⑸ `aof_ok` 는 「redis 가 떠 있는가」가 아니라 「지금 재기동하면 뜨는가」다** (2026-08-05,
[BL-594]). AOF 는 **기동 시에만** 읽히고 healthcheck(`redis-cli ping`)는 떠 있는 프로세스에만
물으므로, 판독 불가 AOF 위에서 6일을 갔는데 아무 지표도 안 움직였다. 수집기는
`redis-check-aof`(★`--fix` 없이 — 읽기 전용)를 돌리고 **양성 서명만 통과**시킨다:

| AOF 상태             | check-aof                                      | 서버 기동                                    | `aof_ok` |
| -------------------- | ---------------------------------------------- | -------------------------------------------- | -------- |
| 정상                 | exit 0 `All AOF files and manifest are valid`  | ✅                                           | ✔        |
| 마지막 INCR 꼬리절단 | exit 1 `Expected to read N bytes, got M bytes` | ✅ (자동 절단)                               | ✔        |
| **비마지막** 파일    | exit 1 **위와 같은 모양**                      | ❌ `the truncated file is not the last file` | ✘        |
| 구분자 손상          | exit 1 `Expected \r\n, got:`                   | ✅ **뜬다**(로더가 CRLF 미검증 폐기)         | ✘★       |
| 중간 손상            | exit 1 `AOF … format error`                    | ❌ `Bad file format`                         | ✘        |

★★**종료 코드로 재면 안 된다** — 도는 redis 의 AOF 꼬리는 언제든 미완결일 수 있고, 그 꼬리는
`aof-load-truncated yes`(기본값)가 기동 시 잘라내므로 **무해**하다. exit code 를 그대로 쓰면
멀쩡한 스택이 거짓 `측정불가` 로 떨어진다. ★반대로 「short read 면 통과」로 넓히면 **비마지막
파일 절단**이 통과한다 — 출력이 같은 모양이고 **유일한 판별자가 「마지막 INCR 인가」**다.
★구분자 손상은 **알려진 거짓 양성**이다(엄격 쪽이라 래칫에는 안전 — 거짓 PASS 는 못 만든다).
판정 규칙의 정본은 [`redis_aof_readability.py`](../../backend/scripts/redis_aof_readability.py)
이고 실측 캡처 7형이 그 테스트로 동결돼 있다.
★**알려진 한계** — `redis-check-aof` 는 **프레이밍만** 본다. 벌크 페이로드 안이 깨져 명령
이름이 망가지면 check 는 `valid` 라고 하는데 서버는 `Unknown command` 로 죽는다(실측).
즉 `aof_ok=✔` 는 「프레이밍이 성하다」이지 「반드시 뜬다」가 아니다. 더 강한 검사는 사본을
띄워보는 것뿐이다 — [BL-594] 후속.

**실격 사건 3종** — ⑴ 자동 사망(`SessionDeactivationReason` 에서 `user_stopped` 를 뺀 8종)
⑵ **phantom** 방향 발산 ⑶ **tick 정체**.
★**`replay_lag` 는 실격이 아니다** — 현행 회복식 기준 **11/11 자가치유**(2026-08-05 실측,
n=19). 무해 갈래를 사망 조건에 넣으면 게이트가 영영 안 닫힌다.

★이 문장은 재무장식 시절 「12/12」였다가 codex 지적으로 「11건 회복 + 1건은 사망 직전 tick」
으로 **정정해야 했다**. 회복식은 그 1건을 처음부터 `phantom` 으로 잡으므로 지금은 정정할
문장이 없다 — §판별식 2차 교체.

★★**라벨 어휘는 3분할이고, 넷째는 없다 — 「그 밖」은 무해가 아니라 측정 무결성 실패다**
([BL-596], 2026-08-05 수리). 게이트는 알려진 무해 `{replay_lag}` / 알려진 실격 `{phantom}` /
**판정 불가 `{unattributed}` ∪ 어휘 밖 전부**를 명시적으로 가른다(`soak_gate_predicate.py` 의
`*_DIVERGENCE_LABELS` frozenset). 셋째 갈래는 **C5 를 떨어뜨려 `UNKNOWN 측정불가`** 로 간다 —
무해로 접으면 실격을 놓쳐 `window_start` 가 앞당겨지고(fail-open), 소급 실격으로 세면 「모른다」를
「유령이었다」로 바꾸는 반대 방향의 거짓말이다. ★판정 순서상 **FAIL 이 C5 보다 먼저**라 어휘
검사가 진짜 실격을 UNKNOWN 으로 덮지 못한다(래칫). ★어휘가 갈리면 게이트는 그 아카이브가
정리될 때까지 UNKNOWN 에 머문다 — 해소는 frozenset 등재 또는 §아카이브 판의 판 이동이다.
★★**둘 중 무엇인지는 라벨 이름이 아니라 출처가 답한다** — `soak-gate.sh` 가 합병 때 관측마다
`archive`/`predicate_version` 을 붙이고, 판정은 `detail.divergence_labels.sources` 로 라벨별
총계 + 표본(상한 5건)을 낸다. 요약 줄에도 첫 출처가 실린다.

★**`phantom` 의 정의는 2026-08-05 에 **두 번** 교체됐다** — 「봉경계식」 → 「재무장 도장식」
→ **「직접 회복 검사」**(현행, `PREDICATE_VERSION = 2026-08-05-recovery-ratchet`).
근거·표·오차 방향은 §판별식 2차 교체 참조. 판정 코드는 게이트가 아니라
[`classify_direction_divergence.py`](../../backend/scripts/classify_direction_divergence.py)
에 있고, 게이트는 그 산출물(`verdicts[].label`)만 읽는다.

★★★**첫 창에서 그 우려가 그대로 실현됐다 (2026-08-05, 게이트 가동 첫 5시간).**
관측 **8건 — phantom 7 · replay_lag 1 · 사망 2**. 즉 **phantom → 사망은 2/7 (29%)** 이고
「phantom = 치명」이 아니다. 게다가 분류기가 스스로 **「봉경계식 vs 시간문턱식 불일치 4건」**을
보고한다. 경과 분포가 **연속적**이다:

| 경과 | 6.90초  | 9.30초  | 36.81초 | 52.22초 | 61.55초       | 702.50초 | 762.35초      |
| ---- | ------- | ------- | ------- | ------- | ------------- | -------- | ------------- |
| 라벨 | phantom | phantom | phantom | phantom | **phantom ★** | phantom  | **phantom ★** |

⇒ 직전 회차의 「경과 24.7초 vs 909초 = **37배, 겹침 0**」은 **그 표본의 성질이지 판별식의
성질이 아니다.** 관측이 봉 시작 직후에 오면 경과 **6.9초**도 봉 경계를 넘어 `phantom` 이 된다.

★**소크 수명 실측**: `39731d57` **38분** · `cc19abd2` **138분** — 둘 다 `position_divergence`.
현행 코드의 실질 MTBF 는 **1~2.3시간**이고, 연속 24h 는커녕 168h 누적도 이 상태로는 못 채운다.

⇒ **`phantom` 을 실격으로 두면 게이트가 안 닫힌다.** ★그렇다고 **지금 판별식을 느슨하게
고치지 않는다** — 그건 정의를 통과시키기 쉬운 쪽으로 바꾸는 것이다. 판별식 재설계와 phantom
자체의 수리는 [BL-591]/[ADR-023] 축의 일이고, **그때까지 게이트는 FAIL 을 유지한다.**
게이트의 첫 산출물이 「이 시스템은 아직 안정하지 않다」인 것은 결함이 아니라 **설계대로**다.

★★**단 `replay_lag`/`phantom` 은 서로 다른 두 사건이 아닐 수 있다** — 2026-08-05 실측:
**같은 발산 하나**가 엔진값·거래소값·최근 체결이 **완전히 동일**한 채 경과만 `1.53초 → 61.55초`
로 흐르자 `replay_lag` → `phantom` 으로 이름을 바꿨다. 판별식이 **경과 시간의 함수**이므로
자가치유하지 않는 발산은 시간이 지나면 **반드시** `phantom` 이 된다. ⇒ 직전 회차의
「경과 24.7초 vs 909초 = 37배, 겹침 0」은 **그 표본의 성질이지 판별식의 성질이 아니다.**
게이트에는 영향이 없다(자가치유한 것은 어차피 `replay_lag` 로 남고 실격이 아니다) —
그러나 **「두 현상이다」의 근거로는 약하다**. 상세 = [BL-591]·[ADR-023].

## ★C1 의 조작적 정의 — 「누적 clean 168h」는 실제로 **「168시간 연속 무실격」**이다

> ★★★**Superseded (2026-08-11 사용자 결정) — C1 문턱을 교체한다.** 아래 2026-08-08 결정
> (「문턱 유지」)은 **이 절의 증명 자체에 의해 무너졌다.** 이 절은 C1 이 누적이 아니라
> **생존** 문턱임을 코드로 증명했고, [BL-641] 이 그 생존 확률을 계산했다:
> **P(168h 무실격) = 4.115e-09.** 39세션에서 24h 도달 **0건**이었고 40세션 만에 처음
> C2 24.80h 가 나왔다(2026-08-10). ⇒ 종전 문턱으로는 **P0 이 영구히 닫히지 않는다.**
> 새 문턱 = **「≥24h 연속 무실격 창을 3회 달성」**.
>
> ★**낱말을 그대로 옮기지 않은 이유.** 사용자가 고른 표현은 「누적 24h × N회」였는데,
> **이 절 자신이 「누적」이 오해를 부른다고 증명했다** — 실격이 나면 그때까지 쌓인 시간이
> 전부 사라지므로 C1 에서 「누적」은 합이 될 수 없다. 「누적 24h」가 합을 뜻한다면 이미
> 오래전에 충족됐고 문턱이 아니게 된다. ⇒ **정합적인 해석은 하나뿐**이다:
> **「24h 이상 연속 무실격 창(= C2 판정 단위)을 3회 달성」.** N=3 은 `[가정]`이다.
>
> **현재 진척 (2026-08-11 게이트 2회차 실측):** 귀속 창 `15.3007h · 0.0133h · 53.8225h`
> ⇒ 24h 를 넘은 것은 **하나** = **1/3.** 실격 0 · 창 시작 `2026-08-07T15:10:49Z`.

### 「누적」이라는 낱말이 오해를 부른다

§리셋 규칙 표가 자동 사망 · `phantom` · tick 정체에서 C1 을 **T0 리셋 = 0** 으로 만든다.
실격이 한 번이라도 나면 그때까지 쌓인 시간이 **전부 사라진다.** ⇒ **C1 은 누적 문턱이 아니라
생존 문턱이다.** 「168시간을 모으면 된다」가 아니라 **「168시간을 한 번의 실격도 없이 연속으로
살아야 한다」**가 정확한 요구다.

### 코드 근거 — 사라진 시간은 어디에도 나타나지 않는다

[`soak_gate_predicate.py`](../../backend/scripts/soak_gate_predicate.py) 의

```python
countable = [a for a in attribution if a.start >= window_start]
```

이 실격 시점에 **이미 열려 있던** 귀속 구간을 **클립이 아니라 통째로 배제**한다. 그 시간은
C1 에도, `unattributed_hours` 에도, `unverified_hours` 에도 나타나지 않고 **사라진다.**
⇒ **「기다리면 언젠가 오른다」가 성립하지 않는다.** 실격 하나가 그 앞의 모든 것을 지운다.

★**이 동작 자체는 의도된 것이다** — §codex 적대 리뷰의 「실격 뒤 인지 전 시간 credit」 수리가
정확히 이것이고, 반대로 두면 거짓 PASS 경로가 열린다. 문제는 동작이 아니라 **서술이 「누적」으로
읽힌다**는 점이다. 이 절이 그 서술을 고친다.

### ★★★그런데 이 ADR 은 **자기가 기각한 안을 집행하고 있다** (2026-08-08 등재)

§대안 **(a) 「연속 168h」를 이 문서가 명시적으로 거부했다** — 「재시작 한 번에 전부 잃는다 …
사실상 도달 불가다」. 그리고 §대안 (b) 는 순수 누적을 「연속 24h 조항으로 보완했다」고 적는다.
**설계 의도는 (a)를 피하는 것이었다.**

그런데 바로 위 코드가 하는 일이 **(a) 그 자체다.** 실격 하나가 C1 을 0 으로 되돌리므로 C1 은
「연속 168h」와 동치이고, (b)의 「4시간짜리 42개」는 **구조적으로 불가능**하다. 즉 이 문서는
한 절에서 기각한 것을 다른 절에서 집행한다.

★**두 절이 서로 다른 자리에 있어서 아무도 잇지 못했다** — §163 은 「서술이 틀렸다」로 봉합했고
§대안은 「(a)는 거부」로 남아 있다. 둘을 같이 읽으면 **거부 사유가 그대로 현행 동작의 비용**이다.
그 비용의 크기가 아래 표다(24h 도달 **0/39** · 최장 19.42h · 요구치는 그 8.65배).

**판정 — 동작을 유지한다. 셋 다 더 나쁘기 때문이다.**

| 갈래                             | 왜 안 하나                                                                   |
| -------------------------------- | ---------------------------------------------------------------------------- |
| 문턱을 낮춘다                    | §결론이 이미 거부 — 게이트가 통과를 파는 것이다                              |
| 리셋을 「그 구간 배제」로 바꾼다 | 실격 뒤 **인지 전** 시간이 credit 된다 = codex 가 잡은 거짓 PASS 경로의 복원 |
| 실격 종류별로 리셋을 나눈다      | §대안 **(h)** 로 기각 — 판정 주체가 사람이라 fail-open                       |

⇒ **바꾸는 것은 동작이 아니라 「그 대가를 아는가」다.** 그래서 §실격 귀속 원장을 신설한다 —
판정에는 참여하지 않고, **무엇이 우리를 죽였는지**만 재현 가능하게 기록한다.

### ★pin 은 C1·C2 를 리셋하지 않는다 — 리셋하는 것은 실격뿐이다 (2026-08-10 등재)

★**위 절이 「실격은 전부를 지운다」를 못 박은 결과, 그 옆에 「재기동도 그렇다」가 붙어 자랐다.**
`status.md` 는 「재기동 시 C1 은 여기서 이어진다(**C2 는 0 부터**)」라고 적었고, 세션 프롬프트는
그것을 **절대 규칙**(「`pin` 금지 — C2 를 0 으로 리셋한다」)으로 승격시켰다. **둘 다 거짓이다.**

**코드 근거** (`soak_gate_predicate.py`) — `pin` 은 창 결정에 등장하지 않는다.

| 줄     | 코드                                                   | 뜻                        |
| ------ | ------------------------------------------------------ | ------------------------- |
| `:614` | `window_start = disq[-1].at`                           | 창 시작 = **마지막 실격** |
| `:652` | `countable = [a for a in attribution if a.start >= …]` | 창 이전 구간만 배제       |
| `:690` | `cumulative_hours = sum(iv.seconds for iv in merged)`  | **C1 = 합**               |
| `:691` | `longest_hours = max(iv.seconds for iv in merged)`     | **C2 = max**              |

**실측 확증** — 게이트가 스스로 내는 「귀속 창」에 고정 sha 가 **두 종류**로 공존한다
(`3f8af9dfe78e` → `fdc53c04a929`). 2026-08-08 에 pin 을 했는데 **그 이전 15.30h 창이 여전히
목록에 있고** 합이 맞는다(`15.3007 + 0.0133 + 26.6558 = 41.97h`). ⇒ pin 은 attribution 을
sha 로 **쪼갤 뿐** 과거를 배제하지 않는다. C2 는 `max` 이므로 **이미 24h 를 넘긴 창은
재기동을 넘어 살아 있다.**

**★그러면 pin 의 진짜 비용은 무엇인가 — `down` 동안의 tick 공백이다.**
`_pin` 은 돌고 있는 고정본 위에 겹쳐 쓰지 못하고(`soak-stack.sh:182-187` — 겹쳐 쓰면 stamp 와
실제 import 가 갈린다는 codex P1) `down` 을 먼저 요구한다. 그 공백이 길면 **C4(표본 간격 ≤ 1h)**
나 tick 정체가 실격을 만들고, **실격이야말로 `window_start` 를 리셋한다.** 즉 위험은
**pin 자체가 아니라 pin 이 실격을 유발할 확률**이다.
2026-08-08 실측 공백 = **63초**(`23:15:49` → `23:16:52`), 실격 0.
**[확인 필요] 표본이 1회다** — 어느 길이부터 위험한지는 측정되지 않았다.

★**오해의 근원은 도구의 문구다** — `soak-stack.sh:185` 가 「연속 창은 끊긴다」고 말한다.
참이지만 뜻은 **「진행 중 창이 거기서 끊긴다」**이지 **「벌어 둔 max 를 잃는다」**가 아니다.
두 번째로 읽혀서 「사망 축 수정은 C1 완주 후」라는 미룸이 재생산됐다([BL-690]).

⇒ **운영 귀결: 사망 축(코드 결함 7건) 수정을 C1 완주까지 미룰 근거가 없다.** 미뤄야 할 이유는
「pin 이 벌어 둔 것을 지운다」가 아니라 **「재기동 자체가 실격을 낼 수 있다」** 하나뿐이고,
그 확률은 실측 1회(안전)로만 알려져 있다.

## ★실격 귀속 원장 — 분류는 남기고 면제는 안 준다 (2026-08-08 신설, [BL-641])

정본 파일 = [`soak-disqualifications.jsonl`](../reference/operations/soak-disqualifications.jsonl).
한 행 = 한 실격이고, 필드는 `at` · `kind` · `session` · `reason` · `cause_class` · `evidence` ·
`decided` 다.

### 계약 (이 셋을 어기면 원장이 아니라 문턱 완화 장치가 된다)

1. **판정에 참여하지 않는다.** `soak_gate_predicate.evaluate()` 의 `conditions`(C1~C5)는 원장이
   있든 없든 **비트 단위로 같다**. 원장은 `detail.disqualification_attribution` 이라는 **보고 축**
   에만 나타난다. 이 불변식은 `test_soak_gate_predicate.py` 의
   `test_the_attribution_ledger_never_moves_the_verdict` 가 지키고, 귀속을 C3 에 새게 하는 변이가
   적발된다(변이 5/5).
2. **`undecided` 는 `code_defect` 와 똑같이 다룬다.** 미등재도, 깨진 행도, 미지 `cause_class` 도
   전부 `undecided` 다. ⇒ **원장을 지우거나 망가뜨려서 유리해지는 경로가 없다**(변이 3/3).
3. **`cause_class` 를 자동 유도하지 않는다.** 근거(`evidence`) 없는 귀속은 등재할 수 없고,
   등재는 git 이력에 남아 리뷰를 받는다. 대안 (h) 가 거부된 이유가 이 필드의 신뢰성이므로,
   그 필드를 기계가 추측하게 두면 거부의 의미가 사라진다.

### 무엇을 사는가 — 층화의 재현성

[BL-641] 의 Trigger 는 「소크 재기동 회차마다 재측정」인데, 종전의 층 경계는 **날짜 상수 4개**를
사람이 손으로 넣는 것이었고 사인은 「오염 1건」 같은 **주석**으로만 적혀 있었다. 주석은 재현되지
않는다. 원장이 있으면 [`mtbf_stratified.py`](../../backend/scripts/mtbf_stratified.py) 가
「운영 사고 제외」 층을 **자동으로** 만든다 — 운영 사고 사망을 **사망에서만 빼고 노출은 남기는**
우측 절단이다(노출까지 빼면 「그 시간엔 코드가 안 돌았다」가 되는데 그건 거짓이다).

## 판별식 2차 교체 — 재무장 도장식 → **직접 회복 검사** (2026-08-05 live-replay-visibility)

> ★아래 §1차 교체 블록은 **지우지 않는다.** 무엇이 바뀌었는지 보이려면 옛 값이 있어야 한다.
> 현행 판 = `PREDICATE_VERSION = "2026-08-05-recovery-ratchet"` (§래칫 참조).

### 왜 또 바꾸나 — 재무장 도장은 **회복을 확인하지 않는다**

1차 교체가 스스로 §남는 위험에 적어 둔 그대로다: 마지막 도장 `H` 뒤에 체결 `F` 가 오면
그 발산이 **이후 영영 낫지 않아도** `F >= H` 인 한 계속 `replay_lag` 이다. codex 가 이것을
P1(**TTL 부재**)으로 냈고 **미수리**로 남았다. 그 블록이 지목한 다음 후보가 바로 이 식이다 —
「같은 세션의 다음 관측이 바로 다음 tick 인가」. **원장도 시각 문턱도 쓰지 않는다.**

봉경계식·재무장식은 둘 다 **대리 지표**였다. 하나는 「얼마나 지났나」를, 다른 하나는
「파이프라인이 조정을 끝냈나」를 물었다. 게이트가 알고 싶은 것은 **「이 발산이 나았나」**
하나이고, 회복 검사는 그것을 직접 묻는다.

### 새 판별식

관측 `T`(세션 `S` · 심볼 `Y` · 봉 간격 `I`), 코퍼스 지평 `C`, 근접 지평 `Hn = 1.5 · I`:

| 조건                                          | 라벨          | 뜻                                        |
| --------------------------------------------- | ------------- | ----------------------------------------- |
| 같은 `(S,Y)` 의 **다음 관측**이 `T + Hn` 이내 | **`phantom`** | 바로 다음 평가에도 어긋나 있었다          |
| 다음 관측이 있고 `T + Hn` 밖                  | `replay_lag`  | 그 사이 나았다 — 뒤의 것은 새 에피소드    |
| 다음 관측 없음 + `T + Hn` 안에 **자동 사망**  | **`phantom`** | 낫지 않았다 — 죽어서 관측이 끊겼다        |
| 다음 관측 없음 + `T + Hn` 안에 `user_stopped` | (판정 불가)   | 우리가 껐다 — 회복 여부를 알 수 없다      |
| 다음 관측 없음 + `C > T + Hn`                 | `replay_lag`  | 충분히 지켜봤고 다시 안 왔다              |
| 그 외 (**로그 창이 거기서 끝난다**)           | (판정 불가)   | → `rearm_label` → `horizon_label` 로 강하 |

`C` = 로그의 **모든 줄**에서 읽히는 최대 타임스탬프(발산 줄만 보면 창의 끝을 모른다).
`--events-json` 입력은 아카이브의 `log_to`, 없으면 `generated_at`, 그것도 없으면 최종 관측.

★**`corpus_end` 에 기본값을 주지 않는다.** 「지금」으로 접히면 **로그 절단이 회복으로
오독**되고 그 방향은 게이트에서 fail-open 이다. 호출자가 무엇을 봤는지 말하게 강제한다
(`test_adjudicate_refuses_to_guess_the_corpus_end`).

## 판별식 1차 교체 — 봉경계식 → 재무장 도장식 (2026-08-05, 같은 날 후속)

> ★위 블록의 숫자(`phantom` 7 · phantom→사망 2/7 · 불일치 4건)는 **봉경계식 기준**이다.
> 지우지 않고 남긴다 — 무엇이 바뀌었는지 보이려면 옛 값이 있어야 한다.

### 왜 바꿨나 — 봉경계식이 가정하는 「60초」가 실측과 안 맞는다

봉경계식은 「마지막 체결이 봉 경계를 넘었으면 엔진이 따라왔어야 한다」를 가정한다.
실측은 그 가정을 부순다:

| 실측                              | 값                                  |
| --------------------------------- | ----------------------------------- |
| tick 이 도는 시각                 | 봉 마감 뒤 **10~15초**              |
| 조건부 주문 **재발주 주기**       | **4~14분** (세션·rule 별 평균)      |
| 재발주마다 **트리거가 움직인 폭** | 평균 **62~271 USDT** · 최대 **531** |
| 같은 창의 **1분봉 range**         | **30~90 USDT**                      |

⇒ 거래소에 얹혀 있는 트리거는 재발주 **한 주기만 늦어도 봉 전체보다 멀리 어긋난다.**
「봉 하나가 지났다」로는 「조정이 끝났는가」를 판정할 수 없다.

### 새 판별식

관측 `T`, 마지막 세션 소유 **체결** `F`, 마지막 **재무장 도장** `H`:

| 조건      | 라벨           | 뜻                                                                 |
| --------- | -------------- | ------------------------------------------------------------------ |
| `H > F`   | **`phantom`**  | 체결 뒤 재무장을 **끝냈는데도** 어긋나 있다 ⇒ 조정 주기를 넘겼다   |
| `F >= H`  | `replay_lag`   | 마지막 재무장 **뒤에** 거래소가 움직였다 ⇒ 아직 판정할 때가 아니다 |
| 도장 없음 | (봉경계식으로) | fail-safe — 증거 부재를 유령으로 접지 않는다                       |

**재무장 도장** = 원장의 반전 주문. `conditional_entry_planner.py:502-589` 가
`quantity = |target - current|` 로 수량을 정하고 `current` 는 **거래소 REST 읽기**이므로,
`L = ledger_net(created_at)` 에 대해 `sign(L + signed_qty) == -sign(L)` 이고 크기가 같으면
그 주문은 **파이프라인이 체결을 인지하고 반대편을 다시 무장했다**는 시각 도장이다.

★★★**이건 인과 판정이 아니라 성숙도 프록시다.** 초안에서 「2배 수량 = 그 순간 엔진·거래소
합의」라고 적었다가 **반증됐다** — `39731d57` `16:24:11` 도장 시점에 엔진은 short, 거래소는
long 이었다. 2배 수량은 **거래소 쪽만** 증언한다(엔진은 이미 그 방향을 들고 있어도 같은
`trade_id` 로 pending stop 을 다시 무장할 수 있다 — `strategy_state.py:728-740`).
**인과 판정은 엔진의 `last_strategy_state_report.open_trades[].entry_bar` 로만 되고, 그
보고서는 세션당 마지막 tick 한 벌만 남으므로 과거 전량에는 못 쓴다.** 그래서 프록시를 쓴다.

### ★바꾸기 **전에** 과거 관측 전량에 적용했다 (n=19)

| 창                                      | n      | 재무장식               | 봉경계식           | 사망  |
| --------------------------------------- | ------ | ---------------------- | ------------------ | ----- |
| A `08-02T13:19 ~ 08-04T06:38`(아카이브) | 11     | phantom 4 · lag 7      | phantom 4 · lag 7  | 2     |
| B `08-04T15:51 ~ 08-05T01:21`(워커로그) | 8      | **phantom 3 · lag 5**  | phantom 7 · lag 1  | 2     |
| **합계**                                | **19** | **phantom 7 · lag 12** | phantom 11 · lag 8 | **4** |

- 바뀌는 것은 **4건뿐**이고 전부 `cc19abd2`(`17:26`·`17:29`·`17:50`·`18:07`) —
  전부 `phantom` → `replay_lag` 이고, **전부 세션이 실제로 회복한 관측**이다
  (프로덕션 킬 규칙도 그 넷에는 발동하지 않았다).
- ★**창 A 는 out-of-sample 이다** — 규칙은 창 B 8건에서 유도했는데 창 A 11건에서는
  두 식이 **11/11 일치**한다.
- **사망 상관(유일한 독립 검사)은 보존된다** — 사망 **4/4** 가 `phantom`.
- ★**그리고 게이트 판정은 그대로 `FAIL` 이다.** 교체가 통과를 사지 않는다 —
  `18:50`·`18:51` phantom + `auto_death` 가 열린 창 안에 그대로 남는다.

★★**「`replay_lag` 12/12 생존」은 과장이었다 — 정정한다.** `died_here` 는 「관측 시각 ±1초에
세션이 죽었나」이므로 **회복을 확인하지 않는다**. 실제로 `39731d57` 의 `16:24:01`(=`replay_lag`)
은 **60초 뒤 사망의 첫 짝**이다. 정확한 진술은 「12건 중 **11건**은 그 에피소드에서 세션이
회복했고, **1건은 사망 직전 tick 이었다**」다. (codex challenge 2026-08-05 적발.)

★**창 B 는 그 뒤로 자랐다** — 2026-08-05 03:00Z 기준 **22건**(창 A 11 + 창 B 11).
새 3건은 전부 살아 있는 세션 `a16aa640` 의 것이고 **두 판별식 모두 `replay_lag`**,
세션은 계속 살아 있다. 위 표의 n=19 는 **교체 시점의 코퍼스**이고 골든 회귀 테스트가
그 19행을 고정한다 — 코퍼스가 자란다고 그 표를 고쳐 쓰지 않는다.

**두 식 모두 오차 방향이 같다 — phantom 과소계상.** 도장이 안 찍힌 구간은 `replay_lag` 쪽으로
기울고, `Order.filled_at` 은 우리 관측시각이라 봉경계식도 같은 쪽으로 기운다.

★★★**그런데 그 방향은 이 게이트에서 fail-OPEN 이다 — 내가 위험 축을 잘못 적었다.**
「거짓 사망을 만들지 않는다」는 **킬 정책**의 축이고, **게이트**의 축은 반대다:
`phantom` 이 줄면 `window_start = disq[-1].at` 이 앞당겨지고 `countable` 이 늘어난다
(`soak_gate_predicate.py:362,405`) ⇒ **누적이 더 쌓이고 통과가 쉬워진다.**
과소계상은 게이트를 **관대하게** 만든다. (codex challenge 2026-08-05 적발.)

**남는 위험 — 재무장 도장에는 TTL 이 없다.** 마지막 도장 `H` 뒤에 체결 `F` 가 오면 그 발산이
이후 영영 낫지 않아도 `F >= H` 인 한 계속 `replay_lag` 이다. 이 식은 **회복을 확인하지 않는다.**
반증 조건: 「체결 뒤 파이프라인이 다시는 재무장하지 않는 동안 발산이 지속」. 실측 재발주 주기가
4~14분이라 살아 있는 세션에서는 곧 도장이 찍혀 `phantom` 으로 넘어가지만, **그 사이 구간은
credit 된다.** 이 위험은 `auto_death`(DB 에서 독립적으로 세어진다)가 뒤를 받치고 있을 뿐
판별식이 스스로 막지는 않는다. ⇒ 다음 판별식 후보는 **직접 회복 검사**다(「같은 세션의
다음 관측이 바로 다음 tick 인가」 — 원장도 시각 문턱도 안 쓴다).

### ★아카이브 판(版) — 개선이 게이트에 반영되려면 옛 라벨을 치워야 한다

실측 2026-08-05: 판별식을 교체하고도 게이트는 **여전히 `phantom` 7건**을 보고했다.
`soak-gate.sh` 가 **모든** `.soak/phantom-*.json` 의 verdict 를 합집합으로 모으고
`(시각, 종류, 상세)` 로만 dedup 하기 때문이다 — **취소된 라벨이 영원히 남는다.**
방향은 fail-closed 라 거짓 PASS 는 안 되지만, **개선이 게이트에 도달하지 못한다.**

⇒ ⑴ 분류기가 `PREDICATE_VERSION` 을 `--json` 과 아카이브에 싣는다
⑵ 아카이브들이 서로 다른 판이면 게이트가 **경고를 찍는다**
⑶ 판을 올리면 옛 아카이브를 **`.soak/superseded-<판>/` 로 옮긴다**(지우지 않는다).
2026-08-05 에 21벌을 `superseded-horizon-predicate/` 로 옮겼고, 그 뒤 C3 가 **7 → 3**,
전 이력 실격이 **17 → 9** 가 됐다. ★창 A 의 phantom 관측은 그 폴더에 보존돼 있고
`--events-json` 으로 재판정할 수 있다(해당 세션의 `auto_death` 는 DB 에서 계속 세어진다).

★**경고 조건은 「판이 둘 이상」이 아니라 「현행 판과 다르다」다** — 전자로 두면 **남은 것이
전부 구버전일 때 집합 크기가 1 이라 경고가 안 뜬다**(codex challenge 적발). 현행 판은 이
실행이 방금 남긴 아카이브가 들고 있으므로 그것을 기준으로 비교한다.

★**대가 — 아카이브를 옮기면 그 아카이브만 가지고 있던 `log_from`/`log_to` 커버리지도 같이
빠진다.** 그 구간은 C1/C2 credit 에서 제외되고 C4 도 더 이상 검사되지 않는다. 방향은
fail-closed(덜 세어진다)라 거짓 PASS 는 안 되지만 **「보존만 하면 된다」는 설명은 불완전**
했다. 옮기기 전에 남는 아카이브가 현재 창을 덮는지 확인해라. 2026-08-05 실측: 남은
아카이브가 `2026-08-04T15:51:23 ~ 현재` 를 덮고 창 시작이 `18:51` 이라 손실 0.

### FAIL 의 범위 — 기본 실행이 FAIL 을 낼 수 있어야 한다

기본 실행에서는 **지금 열려 있는 귀속 구간 안**의 실격 사건만 본다.
「T0 **초과**」로 두면 T0 가 곧 마지막 사건 시각이라 **기본 실행이 구조적으로 FAIL 을 낼 수
없다** — 실측 2026-08-05: 소크가 38분 만에 죽었는데 판정이 `UNKNOWN 진행중` 이었다.
조용히 0 으로 리셋된 것이다. ★**게이트의 첫 실제 사건이 게이트 자신의 결함을 드러냈다.**

FAIL 은 운영자가 `scripts/soak-stack.sh up` 으로 **새 창을 열 때까지** 남는다 — 그 명령이
「인지했고 다시 시작한다」는 명시적 행위다(워커는 재기동하지 않는다. 사망한 것은 라이브
세션이지 워커가 아니다). `--since` 로 창을 강제한 **회고** 실행은 그 창 전체를 본다.

## 근거

### 왜 누적인가, 그런데 왜 연속 24h 를 함께 거는가

**순수 누적**은 4시간짜리 42개로도 채워지므로 장기 지평의 결함을 구조적으로 못 본다.
**순수 연속**은 재시작 한 번에 전부 잃으므로 사실상 도달 불가다(작업 1이 재시작을 드물게
만들지만 0으로 만들지는 못한다).

그래서 **누적 168h 를 통과 기준으로 삼고 「연속 최장 ≥24h」를 별도 필수 조건으로** 함께 건다.
연속 조건은 창 정의 ②에 의해 **단일 커밋**에 대해 성립해야 하므로, 「이 코드가 24시간 무사고로
돌았다」는 주장이 된다 — 누적이 잃는 장기 지평을 그만큼 되산다.

**왜 24h 인가.** 두 가지가 상한을 정한다.

- 아래로 — 역대 최장은 **15.28h**(`e1f6d84c`)다. 24h 는 그 1.6배라 새 기록을 요구한다.
- 위로 — 원장 스캔 상한 `LEDGER_FILL_SCAN_LIMIT = 200`
  ([`order_repository.py:185`](../../backend/src/trading/repositories/order_repository.py))이
  실측 체결률에서 **약 37시간**이면 `overflow` 로 떨어진다([BL-591] 부수 관측). 48h 를 걸면
  BL-003 이 그 수리에 종속된다. 24h 는 그 지평 **아래**라 다른 BL 에 종속되지 않는다.

★**48h 가 더 충실하다는 반론은 유효하다.** 「1주 안정」의 문자 그대로에는 37h 지평을 넘는
증거가 필요하다. 그 경우 `LEDGER_FILL_SCAN_LIMIT` 수리가 [BL-003] 의 **선행 조건**이 된다 —
이 ADR 은 그 종속을 지금은 만들지 않기로 한 것이고, **선택이지 사실이 아니다.**

### 흡수(어둠) 비율을 PASS 요건에서 뺀 이유

`qb_live_ledger_derive_total` 의 판정 불가 outcome 비율(실측 19.0%, 흡수까지 median 26.6분)은
**보고 필수 · 문턱 없음**으로 둔다. 근거: 어둠은 **원장 veto** 를 가릴 뿐, 이 게이트가 실제로
쓰는 실격 신호는 가리지 않는다 — 자동 사망은 **DB** 에서, phantom 은 **워커 로그**에서 온다.
게다가 `duplicate_open` 은 흡수 상태라(`since = sess.created_at`) 장기 창에서는 사실상 100%가
어두워진다. 문턱을 걸면 [BL-003] 이 [BL-591] 계측 수리 없이는 영영 UNKNOWN 이 된다.

**대신 `tick 연속성`(C4)을 PASS 요건으로 넣었다.** 그게 「시계만 돌고 아무 일도 안 한 168h」를
실제로 막는 조건이다.

### 정의를 확정하기 전에 과거 원장에 적용했다 (구현 독립 오라클)

전 **30세션 · 56.70h** 에 술어를 그대로 재생한 결과:

| 판정          | 세션      | 비고                                                                                                                                |
| ------------- | --------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| **실격**      | **4건**   | `0e15c3c0` **tick_stall**(8.65h — 역대 2위) · `70063496` auto_death · `04097fdc` auto_death+phantom · `a201a47b` auto_death+phantom |
| 비실격        | 26건      | —                                                                                                                                   |
| **귀속 가능** | **0.46%** | 56.70h 중 **0.261h**. 나머지 56.44h 는 어느 커밋이 돌았는지 답할 수 없다                                                            |

★★★**「역대 최장 15.3h = 9%」는 두 겹으로 낙관이었다.** ⑴ 역대 2위 **8.65h 는 마지막
46.7분 동안 평가가 멈춰 있었다**(종단 tick lag). 지속시간만 세는 산식은 그 8.65h 를 전부
인정한다. ⑵ 어느 세션도 **어느 커밋이 돌았는지 답할 수 없다** — 그 시절엔 워커가 움직이는
작업 트리를 mount 하고 있었다.

정의가 과거를 **전부 PASS 로 만들지도, 전부 FAIL 로 만들지도 않는다.** 실격 4 / 비실격 26 /
귀속 0.46% 로 갈렸고, 앞으로의 창은 100% 귀속·검증되므로 **통과는 구조적으로 가능**하다.

### 살아 있는 세션의 종단 lag 으로 실격시키지 않는다

재기동 직후에는 정상적으로 여러 봉 뒤처졌다가 한 봉씩 따라잡는다(실측 2026-08-04 스택 교체:
5봉 뒤처짐 → 정상 복귀). 그 순간을 찍으면 **거짓 실격**이 되고, 실격은 누적을 0 으로 되돌리므로
거짓 양성 하나가 168h 를 통째로 날린다.

⇒ 살아 있는 세션은 **①연속 두 표본에서 bar time 이 얼어붙었는가**로만 판정하고, 종단 lag 은
**끝난 세션**에만 적용한다. ①은 따라잡는 중을 구조적으로 통과시킨다.

| `make -i` 우회                   | ⚠ **부분 반증**              | 실행해 보니 recipe 재검사가 compose 를 막고 `metrics-wipe` 도 SKIP — **피해 0**, 남는 건 exit code 거짓말뿐 | 기존 `assert-main-checkout` 와 같은 잔여로 기록        |
| heredoc 파이썬 주입              | ✅ 실재(P2)                  | psql 출력·CLI 인자가 파이썬 **소스로** 확장됐다                                                             | `<<'PY'` + argv/파일로만 전달                          |

★★**수리하다가 내가 결함을 하나 더 만들었다** — TSV 를 stdin 으로 파이프했는데
`python3 - <<'PY'` 는 **stdin 을 프로그램으로 읽는다**. 세션 목록이 조용히 비었고
`auto_death` 실격이 통째로 사라졌다. **판정이 조용히 관대해지는 방향으로** 틀렸다.

★**교훈** — 「세 낱말을 각각 낼 수 있다」를 **자기시험으로만** 증명하면 그 경로가
**운영 조건에서 도달 가능한지**는 증명되지 않는다. 실제로 기본 실행은 구조적으로 FAIL 을
낼 수 없었고(§FAIL 의 범위), 자기시험만 초록이었다.

## 대안 (거부됨)

**(a) 연속 168h.** 재시작 한 번에 전부 잃는다. 작업 1이 재시작을 드물게 만들지만 0으로 만들지
못하므로(호스트 재부팅·도커 업그레이드·패키지 변경) 사실상 도달 불가다.

**(b) 순수 누적 168h.** 사용자 원안. 4시간짜리 42개로 채워져 장기 지평 결함(37h `overflow`,
흡수 누적)을 영영 안 밟는다. **연속 24h 조항으로 보완했다.**

**(c) 흡수 비율 ≤50% 를 PASS 요건으로.** 더 엄격하지만 `duplicate_open` 이 흡수 상태라 장기
창에서 도달 불가다 — [BL-003] 이 [BL-591] 계측 수리에 종속된다. **보고 전용으로 낮췄다.**

**(d) phantom 커버리지를 boolean C5 조건으로.** 로그의 마지막 줄이 항상 `now` 보다 앞서므로
매 실행이 UNKNOWN 이 된다. 허용 오차를 두면 그만큼이 검증 없이 credit 된다.
**자르기(창 정의 ④)로 대체했다.**

**(e) 귀속 불가 시간(56.44h)을 소급 인정.** 「그때도 코드는 잘 돌았다」는 참일 수 있지만
**증명할 수 없다.** 소급 인정하면 이 정의가 거르는 것이 사실상 없어진다.

**(f) 판별식은 그대로 두고 「경과 시간 문턱만 완화」.** 「6.9초짜리를 phantom 이라 부르는 게
문제니 문턱을 2봉·5분으로 올리자」는 안. **거부** — ⑴ 그건 **정의를 통과시키기 쉬운 쪽으로**
바꾸는 것이고 ⑵ 실측 재발주 주기가 4~14분이라 어떤 고정 문턱도 창마다 틀리며 ⑶ 문턱을
올리면 `04097fdc`(경과 2276초)만 남고 **`39731d57`(경과 61.55초, 실제 사망)을 놓친다** —
사망 상관 4/4 가 3/4 로 깨진다. 재무장식은 문턱이 아니라 **시스템 자신의 이벤트**를 쓰므로
그 셋을 동시에 피한다.

**(h) 실격 종류별로 리셋을 나눈다** — 「코드 결함이면 T0 리셋, 운영 사고면 그 세션만 배제」.
2026-08-08 에 실제로 제기됐고, 동기는 정당하다: 자동사망 8건 중 **1건은 코드가 아니라 이중 호스트
오염**이었고([BL-633]), 그 창이 코드 평가에 섞여 **[ADR-025] 반례 판정을 한 번 틀리게 만들었다**.
**거부** — ⑴ 「운영 사고였다」의 **판정 주체가 사람**이다. 그 판정이 리셋을 면제하면 게이트를
통과시키는 가장 싼 길은 코드를 고치는 것이 아니라 **원장에 `operational` 이라고 쓰는 것**이 된다.
⑵ 그 판정은 싸지 않다 — 이번 오염 부검은 사흘이 걸렸고 판정식이 **두 번 반증**됐다(LESSON-082).
사후에, 압박 속에서, 자기 회차를 살리려는 사람이 내리는 판정이 그 품질일 리 없다.
⑶ 방향이 **fail-open** 이다(§codex 적대 리뷰가 반복해서 지적한 바로 그 방향).
⇒ 대신 **판정에 참여하지 않는 원장**으로 낮췄다 (§실격 귀속 원장). 분류는 남기고 면제는 안 준다.

**(g) 아예 `auto_death` 만 실격으로.** n=19 에서 phantom **에피소드** 4개 ≡ 사망 4건이라
`phantom` 이 `auto_death` 와 중복인 것은 사실이다. **거부** — 킬 규칙은 「연속 2회 **판정된**
tick」이라 `probe_failed` 가 사이에 끼면 strike 가 안 이어진다([BL-591] D1). 그때 낫지 않은
발산이 **아무 데도 안 잡힌다.** 조기 신호를 남긴다.
