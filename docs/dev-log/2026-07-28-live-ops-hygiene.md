## 한 줄

라이브 조건부 진입이 남긴 **정리 주체 부재**를 닫고 계정 스코프 표의 **누르면 실패하는 버튼 두 축**을 없앴다. 그리고 이 스프린트는 **구현자와 판정자를 분리했을 때 무엇이 잡히는지**에 대한 1회차 데이터다.

## ★핵심 발견

### 1. ★★★게이트가 전부 green 인 상태에서 P1 이 세 번 나왔다

이게 이번 스프린트의 본론이다. 아래 셋은 **모두 BE·FE 스위트가 통과하는 상태에서** 발견됐다.

| 발견 장치            | 그때 게이트                 | 발견한 것                                                                             |
| -------------------- | --------------------------- | ------------------------------------------------------------------------------------- |
| 거래소 실주문 오라클 | BE 3226 passed              | Bybit 이 `orderId` 를 우선해 **살아 있는 주문을 "미발주" 로 오판**하고 reject         |
| 변이 주입            | 표적 84 passed              | cutoff 를 **0 으로 무력화해도 통과**하는 테스트(거짓 게이트)                          |
| 적대 검증 3기        | BE 3226 passed              | **유령 케이스가 한 건도 안 닫힌다** — task 는 `{0,0,0}` 으로 "고칠 게 없었다" 를 보고 |
| codex 최종 리뷰      | BE 3247 · FE 1181 · e2e 101 | 접기가 **hedge 의 실포지션 leg 를 화면에서 지운다**                                   |

이유는 하나다 — **생성자가 쓴 테스트는 생성자의 구현을 비춘다.** codex 의 테스트는 ccxt 를 mock 하므로 "Bybit 이 `orderId` 를 우선한다" 를 **구조적으로 볼 수 없다**. 파이프라인 문서 §1 이 예측한 실패 모드가 1회차에서 그대로 재현됐고, 차단 장치(구현 전 동결한 수용 기준 + 표적 변이 + 외부 오라클)가 실제로 그것을 잡았다.

### 2. ★★내 결론 하나가 거래소에 의해 반증됐다 (F-A 철회)

나는 "ccxt 는 `trigger=True` 일 때만 `orderFilter=StopOrder` 를 붙이므로, 그걸 안 넘기는 우리 probe 는 조건부 주문에 **무력**하다" 고 결론냈다. codex 도 독립적으로 같은 결론을 냈다(P1-2). **둘 다 틀렸다.**

데모 거래소에 조건부 주문을 실제로 올려 물어보니(2회 독립 실행) —

| 조회                                | 결과    |
| ----------------------------------- | ------- |
| 진짜 `orderId` 단독 (= 기존 probe)  | **1건** |
| `orderId` + `orderFilter=StopOrder` | 1건     |
| `orderId` + `orderFilter=Order`     | 1건     |
| 심볼 목록, `orderFilter` 없음       | 1건     |

`orderId` 가 지정되면 Bybit 이 필터를 느슨하게 적용한다. **기존 probe 는 죽어 있지 않았다.**

★교훈은 "둘이 같은 답을 냈다" 가 신뢰의 근거가 아니라는 것이다. 나와 codex 는 **같은 내부 증거(ccxt 소스 + 우리 코드)** 를 봤으므로 독립 표본이 아니었다. 외부 오라클만이 그것을 깼다.

★그리고 그 필터는 무해하지도 않았다 — 조건부 주문이 **트리거되면 StopOrder 큐를 떠나므로** `orderFilter=StopOrder` 는 체결된 주문을 숨겨 `rejected` 로 찍을 수 있었다. 상방 0, 하방 실손실.

### 3. ★★초안 설계가 "장부 잡음" 을 "관리 불가 실주문" 으로 바꿀 뻔했다

BL-503 form 1(제출 중단, `submitted` + `exchange_order_id` NULL)을 **"물어볼 대상이 없으니 `rejected`"** 로 처분하려 했다. dispatch 순서를 읽고 나서 뒤집혔다 — `transition_to_submitted`+commit → `provider.create_order`(**거래소 등재**) → `attach_exchange_order_id`+commit. 그 사이에 죽으면 **주문은 거래소에 살아 있다.**

물어볼 대상은 있었다. `tasks/trading.py:377` 이 `client_order_id=str(order.id)` 를 싣고 provider 가 Bybit `orderLinkId` 로 보낸다. **거래소는 우리 `Order.id` 를 안다.**

★그리고 codex 가 한 걸음 더 갔다 — `transition_to_rejected` 에 `exchange_order_id IS NULL` CAS 가 없고 worker 가 `attach` 의 rowcount 를 안 보므로, reject 뒤 늦은 attach 가 **조용히 no-op** 되어 id 를 영원히 잃는다. janitor 전용 CAS 전이를 새로 만들었다.

### 4. ★★거짓 게이트 두 건 — 둘 다 "실패할 수 없는 단언"

| 위치                        | 증상                                 | 원인                                                                |
| --------------------------- | ------------------------------------ | ------------------------------------------------------------------- |
| janitor cutoff 테스트       | cutoff 를 0 으로 만들어도 84건 green | 판별자로 던진 `AssertionError` 를 코드의 `except Exception` 이 삼킴 |
| BL-502 과차단 테스트        | 고정 단일 키로 바꿔도 green          | 부정 단언을 `waitFor` 로 써서 **t=0 에 즉시 성공**                  |
| identity 백필 commit 테스트 | `commit()` 을 지워도 green           | 같은 SQLAlchemy 세션의 identity map 에서 다시 읽음                  |

셋 다 "맞는 것" 을 단언하고 있었지만 **그 단언이 실패할 수 있는 경로가 없었다.** 앞의 둘은 변이 주입이, 셋째는 codex 최종 리뷰가 잡았다.

★일반화 — **부정을 `waitFor` 로 단언하지 마라**(동기화 지점을 먼저 잡아라). **예외를 삼키는 코드 경로에서 예외를 판별자로 쓰지 마라**(호출 기록으로 검증하라). **같은 세션에서 다시 읽는 것은 commit 을 검증하지 못한다**(spy 를 써라 — 레포 규칙 `backend.md` §3 이 이미 요구한다).

### 5. ★★화면 검증은 내가 만들 수 있는 상태만 검증한다

G4 에서 데모 계정에 실제 포지션을 열고 확인했다 — 같은 uid 계정 2개가 **행 1개**로 접히고, 대표가 **쓰기 가능** 계정이고, 청산 버튼을 눌러 체결되고, 거래소가 flat 이 됐다. 3중 대조 전부 일치.

**그런데 그 화면이 P1 을 통과시켰다.** 접기가 hedge 의 두 leg 를 병합해 하나를 지우는 결함은 dogfood 계정이 **one-way 단일 leg** 라 재현되지 않았다. 화면에 없는 상태는 화면 검증이 못 본다.

★그래서 화면 검증은 코드 대조·변이·적대 검증을 **대체하지 않는다.** 이번엔 codex 최종 리뷰가 서버 테스트(`test_hedge_legs_are_not_closable` 가 2행을 단언)와 FE 접기 로직을 대조해서 잡았다.

### 6. ★uid 로 접되 청산은 계정 id 로 — 두 축을 갈라놓아야 했다

BL-501 의 자연스러운 설계는 "같은 uid 면 대표 계정 하나만 조회" 였다. **그러면 기능이 역효과였다.** 세션 귀속과 자격증명은 uid 가 아니라 `exchange_account_id` 에 묶여 있어(`live_signal_session_repository.py:92`), 실측 배치처럼 read-only 형제가 그 심볼 세션을 갖고 있으면 쓰기 대표가 `no_owning_session` 이 되어 **청산 버튼이 오히려 사라진다.**

채택 = **표시 전용 접기.** 계정은 전부 조회하고 화면에서만 병합하되, 살아남은 행의 청산 대상은 **쓰기 가능 + 귀속 세션 보유** 형제에서 고른다. `close_service` 무변경 → 청산 시맨틱 무변경. 15초 잔존 창은 접기가 아니라 **청산 시 uid 형제 스냅샷 키까지 삭제**해서 닫았다.

## 함정 (이번에 실제로 밟거나 확인한 것)

- ★**codex 는 이 스택의 DB(5433)에 접속하지 못한다.** 샌드박스가 소켓을 `PermissionError` 로 막는다. 그래서 codex 의 "테스트 통과" 보고는 **DB 비의존 서브셋만**이고, 전체 스위트는 매번 내가 돌려야 했다. 실제로 codex 가 green 이라 보고한 상태에서 DB 테스트 1건이 red 였다(patch 대상 오류).
- ★**모델에 컬럼을 추가하면 `tests/test_migrations.py` 가 로컬에서 깨진다.** conftest 의 `create_all` 이 새 컬럼을 먼저 만들고, `quantbridge_test` 는 이전 head 에 스탬프돼 있어 `upgrade head` 가 `DuplicateColumn` 을 낸다. `alembic stamp head` 로 정렬하면 해소된다 — 코드 결함이 아니다.
- ★**배포는 migration-first 여야 한다.** 새 ORM 필드가 모든 `ExchangeAccount` select 에 즉시 포함되므로 코드가 먼저 뜨면 `UndefinedColumn` 이다. nullable 추가라 구 코드와는 호환되므로 **마이그레이션 → 코드** 순서면 안전하고, 롤백은 반대(코드 → 마이그레이션)다.
- ★`git checkout <file>` 로 변이를 복원하지 마라 — 그 파일의 신규 코드까지 사라진다. 문자열 치환 쌍 + 마지막 복원 확인.
- ★이번엔 **stale CSS 거짓 red 가 재발하지 않았다.** 프로덕션 빌드 후 dev 서버 정체성을 재확인했고 캐논 32건이 그대로 통과했다.

## 남긴 것

- **BL-499** 열림 — 신설 metric 실관측 **0건**. beat 은 정상 발화하지만 고착 행이 0이라 경로가 주행되지 않았다. "관측되지 않음" 이지 "일어나지 않음" 이 아니다.
- **BL-505** 신규 — 청산 lock 축이 포지션 정체성이 아니라 `sessionId + symbol`.
- **BL-506** 신규 — worker 프로세스 metric 이 스크레이프되지 않아 gauge 규율 전체가 관측 불가. ★BL-503 이 닫았다고 적은 gauge 표류가 **배포 토폴로지에서는 안 보인다**.
- **BL-507** 신규 — 접기·청산 가능성 판정이 view 안에 있다. 이번 P1 이 그 경계에서 나왔다.
- **기각(사유 기록)** — identity 조회 실패 시 read-only 차단이 fail-open 인 것. 의도된 설계다. 모를 때 막으면 **정상 계정의 청산까지 끊긴다** — 기능이 안 되는 쪽이 잘못 막는 쪽보다 안전하다.

## 파이프라인 1/3 회차 평가

**작동했다.** 구조적 분리가 실제로 비순환성을 만들었고, 자기 검증이었다면 놓쳤을 것을 네 장치가 각각 잡았다.

**비용도 실측됐다** — codex 세션 8회(플랜 검증 1 + 구현 3 + 정정 4), 내 게이트 실행 10회 이상. BL 1건당 왕복이 2~4회였고 그중 절반은 **codex 가 DB 를 못 돌려서** 생긴 왕복이다.

**다음 회차에 바꿀 것** — codex 태스크 스펙에 "DB 의존 테스트는 평가자가 돌린다" 를 처음부터 명시해 codex 가 통과 여부를 추측하지 않게 하고, 수용 기준에 **"이 변이가 red 여야 한다" 를 구현 전에 함께 준다.** 이번에 거짓 게이트 3건이 전부 "테스트는 있는데 실패할 수 없다" 였으므로, 변이를 수용 기준의 일부로 넘기면 생성자가 처음부터 그것을 만족시킨다.
