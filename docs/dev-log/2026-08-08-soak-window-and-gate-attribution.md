# 2026-08-08 — soak-window-and-gate-attribution

> 창을 안 끊고 게이트의 **귀속**을 세운 회차. `backend/src` **0줄** · 커밋 5 ·
> 소크 무중단(C1/C2 **9.00h**, 재-pin 0회 · 실격 0).

## 이 회차가 물은 것

`status.md` ⓪ 표는 후보 5개를 놓고 A([BL-634] 계정 배타성)를 ★★★로 밀었다. 그런데 **표의
어느 후보도 P0([BL-003])를 전진시키지 않는다** — [BL-641] 자신이 이미 적어 뒀다:

> 오염은 자동사망 8건 중 1건뿐이었다(나머지 7건은 맥→오라클 이관 전이라 호스트가 하나였다).
> 「배타성을 고치면 MTBF 가 오른다」는 성립하지 않는다. [BL-634] 가 사는 것은 **재발 방지**다.

그래서 표의 진짜 축은 「A vs B~E」가 아니라 **「창을 끊는가 / 지키는가」**였다. A 만
`backend/src` 를 건드리고, 건드리면 re-pin 이 필요하며, 그때 태울 값이 지금 9시간이다.
⇒ **A 의 최적 시점은 「지금」이 아니라 「다음 사망 직후」**(re-pin 비용 0)이고, 이 회차는
창을 지키면서 아무도 안 물은 질문을 물었다 — **게이트 자신은 정당한가.**

## ★★★핵심 — ADR-024 는 자기가 기각한 안을 집행하고 있었다

[ADR-024] §대안 **(a) 「연속 168h」를 명시적으로 거부한다** — 「재시작 한 번에 전부 잃는다 …
사실상 도달 불가다」. 그리고 §대안 (b)는 순수 누적을 「연속 24h 조항으로 보완했다」고 적는다.
**설계 의도는 (a)를 피하는 것이었다.**

그런데 `soak_gate_predicate.py:502` 의 `window_start = disq[-1].at` 가 하는 일이 **(a) 그
자체다.** 실격 하나가 C1 을 0 으로 되돌리므로 C1 은 「연속 168h」와 동치이고, (b)의 「4시간짜리
42개」는 구조적으로 불가능하다.

★**§163 과 §621 이 서로 다른 자리에 있어서 아무도 잇지 못했다.** §163 은 「**서술**이 틀렸다」로
봉합했고 §대안은 「(a)는 거부」로 남아 있었다. 둘을 같이 읽으면 **거부 사유가 그대로 현행 동작의
비용**이다 — 24h 도달 **0/39** · 최장 19.42h · 요구치는 그 8.65배.

**판정 = 동작 유지.** 셋 다 더 나쁘기 때문이다(문턱 인하 = 통과를 판다 · 클립 = codex 가 잡은
거짓 PASS 복원 · 사인별 리셋 = fail-open). 대신 **판정에 참여하지 않는 원장**으로 낮췄다.

## ★새 층이 곧바로 자기 자신을 겸손하게 만들었다

오염 1건을 사망에서 빼자 MTBF **14.52h → 16.59h** 인데 **95% CI 가 전 이력과 겹친다**
([8.05, 41.27] ↔ [7.37, 33.63]). ⇒ **「오염을 빼면 MTBF 가 낫다」고 말할 수 없다.** 이 회차가
만든 장치가 이 회차의 결론을 사지 않았다는 뜻이고, 그게 이 도구의 설계 목적이다.

★**`position_divergence` 5건을 `code_defect` 로 적지 않았다.** [ADR-025] 가 「사망 5/5 를
상류에서 닫았다」고 적지만 **그 5건이 이 5행과 같은 집합인지 행 단위로 대조된 적이 없다.**
「닫았다」는 서술과 「이 사망이 그 원인이었다」는 귀속은 다른 주장이다 — 그 대조가 다음 작업이다.

## 반증된 것 (내 것 넷 · 문서 것 셋)

### ★★★내 [가정]이 틀렸다 — 9.03h 는 역대 **4위**다

계획서에 「역대 2위권」이라 적고 `[가정]` 표시를 달았는데, `mtbf_stratified.py` 로 재니
**4위**였다(19.42 / 15.28 / 12.34 / **9.03** / 8.65). ADR-024 가 적어 둔 「역대 2위 8.65h」도
낡은 값이었다(지금 5위). ⇒ **순위는 세션이 하나 늘 때마다 낡는다. 박지 마라.**

### ★★★[BL-650] 재현 실패 — 그리고 그것이 결과다

| 조건             | idle CPU | `/` 응답      | RSS    |
| ---------------- | -------- | ------------- | ------ |
| 1.99GB (기록)    | 416.9%   | 120s 타임아웃 | 1000MB |
| **593MB (실측)** | **0.1%** | **0.61s**     | 945MB  |

증상은 **크기 단조가 아니다** — RSS 는 이미 945MB 인데 CPU 는 0.1%. 1.99GB 를 만들려면 며칠이
걸리므로 **문턱을 아래에서 잴 수 없었다.** ⇒ `make fe` 경고선 1GB 는 **정책이 아니라 관측
장치**이고 근거는 두 점뿐이다. 그 사실을 Makefile 주석에 적었다.

### ★★`turbopackMemoryLimit` 은 존재하지 않는다

[BL-650] 이 적은 수리 방향 ①이 **실행 불가**였다. Next 가 `experimental.turbo.memoryLimit` 과
`experimental.turbopackMemoryLimit` 을 **둘 다 제거**했고 대체가 없다. 실재하는 손잡이는
`turbopackFileSystemCacheForDev`(dev 기본 켜짐) 와 `turbopackMemoryEviction`(기본 `'auto'`) 둘뿐.
⇒ **백로그의 「택1」 목록도 실재 여부를 확인하고 적어야 한다.**

### ★★내 테스트가 이름이 주장하는 것을 안 쟀다 — 변이가 잡았다

`test_one_ledger_row_cannot_attribute_two_disqualifications` 를 써 놓고 M3(`pop` → `get`) 변이를
걸었더니 **50 passed** 였다. 그 테스트는 같은 시각에 **`kind` 가 다른** 실격 둘을 놓았는데,
키가 다르면 `pop` 이든 `get` 이든 결과가 같다. 진짜 `pop` 이 사는 자리는 **같은 `(at, kind)` 의
실격 둘**(같은 순간 다른 세션)과 **매칭된 행이 stale 로 재보고되지 않는 것**이었다. 둘 다
테스트로 세우자 M3 가 **2 failed** 로 잡혔다.
⇒ **이 레포가 이미 덴 자리다**(「워커의 충돌 테스트가 이름이 주장하는 것보다 적게 단언했다」).

### ★★zsh 배열은 1-based — 변이 하나가 아예 안 돌았는데 출력은 그럴듯했다

`declare -a` + `${ARR[0]}` 로 변이 루프를 짰더니 첫 원소가 **빈 문자열**이라 M4 가 통째로
건너뛰어졌고, 표는 이름과 결과가 한 칸씩 밀린 채 **정상처럼 보였다**(AssertionError 한 줄만
위에 찍혔다). ⇒ **변이 하네스는 「몇 개 돌았나」를 스스로 세게 하거나, `while read` 로 짜라.**

### ★★`pgrep -f "next dev"` 는 부모 래퍼를 준다

그 PID 로 재면 RSS 71MB · CPU 0.18s 라 **「서버가 조용하다」로 읽힌다.** 실제 서버는 자식이고
(RSS 945MB) 판별자는 **`lsof -nP -iTCP:<port> -sTCP:LISTEN -t`** 다.
⇒ **[BL-650] 계열의 측정 도구 오류가 이번에도 났다** — 그 백로그가 경고한 `ps -o pcpu` 함정과
**다른** 함정이다.

### ★낡은 빌드 5벌 8.5GB 를 `.gitignore` 가 가려 왔다

`frontend/.gitignore:3` 의 `.next*/` 때문에 git status 에 영원히 안 나온다. 백로그는 「4벌」이라
개수만 적고 크기를 안 쟀다 — 실제로는 **5벌 8.5GB**(`.next.stale-fp-20260723` 5.8G ·
`.next.bak-turbocache` 2.0G). 레포 **26G → 18G**.

### ★게이트가 착지 직후 나를 두 번 물었다

⑴ `bl-audit` — 상태 어휘를 「🟡 **부분 —**」로 썼더니 `UNKNOWN (어휘 미해석)`. 정본은
「부분 해결 / 부분 Resolved / 부분 완료 / Partial」다. ⑵ `docs-audit` — 인덱스 표 행이 **1119자**로
상한 1000자 초과. 둘 다 **문장을 비틀지 않고** 어휘와 길이를 고쳤다.
