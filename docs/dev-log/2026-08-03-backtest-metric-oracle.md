## 1. 무엇이 문제였나

`baseline_metrics.json` 은 코퍼스 5벌 × 12 metric 을 고정한다. 그런데 그 5벌이 **전부 자본을
음수로 몰고 끝난다** — 사이징을 선언하지 않아 `compute_qty` 가 1.0(=1 BTC ≈ $64,000)을 돌려주고
초기자본 10,000 위에서 그게 돈다(BL-466 이 이미 등재한 사실).

귀결: `sharpe_ratio` 가 **5벌 모두 정확히 `"0.00000000"`**, `sortino_ratio`·`calmar_ratio` 가
**5벌 모두 `null`**. 값이 상수로 못 박혀 있으니 세 지표의 **산술**이 회귀해도 baseline diff 에
움직일 여지가 없다. 게다가 `sharpe_convention` 은 baseline 에 아예 없어 컨벤션이 뒤집혀도 diff 0.

## 4. 가장 아픈 숫자 — 하루치 백테스트가 Sharpe 16.56 을 보고했다

`_periodic_returns` 의 daily fallback 이 리샘플 없이 **전 bar** 를 기간 표본으로 쓰면서 RFR 은
일간(2%/365)을 적용했다. 즉 1시간 봉 하나를 하루로 셌다.

| 같은 자본 경로 `[100, 110, 99]` 를 | sharpe        | sortino       |
| ---------------------------------- | ------------- | ------------- |
| 1D 봉 3개로 적으면 (참 값)         | −0.000548     | −0.000774     |
| 1h 봉 72개로 적으면                | **−0.003265** | **−0.004614** |

그리고 하루치 1h 봉 24개 상승 구간에서는 23개의 가짜 "일간" 수익률로 **Sharpe 16.56**.
없는 정보를 지어내고 있었다. 리샘플 후 표본이 2 미만이면 이제 `unavailable` 이다.

★**이건 이론이 아니다** — `scripts/seed_dogfood.py` 의 `daily` RunSpec(2026-03-02~03-30,
`TIMEFRAME="1h"`)이 정확히 이 케이스라, dogfood 화면이 그동안 이 숫자를 보여주고 있었다.

★**백로그의 우려는 빗나갔다.** BL-461 은 "고치면 sortino 값도 바뀌어 baseline regen 이
2 metric 으로 번진다" 를 걱정했다. 실제 regen diff 는 **0행**이었다 — 코퍼스 7벌이 전부 월간
경로라 daily 분기를 아무도 안 탄다. 그래서 원래 이 결함은 **골든 오라클로 도달 불가**였고,
단위 hand-oracle 로만 잡을 수 있었다.
