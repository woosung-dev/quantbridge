## 무엇을 고쳤나

**BL-543 — position epoch.** 엔진 포지션은 outbox 발행을 허용한 epoch **이후 bar 에서만** 쌓인다. 재생은 지표 warmup 으로 그대로 돌리되 epoch 이전 상태(open/closed 거래 · exit 브래킷 · `running_equity` · `liquidation_count`)를 폐기한다. epoch 은 기존 `live_signal_states.last_strategy_state_report` JSONB 키(`_qb_position_epoch`) 하나로 영속 — 선례 `_DIRECTION_MISMATCH_KEY`. `strategy_state.discard_state_before_epoch()` 21줄 순수 추가.

**BL-535 — 백테스트 계기 정렬.** `TimescaleProvider.get_ohlcv` 가 canonical(`BTC/USDT`)을 받아 **상품 키**(`BTC/USDT:USDT`)로 lock·gap·fetch·insert·get_range 한다. **fetch 경로 1사이트** — 세 소비자(backtest·optimizer·stress_test)가 이 프로토콜 하나를 지난다. 신규 변환 함수 없음(`to_ccxt_perpetual_symbol` 재사용). 경계 정본 신설: `docs/reference/instrument-symbol-boundary.md`.

## ★문서 모순 2건 — 실측으로 정정했다

**① worker 는 `src` 를 bind-mount 한다.** `status.md` 와 워커 보고가 "bind-mount 하지 않는다(baked image)" 라고 적었으나 `docker inspect` 실측은 `backend/src → /app/src (ro)` 였다. `gates-and-traps.md:72` 쪽이 맞았다. 이 모순이 위험한 이유는 **양쪽 다 잘못된 행동을 유도**한다는 것이다 — "baked" 를 믿으면 불필요한 rebuild 를 하고, 반대로 워크트리에서 "bind-mount 니까 내 코드가 돈다" 고 믿으면 **메인 코드를 자기 코드로 착각**한다(그게 워크트리에서 celery 검증이 불가능한 이유다). 이번엔 `_qb_position_epoch` 가 기록된 것이 **worker 가 stage 코드를 돌고 있다는 실행 증거**였다.

**② "이 레포에서 병렬화가 가능한 것은 읽기뿐" 은 더 이상 사실이 아니다.** `generator-evaluator-pipeline.md` G3-4 가 테스트 DB 1개를 전제로 그렇게 못박았는데, 워크트리 슬롯 체계(PR #495/#500)가 `quantbridge_w{N}_test` + Redis lock DB 분리로 그 제약을 풀었다. 이번에 두 워커가 슬롯 1·2 에서 **동시에 pytest 를 돌려 서로를 깨지 않았다.**

## 방법론 관찰기록 (지표는 착수 전 동결)

교란을 먼저 적는다: **작업 난이도가 다르므로 우열 판정이 아니다**(diff 2배, 위험도 🔴 vs 🟡).

| #   | 지표                     | `bl543` (B)         | `bl535` (A) |
| --- | ------------------------ | ------------------- | ----------- |
| 3   | 자기 보고 BE pytest      | 3451                | 3432        |
| 4   | ★**CONTROL 재측정 격차** | **0**               | **0**       |
| 5   | blocked / 사람 개입      | 0 / 1회             | 0 / 1회     |
| 6   | 표적 변이                | **16/16 전건 판별** | 4종         |
| 7   | 금지 경로 침범           | 0                   | 0           |

baseline 3424 + 27 + 8 = **3459** = 통합 실측. 두 방법론 모두 **자기 보고와 실측의 격차가 0** 이었고, 합쳐서 깨지는 상호작용 결함도 없었다.

갈린 것은 **외부 검증자의 유무**다. B 는 codex 가 G1(코드 쓰기 **전**)에서 FAIL 8건을 내고 **전건 재현·기각 0**, G6 에서 P1 2건을 추가 실재 판정했다. 그중 P1-A 는 "catch-up 발행 창과 epoch 이 어긋나면 **실주문을 내고 그 포지션을 즉시 잊는다**" 였고, codex 가 "state 행 없는 예외" 로 좁게 본 것을 워커가 실측으로 넓혀 **불변식 clamp** 로 잡았다. A 는 자기 검증만 했지만 기존 유틸을 재사용하고 BL 을 Resolved 로 표기하지 않는 등 **과장을 피했다** — 게이트를 어느 커밋에서 쟀는지(amend 사실까지) 스스로 적었다.

★**두 방법론 다 무개입 완주는 못 했다.** 각 1회 개입이 필요했고, `bl543` 은 `agent_status=idle` + `status=running` + **커밋 0건** 상태로 멈춰 있었다. `idle` 은 "입력 대기" 이지 완료가 아니다 — **완료 판정은 `status` 파일과 커밋 수로만 해야 한다.**
