## 한 줄

라이브 자동매매가 `strategy.entry(..., stop=)` 진입을 **거래소에 올린 적이 없었다.** 선언적 reconcile 로 등재·취소·동기화·청소를 배선하고 차단을 풀었다. 데모에서 **조건부 진입 5건이 실제 체결**됐고 거래소 원문과 5/5 일치했다.

---

## 왜 이게 필요했나

지난 스프린트가 남긴 상태 — stop-entry 전략은 세션 시작이 422 로 막혀 있었다. 거짓말은 멈췄지만 시드 전략 `s1_pbr` 은 진입 2개가 100% 이 경로라 **라이브를 아예 못 돌았다.**

```
strategy_state.py:619-630   entry(stop=) -> PendingOrder 파킹 + return None (이벤트 미발행)
event_loop.py:351-353       run_live 가 action not in ("entry","close") 를 버림 -> "fill" 폐기
                            독스트링: "broker 가 자체 fill 알림 처리"  <- 그 stop 을 올린 적이 없다
```

원장이 증상을 그대로 담고 있었다 — PbR 세션 `0e15c3c0` 이 8시간 동안 **close 29건 / entry 0건**.

## ★★설계 — delta 를 버리고 `target_position` 으로

내가 codex 에게 준 최초 지시("역전 사이징 = `|보유| + 신규`")는 **인터페이스 자체가 틀렸다.** 적대 검증(E1)이 P1 4건을 잡았고 그중 3건이 하나의 근본 원인이었다.

| 지적                                   | 재현                                                                                                                                                                              |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 같은 id 재발행이 포지션 **2배**        | `check_pending_fills` 가 체결 시 같은 id 를 **먼저 닫고 다시 연다**(`strategy_state.py:788-796`). 순변화 0인데 delta 8을 보내면 거래소는 +16. **시드 `s1_pbr` 이 정확히 이 형태** |
| pending 2건이면 delta 가 **서로 모순** | 각자 "지금 포지션" 을 가정하는데 한쪽이 체결되면 그 가정이 깨진다                                                                                                                 |
| 가산 수량이 엔진 마진 게이트 미통과    | 엔진은 `order.qty` 만 심사                                                                                                                                                        |

**교체한 계약** — 스냅샷은 **`target_position`**(체결 후 순 포지션)을 싣고, 주문 수량은 reconciler 가 **거래소 실포지션과의 차**로 계산한다. 거래소가 시뮬과 어긋나도 매 tick 스스로 수렴한다.

★**이 재설계의 값이 dogfood 에서 실증됐다.** 관측 시점에 시뮬 포지션은 `-0.0291`(숏), 거래소는 `0`(flat)이었다. delta 방식이었다면 `|0.0291 − (−0.0291)| = 0.058` 로 **정확히 2배**를 발주했을 것이다.

## 적대 검증이 잡은 것 (E1~E4)

- **E2** — 계획기의 미매칭 정리 루프에 **소유 판정이 하나도 없었다.** `actual` 에 우리 TP/SL 이 섞이면 **사용자 손절이 지워지는 경로**가 열려 있었다. `reduce_only=True` 는 절대 취소하지 않는 마지막 방어선을 계획기에 뒀다.
- **E4** — ★**멱등성 재생.** `OrderService.execute` 는 같은 key 를 다시 보면 **거래소로 dispatch 하지 않고** 캐시 응답을 돌려준다. key 가 `(trade_id, 가격, 수량)` 만으로 결정되면 **취소 후 재등재가 거래소에 닿지 않는데 DB·metric 은 "등재됨" 으로 보고**한다. key 에 `bar_time`(epoch 초)을 넣어 바 단위 멱등으로 바꿨다.
- **E4** — `current_position` 이 **같은 tick 의 비동기 시장가 dispatch 이전 값**이라 초과 수량 진입(실측 예 3배). 시장가 이벤트가 있는 tick 은 reconcile 을 한 tick 미룬다.
- **E4** — notional 게이트가 mark 로 검사했다. 조건부는 **트리거가**에서 집행되므로 long 돌파에서 명목을 과소평가해 게이트를 통과시키고 트리거 시점에 거래소가 조용히 거부한다.

| 층          | 출처                          | 결과                                                                  |
| ----------- | ----------------------------- | --------------------------------------------------------------------- |

### ★dogfood 가 잡은 결함 2건

1. **눈금 미만 무음 드롭 (P1 정직성).** 시드 PbR 의 `position_size_pct` 가 0.01% 라 목표가 `0.00029138`, BTCUSDT 스텝은 `0.001`. 절삭하면 0이 되는데 계획기가 **조용한 no-op** 으로 넘겼다. 화면엔 대기 주문이 뜨는데 거래소엔 영원히 안 나가는 **되는 척**이다. 판정 기준을 "남은 차이"가 아니라 **"목표 자체가 눈금 미만"** 으로 잡아 발산 보고.
2. **`110093` 재시도 루프.** 가격이 피벗을 이미 지나가면 시뮬은 `low <= stop` 으로 즉시 체결로 보는데 거래소는 이미 돌파된 stop 을 거부한다. 매 tick 재시도해 104분에 10건. 마지막 종료 bar 종가를 참조가로 넘겨 사전 차단.

### ★예정에 없이 관측된 것 — G5+G6 이 함께 작동했다

```

07:45  상한 초과 -> resync -> 거래소 Sell 0.029 vs 시뮬 불일치

결과   거래소 미체결 0건 · 유령 주문 0건
```

조용히 계속했다면 엔진이 없는 포지션을 믿고 청산을 발주해 `reduce_only` 거부가 났을 것이다 — BL-488 이 만들던 바로 그 상황이다.

## ★★내가 틀린 것

1. **설계 지시 자체가 틀렸다.** codex 에게 "delta 를 방출하라" 고 지시했고 E1 이 반박했다. `target_position` 이 옳다.
2. **라이브 세션을 죽였다.** `event_loop.py` 를 두 번의 편집으로 고치는 사이 watchfiles 가 중간 상태를 물어 `NameError` 로 세션이 fail-closed 종료됐다. 정본에 "변이 스크립트만의 문제가 아니다 — 평범한 여러-단계 편집도 같은 함정" 으로 승격.
3. **"정규화가 BL-486 churn 방어" 는 과장이었다.** 실측 반박(0.09375 -> 0.093 vs 0.0625 -> 0.062).
4. **그 정정도 과했다.** "매분 취소·재등재" 라고 고쳐 썼는데 실측은 104분에 **8건**(13분에 한 번꼴). 수량이 `0.029`(스텝 0.001에서 유효숫자 3자리)라 미세 드리프트가 절삭에 흡수되고 33% 스윙은 드문 사건이다. **양방향으로 틀렸다.**
5. **"동일 값 재등재 8건" 오보.** 이전 주문의 상태를 안 보고 분류했다. 재분류하니 **0건**이고 전부 거부·체결 뒤의 정당한 재등재였다.
6. **귀속 테스트 3건이 판별력이 없었다.** 변이를 넣었더니 전부 생존 — 남의 주문 `trade_id` 가 desired 와 같아 매칭돼버려 애초에 취소 대상이 안 됐다. "테스트를 추가했다" 와 "그 테스트가 뭔가를 잡는다" 는 다른 말이다.
7. **`bar_time.isoformat()` 에 콜론이 있다.** key 파싱을 깨뜨려 epoch 초로 교체.
8. **세션 게이트 호출에 `ohlcv` 를 `last_bar_time` 자리에 넘겼다.** mypy 와 테스트가 둘 다 잡았다.
9. **codex 제약을 두 번 잘못 걸었다.** G1 은 pytest 범위를 좁혀 패리티 회귀를 놓치게 했고, G7 은 파일 수를 좁혀 **codex 가 질문하고 멈추게** 했다. "정확히 N개" 는 신규 작업 파일에만 걸고 그 변경이 깨뜨리는 기존 파일은 별도로 열어줘야 한다.
10. **변이 하나가 no-op 이었다.** `order_link_id=None or (...)` 는 Python 에서 `X` 라 "테스트 구멍" 으로 오판할 뻔했다. 변이가 실제로 의미를 바꾸는지 먼저 확인해야 한다.

★그리고 **테스트가 구현의 잘못된 가정을 복제한 사례**를 하나 잡았다 — G6 의 resync 판정이 `open_trades` 를 `dict` 로 검사했는데 `to_report()` 는 **list** 를 준다. `simulated_flat` 이 항상 False 라 조용한 resync 가 절대 안 타고 모든 장기 공백이 세션을 죽였다. **codex 테스트 픽스처도 dict 를 넣어 통과했다.** 변이 검증으로는 못 잡는다(양쪽이 같은 방향으로 틀렸으니까). 잡은 방법은 diff 를 읽다가 타입이 걸려 `to_report()` 를 직접 열어본 것뿐이다.

## 남긴 것 (알려진 한계)

- **첫 바 커버리지 공백** — tick 은 바 종료 56초 뒤에 돈다. 시뮬은 다음 바 전체에서 체결 가능하다고 보지만 주문은 그 바의 93% 가 지난 뒤 올라간다. PbR 처럼 매 바 재발행하는 전략은 최초 1바만 해당.
- **BL-486 창 드리프트 churn** — 104분에 8건. 정규화는 sub-step 만 흡수한다.
- **분 안 가격 변동으로 인한 `110093` 잔여** — 참조가는 마지막 종료 bar 종가라 그 안의 변동은 못 잡는다. fail-closed 이고 원장에 사유가 남는다.
- **시뮬↔거래소 stop 시맨틱** — 이미 돌파된 stop 을 시뮬은 체결로 보고 거래소는 거부한다. 시장가 근사는 라이브 매매 의미를 바꾸므로 별도 BL.
- **`min_qty != qty_step` 인 심볼** — BTCUSDT 는 둘 다 0.001 이라 절삭이 최소수량을 겸하지만 일반 보장은 아니다.
