## ⓷ [BL-605] — 뿌리는 **데이터**였다 (처방 후보 2개 전건 폐기)

백로그는 뿌리를 「적재 경로가 분류 pass 별로 행을 새로 쓰는 것으로 보인다(**뿌리 미확정**)」로
적고 그 위에 처방 후보 둘을 올려 뒀다. **분류 pass 는 하나뿐이다.**

```
list_by_exchange(bybit)  →  계정 행 2개 (같은 exchange_uid 558689281)
                            19a8166a  bybit demo        read_only=f
                            0277c150  bybit demo- aaa   read_only=t
        ↓ 각자 같은 closed-pnl 창을 조회
compute_row_hash(거래소 값 8개만)  →  두 행의 row_hash 가 동일
UNIQUE (exchange_account_id, row_hash)  →  축이 달라 충돌하지 않는다
        ↓
정확히 2배.  배수 = 같은 uid 를 공유하는 계정 행 수
```

**서버 DB 실측이 셈을 닫는다:** `trading.exchange_exits` **574행 = 287 × 2**, 그리고
`having count(distinct exchange_account_id) = 2` 가 **287/287**. 계정별로는 `19a8166a` 의
`ours/exact` 262행이 미조인 **0**, `0277c150` 은 287행 **전량** 미조인이다.

`ours`/`unknown` 쌍이 나오는 이유도 같은 코드다 — 매칭이 계정 스코프
(`order_repository.py:753-765`)라 형제 행은 **구조적으로** `unknown`/`matched_order_id IS NULL`
이 된다. 「과거 회차의 계정별 분리는 부수효과 dedup」이라는 백로그의 관찰이 여기서 설명된다.

**처방(확정) = 스윕 계정 루프에서 같은 `exchange_uid` 는 대표 1행만.** 선례가 이미 3곳 있다
(`tasks/trading.py:507-512` · `:851` · `websocket/position_fanout.py:69-80`).

**폐기한 두 후보와 그 이유:**

| 후보                        | 왜 빗나가나                                                       |
| --------------------------- | ----------------------------------------------------------------- |
| `order_link_id` 단위 upsert | 두 행의 `exchange_account_id` 축이 달라 unique 로 흡수되지 않는다 |
| 소비 계약에 dedup 의무      | 증상을 소비처마다 반복해 막을 뿐 **적재를 안 고친다**             |

둘 다 **「적재 코드가 잘못 쓴다」를 전제**로 삼았다. 전제가 틀렸으므로 표적 자체가 없었다.
→ **LESSON-088**

## ⓸ [BL-639] — 판정식은 이미 있었고, 인용된 판별력은 틀렸다

**판정식을 새로 설계할 필요가 없었다.** `backend/scripts/live_session_admin.py:206-256` 이 이미
구현했고 근거 주석까지 달려 있다:

```
EXCLUSIVE ⟺ ∀ resting conditional order o (reduce_only=None 전량) : o.order_link_id ∈ {Order.id}
```

**실측 (서버, 소크 진행 중 세션 `a4f1cbfb` · `--symbol BTC/USDT`):**

```
bybit demo:      sell other qty=0.058 trigger=64879.9 link=dd58ef44… [ours]
bybit demo- aaa: sell other qty=0.058 trigger=64879.9 link=dd58ef44… [ours]
RESTING_CONDITIONAL=2      FOREIGN_RESTING=0      EXCLUSIVE=YES
```

- **정상 상황 거부 0** — 판정식이 가드로 쓸 수 있다는 것의 실측 근거다.
- ★**같은 실행이 새 결함을 드러냈다** — 실제 조건부 주문은 **1건**인데 `RESTING_CONDITIONAL=2`
  다. 계정 중복이 **거래소 조회 루프**에서도 2배를 만든다. [BL-605] 의 처방(스윕 루프)은 이
  자리를 안 고친다 — 축이 다르다. → **[BL-651]** 신규.

**「판별력 0 · 34행 전량」의 반증:** 계정을 좁히면 287 중 25(8.7%)이고 `ours/exact` 262행은
미조인 0이다. 그래도 결론은 유지된다 — 남은 25 중 12가 `external_manual`(사용자 수동 청산)이라
정상 상황에서도 나고, 오염 창에만 몰린 `unknown` 8건은 **그 창 하나에서 유도한 값이라 적합이지
검증이 아니다**(표본 1). → **LESSON-089**. 인용처 3곳(백로그 본문·인덱스 표·코드 주석)을 함께
고쳤다.

**실패 모드 4종**을 백로그에 적었다 — 미탐 2(시장가 전용 호스트 · 다심볼), 오탐 위험 1(소유권
집합의 계정 축 미결 — [BL-634] 소관), 개수 오염 1([BL-651]).

## ⓹ MTBF — 예측하고, 음성 대조로 확인했다

`mtbf_stratified.py` 는 `operational` **만** 사망에서 뺀다(`:131`). `undecided` 와 `code_defect`
는 **동일 취급**이다. ⇒ 이번 승격 6건은 수치를 안 바꾼다는 것이 **실행 전에 예측 가능**했다.

그래서 재기 전에 예측을 적고 **음성 대조**를 돌렸다 — 승격 **전** 원장(`git show HEAD:…`)과
승격 **후** 원장으로 같은 입력·같은 `--now` 를 물려 표를 diff:

```
★표 동일 — 승격이 MTBF 를 한 자리도 안 바꿨다 (음성 대조 통과)
```

현재 값(2026-08-08T13:16Z, 39세션 117.84h): 전 이력 MTBF **14.73h** [7.48, 34.12] ·
운영 사고 제외 **16.83h** [8.17, 41.87] — **어느 두 층도 CI 가 겹친다**(10쌍 전부).
24h 도달 **0/39** · 최장 **19.42h** · self-check ✓(앞 38행으로 13.39h/8.70h 재현).

⇒ 원장 승격이 사는 것은 수치가 아니라 **귀속의 재현성**이다. ADR-024 가 「그 대조가 이 원장의
다음 작업이다」라고 적은 것을 이행한 것이고, 그 이상을 주장하면 안 된다.
