## 4. [BL-618] — 정본이 셋이 아니라 **넷**이었고, 1200px 은 다른 축이었다

### 선행 과제 규명

`@media (max-width: 1200px)` 는 **5곳**(`globals.css:1836 · 2442 · 2531 · 2991 · 3503`)이고
**다섯 전부 콘텐츠 그리드 열 수 축소**다(`.kpi-row`·`.metric-groups`·`.diag-row`·`.cta-row` /
`.create-grid` / `.strip-3` / `.setup-grid` / `.lp-hero`·`.lp-feat-grid`·`.lp-steps`).
사이드바·토프바·`.page` 폭에 개입하는 블록이 **하나도 없다**.

⇒ `DESIGN.md` §10.2 의 「1200px↓ 사이드바 축소」는 **코드 근거 0건**이었고, 셸 경계는
**1024 / 768 둘뿐**이다. 220/60 과 chevron 토글도 v2 잔재였다(접힘은 순수 CSS, `sidebarOpen`
스토어는 삭제됨).

### ★★★네 번째 정본

`globals.css:204-211` 의 `@theme` 이 Tailwind 스케일을 덮어쓴다 — `sm:` 640 → **375**,
`xl:` 1280 → **1200**, `2xl:` 1536 → **1440**. `frontend/AGENTS.md` 표는 이것을
「Tailwind v4 기본값」이라 적고 있었으므로 **미비가 아니라 틀린 값**이었고, `sm:` 은 실사용
**36건**이라 화면에 실제로 영향을 준다.

### 오라클 신설 — e2e 전체 `sidebar` grep 이 **0건**이었다

어떤 spec 도 `--sidebar-w` · `.sidebar` 폭 · `.page` max-width 를 재지 않았다. 유일한 인접 검사인
`design-canon-tokens.test.ts:79` 는 `:root` 기본값(232px)만 문자열 대조하고 미디어쿼리 사다리는
안 본다. ⇒ `e2e/design-canon-responsive.spec.ts` 를 3층으로 세웠다.

| 층                | 무엇                      | 왜 이것만으로는 부족한가                         |
| ----------------- | ------------------------- | ------------------------------------------------ |
| ① 토큰 사다리     | `:root --sidebar-w` 4점   | 토큰이 맞아도 사슬이 끊길 수 있다                |
| ② 주입 `.sidebar` | `offsetWidth` + `display` | 공개 라우트엔 `.sidebar` 가 없다 → 주입으로 대신 |
| ③ 실물 `.page`    | 렌더된 요소의 max-width   | 주입은 실제 렌더를 증명하지 않는다               |

**실측 결과가 status.md 의 예측표를 확인했다** — 1025→232px · 1024→64px · 769→64px · 768→0px ·
`.page` 1240 · `.lp-page .page` 1120. 그 표는 그때까지 **정적 읽기였고 실화면을 안 밟았다**.

★**스크롤바 보정이 없으면 이 spec 은 못 쓴다.** `max-width` 미디어는 스크롤바를 뺀
`documentElement.clientWidth` 로 매칭하므로 1025 를 요청해도 유효 폭이 1010 이 되어 `≤1024` 가
발화한다. 그 red 는 셸 결함과 구별이 안 된다 — `setCssWidth` 가 gap 을 되보정하고, 못 맞추면
「측정 문제이지 셸 문제가 아니다」를 어서션 메시지에 박는다.

## 7. ★★★개발 환경이 두 번 죽었다 — 범인은 FE 코드가 아니었다

머신이 CPU 100% 로 두 번 다운됐고, Bash 툴이 `echo` 조차 exit 1 로 죽었고, playwright 가
`Test timeout while setting up "page"` 로 4건 실패했고, dev 서버가 `Ready` 뒤 무응답이 됐다.
**넷 다 같은 원인이었다** — dev 로그의 `fork failed: resource temporarily unavailable`.

### 판별 순서

1. **React 렌더 루프 가설 → 기각.** 랜딩 트리(`app/_components/*`)에 `useEffect`·`rAF`·
   `setInterval` **0건**, `layout.tsx` 도 clean. 무엇보다 **클라이언트가 0개인데** CPU 가 탔다 —
   렌더 루프는 클라이언트 없이 성립하지 않는다.
2. **측정 도구 의심.** macOS `ps -o pcpu` 는 **수명 평균**이라 「지금 도는가」를 못 가른다.
   `ps -o time` 을 10초 간격 두 번 떠 벽시계로 나눴다 — **433.6%**(수명평균 435.5%). 진짜였다.
3. **`turbopack.root` 가설 → 반증.** 레포 루트 오추론은 실재했지만(`Can't resolve 'tailwindcss' in
<레포 루트>`), 고정 전후 A/B 가 **415% → 415%** 로 불변이었다.
4. **캐시 A/B → 확정.** `.next/dev` 가 **1.99GB** 였다. 옆으로 옮기고 재기동하니:

| 지표                             | 캐시 1.99GB   | 제거 후   |

| idle CPU (요청 0 · 클라이언트 0) | **416.9%**    | **0.1%**  |

★★두 번째 증상이 더 위험하다 — 변이한 CSS 가 **dev 서버 완전 재기동을 넘어** 낡은 채로 서빙됐고

## 9. 방법론 — 이 회차가 실제로 쓴 규칙

- **줄 번호를 계산하지 마라.** F2c 편집이 `+12` 를 밀어 내가 처음 쓴 `2979 · 3491` 이 틀렸고

- **인덱스 표를 늘리면 표 전체가 커진다.** prettier 가 모든 셀을 최장 셀 폭으로 패딩하므로
  한 행에 긴 요약을 넣자 **41줄이 1,000자 캡을 넘겼다**. 요약은 섹션 본문에, 인덱스는 짧게.
- **병렬을 포기했다.** 계획의 4기 fan-out 은 CPU 사고 직후 폐기하고 전 구간을 직렬로 돌렸다
  (Bash 1건씩 · `--workers=1` · dev 서버 1개 · e2e spec 각각 따로).
- **`.claude/worktrees/` 가 699,102 파일**이다(레포 루트 전체 ~82만). 이번엔 원인이 아니었지만
  루트를 훑는 도구를 붙일 때마다 다시 물릴 자리다.
