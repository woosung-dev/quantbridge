## 1. 계측기가 먼저다

### 1.1 토큰 환산 **계수**는 추정이 아니다 — 트랜스크립트에서 역산했다

한국어는 바이트/문자/토큰 비가 전부 다르다. 그래서 실제 세션 기록에서 계수를 뽑았다 —
단일 `tool_result` 만 들어간 턴에서

```
tokens(tool_result) ≈ Δ(input + cache_creation + cache_read) − 직전 턴 output_tokens
```

직전 3회차 CONTROL 세션(`80dcce10` divergence-label-split · `48be44f4` entry-completeness-rejudgement ·
`8cc0bf0f` silent-surface-honesty)에서 md 표본 **16건 110,395자 → 81,218 tok = 0.736 tok/자**.
코드 0.445 · Bash 출력 0.587. 계수와 그 출처를 `scripts/context-budget.sh` 주석에 박았다 —
**어디서 온 숫자인지 모르는 상수를 남기지 않는다.**

★★**단, 「계수는 실측」과 「파일별 토큰 수는 실측」은 다르다** (codex MINOR). 파일별 값은
`문자수 × 0.736` 이라 **추정**이고, 압축 전후로 링크·표·식별자 비중이 달라지면 그 감소율이
실제 토큰 감소율과 어긋날 수 있다. 그래서 출력 컬럼 이름이 `~tok` 이고, 아래 표의 tok 값은
**전부 추정치**다. 문자 수는 실측이다.

## 6. 정직하게 남긴 것

- **Bash 출력이 컨텍스트의 19~22%** 로 문서 Read(7~9%)의 2.4~3.2배지만 **이번 스코프 밖**이다.
  문서를 0으로 만들어도 절반 이상이 남는다 — **문서 압축의 이론적 상한이 여기서 결정된다.**
- **`MEMORY.md` 압축은 C3 로 검증되지 않는다.** 판별력 시험은 레포 문서만 대상으로 하고
  개인 메모리는 서브에이전트 컨텍스트에 애초에 들어가지 않는다. 그 위험은 **미래의 내 세션**에 있다.
- **C4 는 「상세가 실재하는가」를 증명하지 「좋은 자리에 있는가」를 증명하지 않는다.**
  원문 아카이브로 링크하면 토큰은 언제나 실재한다.
- **변동비는 프로브 기반이다** — 새 세션을 실제로 돌려 잰 것이 아니라, 직전 회차가 실제로 친 명령을
  before/after 에 똑같이 먹여 stdout 을 센 것이다. **C5 를 「판정 불가」로 쓰지 않은 이유가 이것뿐**이고,
  프로브 4종(P1~P4)이 실제 세션의 읽기 분포를 대표한다는 보장은 없다.
- ★**도달 비용은 늘었다** — §5.3. 정보는 6/6 살았지만 같은 답에 파일을 **4.0 → 6.67개** 거친다.
  「−91.4%」만 인용하면 이 대가가 사라진다. **두 숫자를 항상 같이 인용해라.**
- **C3 는 이번 회차를 검증하지 못했다** — 출처가 `INDEX.md` 인 문항이 0개였다(§5.2).
  사후에 C6 를 추가해 메웠지만, **사전등록 단계에서 「이 시험이 무엇을 비추나」를 묻지 않은 것**이 결함이다.
- **`live-observability` 는 여전히 취약하다** — dev-log 파일도 `archive/sprints/` 폴더도 없고,
  판정표 링크를 이번에 이었을 뿐이다. 그 파일이 사라지면 이 회차의 기록은 아카이브 요약뿐이다.
- **`AGENTS.md` 는 줄이려다 늘었다**(+389 tok). 정정이 새 내용이라서다. 사후에 목표를 옮기지 않고
