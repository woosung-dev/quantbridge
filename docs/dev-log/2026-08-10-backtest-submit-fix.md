## 무엇이었나 — 테스트 결함이 아니라 **212 커밋 묵은 프로덕션 결함**

`<form id="backtest-setup-form">` 에 `noValidate` 가 없어 native constraint validation 이 살아 있었고,
비용 필드 두 개의 기본값이 자기 `step` 격자를 어겼다:

| 필드           | 기본값    | `step`     | `stepMismatch` |
| -------------- | --------- | ---------- | -------------- |
| `fees_pct`     | `0.00055` | `"0.0001"` | **true**       |
| `slippage_pct` | `0.00014` | `"0.0001"` | **true**       |

폼이 constraint-invalid 이면 브라우저는 **submit 이벤트를 발화조차 하지 않는다.**
⇒ `handleSubmit`·`onSubmit`·`create.mutate`·`getToken` 이 **전부 안 돈다.** 422 도 에러도 없다.
제출 버튼이 `<form>` **밖**(요약 aside)에 `form={id}` 로 붙어 있어 native 경고 UI 조차 안 떴다 —
사용자에게는 **버튼을 눌러도 아무 일도 안 일어나는** 화면이었다.

**회귀 시점 = `753f4bf6`** (2026-08-07, [BL-603] "narrow default cost assumptions").
`fees 0.001→0.00055` · `slippage 0.0005→0.00014`. 종전 `0.0005` 는 격자에 맞아 통과했다.
**폼 코드는 한 줄도 안 건드린 커밋이 폼을 죽였다.**

**수정 (프로덕션 3줄)**: `<form>` 에 `noValidate` + 두 필드 `step="any"`.

## 반증 목록

### ⑴ 회차 지시의 「1순위 후보 = 토큰 획득」이 거짓이었다

프롬프트가 `mutationFn` 의 `await getToken()` 을 1순위로 지목했다. 추론은 타당했다 —
거기서 멈추면 「요청이 안 나감」과 증상이 맞는다. **그러나 고장은 `handleSubmit` 상류라
토큰은 요청조차 되지 않았다.** 이벤트 부재를 하류로 쫓으면 영원히 안 나온다 → [LESSON-097].

### ⑵ 원장 [BL-698] 의 「권장 접근」 3후보가 전부 무관했다

원장은 실패 지점을 `sprint46-tier3-nth.spec.ts:553-554` 의 **422 응답 문구 assertion** 이라 적고
원인 후보를 ⑴ BE 422 메시지 변경 ⑵ FE 카드 렌더 변경 ⑶ 픽스처 Pine 셋으로 좁혀 뒀다.
**실제 실패는 그보다 앞선 `tier1:124` 의 `page.waitForRequest(POST ...)` 15초 타임아웃**이고
문구는 애초에 **도달하지 않는다.** 좁혀 둔 후보 집합을 그대로 상속했으면 못 찾았다.

### ⑶ 「기존 단위 테스트 17건」이 왜 초록이었나 — 검증을 우회하고 있었다

전부 `fireEvent.submit(form)` = submit 이벤트 **직접 디스패치** = native validation **전면 우회**.
결함이 사는 층을 **건너뛴 지점부터** 시작한다. 시작점을 `click` 으로 한 칸 옮기자 즉시 red →
[LESSON-098].

### ⑷ 내 판정이 반박된 것 — 「레포의 다른 RHF 폼 5개와 동일 관례」

`noValidate` 의 근거로 주석에 이렇게 적었다. `/code-review` Standards 축이 잡았고 **옳았다**:
내가 센 5는 `noValidate` **문자열이 있는 파일 수**였고 2개는 RHF 폼이 아니다. 실제로는
**RHF 폼 9개 중 3개뿐** — `noValidate` 는 **소수파**다. 「동일 관례」라는 근거 제시가 성립하지 않는다.
⇒ 주석을 메커니즘 + RHF 이중화 실측 기반으로 다시 썼다. 나머지 6개는 [BL-699].

### ⑸ 내 수리가 새 flake 를 심을 뻔했다

신설 테스트에 `await vi.waitFor(() => expect(mutate)...)` 를 썼다. Spec 축 평가자가
**1024ms 에서 mutate 0회로 실패하는 것을 1회 관측**했고(이후 20/20 통과),
`mutate` 는 `await act` 안에서 **동기 호출**이라 `waitFor` 는 값 없이 폴링 타임아웃만 추가한다고
지적했다. **상시 red 게이트를 없애려는 회차가 새 flake 를 심는 것은 자기모순**이라 즉시 채택.
직접 단언으로 교체 후 **연속 20/20**, 그리고 ★**변이 시 실패까지의 시간이 ~1030ms → ~17ms**
로 떨어졌다 — `waitFor` 가 순수 타임아웃 표면이었다는 직접 증거다.
