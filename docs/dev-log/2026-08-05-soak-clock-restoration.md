## §1. 작업 1 — 소크와 개발을 분리했다

### 무엇이 교착이었나

`docker-compose.isolated.yml:28-38` 이 `./backend/src` 를 mount 하고 celery 를 `watchfiles` 로
감싼다(4워커 전부). `.py` 한 줄만 고쳐도 워커가 재적재된다(누적 실측 **105회**).

### 고른 안 — 커밋 고정 스냅샷 mount + watchfiles 제거

`docker-compose.soak.yml` 을 **3번째 층**으로 얹어 4워커의 `volumes`/`command` 두 키만
`!override` 로 재대체한다. `-f base -f isolated -f soak` 순으로 포트 재배치(5433/6380)는 살고
mount 만 `./.soak/src` 로 바뀐다. 3층 겹침에서 **마지막이 이긴다**는 것을 `compose config` 로
먼저 실측했다(`watchfiles` 잔존 0건).

`scripts/soak-stack.sh` 가 순서를 지킨다 — `pin`(`git archive <sha> backend/src`, **dirty 면 거부**)
/ `up` / `down` / `commit` / `status` / `assert-not-pinned`.

### 버린 안 (넷)

| 안                                    | 왜 버렸나                                                                                                                                          |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 베이크 이미지로 소크                  | `Dockerfile` 의 `COPY . .` 가 **미커밋 트리까지** 담아 커밋 기록과 내용이 어긋날 수 있다. 재고정 분 단위                                           |

| 워크트리에서 편집                     | 워커가 메인 체크아웃 src 를 mount 하므로 교착이 안 풀린다                                                                                          |

### 음성 대조 — 같은 세션, 두 국면

3건이고 그중 재적재가 원인으로 특정된 건이 없다. 편집이 **결정론적으로** 일으키는 것은 재적재다.
그래서 관측량을 「세션 사망」이 아니라 **「워커 재적재」**로 잡았다(사망을 관측량으로 쓰면
판별력 0 인 하네스가 된다).

| 국면                         | 편집 시각   | 기동 배너                          | celery 프로세스            | 세션            |
| ---------------------------- | ----------- | ---------------------------------- | -------------------------- | --------------- |
| **A · watchfiles (수리 전)** | `15:47:39Z` | 1 → **2** (`15:47:48.96Z`, 9초 뒤) | 70/83/84 → **120/132/133** | `39731d57` 생존 |

**같은 세션**(id·`created_at` `2026-08-04T15:46:58.529Z` 동일)으로 양쪽을 쟀다 — 세션은 DB 행이라
스택 교체를 넘어 산다. 편집은 **바이트 단위로 동일**했다(md5 `8663ee85…` 양쪽 일치).
컨테이너 안 `/app/src/tasks/live_signal.py` 는 국면 B 의 편집을 **보지 못했다**.

★★**내 계측기가 자기 자신을 셌다.** PID 스캔 셸의 cmdline 에 매칭 패턴(`*bin/celery*`)이
문자열로 들어 있어 **자기 매칭**했다. 그래서 매 측정마다 유령 PID 가 하나 끼었고 하마터면
「PID 가 바뀌었다」로 오독할 뻔했다. `$$` 를 건너뛰게 고쳤다.

### 프로세스의 증거 (파일의 증거가 아니라)

`cat /app/src/__soak_commit__` 은 **파일**의 증거다. `soak-stack.sh commit` 은 셋을 함께 낸다 —
⑴ celery MainProcess 의 `/proc/<pid>/root` 를 통해 읽은 값(그 **프로세스가 보는** 파일)
⑵ 그 PID 의 생성 시각(`15:53:49`) > pin 기록 시각(`15:51:14`) ⑶ 기동 배너 시각.
★그리고 **증명하지 않는 것도 적는다** — 그 프로세스가 이 파일들을 실제로 import 했는지는 별도다.

### 창의 시작은 `StartedAt` 이 아니다

컨테이너 `StartedAt` **15:51:22** vs celery ready **15:53:57** — **2.6분** 벌어진다
(그 사이 `uv run` 이 환경을 동기화한다). 그 구간엔 아무것도 평가되지 않으므로 창에 넣으면
「돌고 있었다」를 과대계상한다. ⇒ `up` 이 **배너를 기다리고 배너 시각을 기록**한다.
(재적재 지문이 `watchfiles` 로그가 아니라 celery 배너인 것과 같은 이유다.)

### 정의를 확정하기 **전에** 과거 원장에 적용했다

전 **30세션 · 56.70h** 재생:

| 판정          | 세션      | 비고                                                                                                |

| 비실격        | 26건      | —                                                                                                   |
| **귀속 가능** | **0.46%** | 56.70h 중 **0.261h**                                                                                |

★★★**「역대 최장 15.3h = 9%」는 두 겹으로 낙관이었다.**
⑴ **역대 2위 8.65h(`0e15c3c0`)는 마지막 46.7분 동안 평가가 멈춰 있었다**(종단 tick lag).
나머지 29세션은 전부 1.2~2.9분이다 — **16배 벌어져 겹침이 없다.** 지속시간만 세는 산식은
그 8.65h 를 전부 인정한다.
⑵ 어느 세션도 **어느 커밋이 돌았는지 답할 수 없다**. 그 시절 워커는 움직이는 작업 트리를
mount 하고 있었다.

정의가 과거를 **전부 PASS 로도 전부 FAIL 로도** 만들지 않았고, 앞으로의 창은 100% 귀속·검증되므로
통과는 구조적으로 가능하다.

### 세 낱말을 각각 실제로 냈다 (손조립한 상태 없이)

| 낱말                   | 입력                                                     | 근거                                 | exit  |
| ---------------------- | -------------------------------------------------------- | ------------------------------------ | ----- |
| **FAIL**               | `--since 2026-08-03T09:00:00Z`                           | 그 창에 실격 6건이 **실재**          | **1** |
| **UNKNOWN `진행중`**   | 기본 (T0 = `2026-08-03T15:54:34Z`)                       | 실격 0 인데 누적 0.25h < 168h        | **2** |
| **UNKNOWN `측정불가`** | `QB_DB_CONTAINER=nope` / `QB_METRICS_URL` 죽은 포트      | 실제 장애 유도 — DB·스크레이프 실패  | **2** |
| **PASS**               | 기본 창 + `--require-hours 0.1 --require-continuous 0.1` | **실제 원장**으로 PASS 경로를 태운다 | **0** |

★★**두 번째 `측정불가` 시도가 fail-open 을 잡았다.** 죽은 포트를 가리켰는데 파이프 끝 python 이
`{"undecidable":0,"total":0}` 을 내서 **「어둠 0%」로 읽혔다** — 측정 불가가 정상으로 수렴했다.
`curl` 의 rc 를 파이프 밖에서 보게 고쳤다. ★`total=0` 자체는 정상일 수 있다(counter 미발화) —
그 둘을 구분해야 한다.

### 168h 카운터를 독립 재현했다

창의 네 경계를 각각 원장/파일에서 **직접** 읽어 손으로 더했다:

```
창 = [max(T0, up, session_start), min(coverage_end, now)]
    = [2026-08-04T15:53:57Z, 2026-08-04T16:09:01.798Z]
손 계산 0.2513h  =  스크립트 0.2513h   ✅
```

### 자기 계측이 두 번 더 틀릴 뻔했다

1. **phantom 커버리지를 boolean 으로 두니 매번 UNKNOWN** 이었다 — 워커 로그의 마지막 줄은 늘
   `now` 보다 수십 초 앞선다(celery 가 매초 안 찍는다). 허용 오차를 두면 그만큼이 검증 없이
   credit 된다. ⇒ **boolean 이 아니라 자르기**로 바꿨다. **구조적 방어가 문턱보다 강하다.**
2. **살아 있는 세션의 종단 lag 이 거짓 실격을 만들 뻔했다** — 스택 교체 직후 세션이 5봉
   뒤처졌다가 한 봉씩 따라잡았다. 그 순간을 찍으면 실격이고 실격은 **누적을 0 으로 되돌린다**.
   ⇒ 살아 있는 세션은 **연속 두 표본에서 bar time 이 얼어붙었는가**로만 판정한다.
3. **자기시험 실행이 운영 `last-result` 를 덮었다** — `--status` 가 문턱 0.1h 짜리 PASS 를
   현행 판정으로 보여줬다. `--require-*`/`--since` 가 붙으면 안 쓰게 했다.

## §3. ★★★게이트를 세운 지 38분 만에 소크가 죽었다 — 그리고 게이트가 자기 결함을 드러냈다

세션 `39731d57` 이 `2026-08-04T16:25:01.695Z` 에 **`position_divergence`** 로 죽었다(생존 38.1분).
분류기 판정 = **`phantom`**.

⇒ **[BL-591] 슬라이스 A / [ADR-023] 의 명시된 재개 조건 —「`phantom` 이 1건이라도 재발하면
즉시 착수하고 [ADR-023] 긴급도를 되올린다」— 가 충족됐다.**

### 부검

| 시각(UTC)      | 사건                                                               |
| -------------- | ------------------------------------------------------------------ |
| `16:21:13.99`  | `b964043f` **buy 0.058** 발주 (= 2 × 0.029, Pine 반전 수량)        |
| `16:24:00.145` | `b964043f` **체결** ⇒ 거래소 `-0.029` → **`+0.029`**               |
| `16:24:01.674` | 발산 관측 ① — 엔진 `-0.029722` / 거래소 `+0.029` · 경과 **1.53초** |
| `16:24:11.79`  | `d004ca9f` sell 0.058 발주                                         |
| `16:25:01.694` | 발산 관측 ② — **값이 완전히 동일** · 경과 **61.55초** → **킬**     |

### ★★★같은 발산 하나가 이름을 바꿨다

| 관측 | 엔진        | 거래소  | 최근 체결  | 경과        | 라벨          |
| ---- | ----------- | ------- | ---------- | ----------- | ------------- |
| ①    | `-0.029722` | `0.029` | `16:24:00` | **1.53초**  | `replay_lag`  |
| ②    | `-0.029722` | `0.029` | `16:24:00` | **61.55초** | **`phantom`** |

**엔진값도 거래소값도 최근 체결도 완전히 동일하다. 바뀐 것은 경과 시간뿐이다.**
판별식이 `t_fill >= floor(관측시각, interval)` 이므로 봉 경계를 넘는 순간 라벨이 바뀐다.

⇒ **자가치유하지 않는 발산은 시간이 지나면 반드시 `phantom` 이 된다.** 직전 회차의
「경과 24.7초 vs 909초 = **37배 벌어져 겹침 0**」은 **그 표본의 성질이지 판별식의 성질이 아니다.**
「`direction` 은 두 현상이다」의 근거로 쓰였다면 그 근거는 이번 관측으로 **약해진다** —
같은 현상의 두 **단계**일 수 있다.

★단 「`replay_lag` 7/7 자가치유」는 여전히 참이다(그 7건은 실제로 치유됐다). 게이트도
영향받지 않는다 — 치유된 것은 `replay_lag` 로 남고 실격이 아니다.

### ★게이트의 첫 실제 사건이 게이트 자신의 결함을 드러냈다

죽은 직후 판정이 **`UNKNOWN 진행중`** 이었다. 누적만 조용히 0 이 됐다.
뿌리 — `window_start = 마지막 실격 사건 시각` 인데 violations 를 「그 시각 **초과**」로
필터했다. **그 시각의 사건 자신은 언제나 제외된다** ⇒ **기본 실행이 구조적으로 FAIL 을 낼 수
없었다.** 자기시험(`--since`)에서만 FAIL 이 나왔으므로 **완료 기준 3 을 통과한 채로도
운영에서는 영영 FAIL 을 못 볼 뻔했다.**

수리 — 기본 실행은 **지금 열려 있는 귀속 구간 안**의 사건을 본다. FAIL 은 운영자가
`scripts/soak-stack.sh up` 으로 **새 창을 열 때까지** 남는다(워커는 재기동하지 않는다 —
사망한 것은 라이브 세션이지 워커가 아니다). 회고(`--since`) 실행은 그 창 전체를 본다.
수리 후 실측: **`FAIL 실격` · exit 1**.

★★**교훈** — 「세 낱말을 각각 낼 수 있다」를 **자기시험으로만** 증명하면, 그 경로가
**운영 조건에서 도달 가능한지**는 증명되지 않는다.

### ★★★후속 — 재가동한 세션에서 phantom 이 2건 더 났다 (사망 없이)

게이트 가동 첫 3시간의 관측 4건:

| 관측       | 세션       | 경과       | 라벨          | 사망 |
| ---------- | ---------- | ---------- | ------------- | ---- |
| `16:24:01` | `39731d57` | 1.53초     | `replay_lag`  | —    |
| `16:25:01` | `39731d57` | 61.55초    | **`phantom`** | ★    |
| `17:26:01` | `cc19abd2` | 52.22초    | **`phantom`** | —    |
| `17:29:01` | `cc19abd2` | **6.90초** | **`phantom`** | —    |

**phantom 3건 중 사망은 1건.** 직전 회차의 「phantom 4 · 사망 2/2」에서 온 「phantom = 치명」
연결이 첫 주에 약해졌다. 그리고 분류기가 스스로 **「봉경계식 vs 시간문턱식 불일치 2건」**을

## §5. ★★★codex 적대 리뷰 — 다 짓고 자기시험까지 통과한 게이트에서 거짓 PASS 5개

**P1 6건 + P2 1건.** 그중 **5건이 거짓 PASS 를 만들 수 있었다.** 전건 처분표와 근거는
[ADR-024 §codex 적대 리뷰](../decisions/024-soak-stability-gate.md). 여기엔 방법론만 적는다.

- ★**「세 낱말을 각각 낼 수 있다」를 자기시험으로만 증명하면, 그 경로가 운영 조건에서
  도달 가능한지는 증명되지 않는다.** 기본 실행은 구조적으로 FAIL 을 낼 수 없었는데
  자기시험(`--since`)만 초록이었다. 실제 사망이 나서야 드러났다.
- ★**동시 활성 세션 합산** — 유저당 5개까지 허용되므로 세션 2개면 **84시간 만에 168h** 다.
  내가 「세션 하나」를 암묵 전제로 짰다.
- ★★**수리하다가 결함을 하나 더 만들었다** — TSV 를 stdin 으로 파이프했는데
  `python3 - <<'PY'` 는 **stdin 을 프로그램으로 읽는다**. 세션 목록이 조용히 비었고
  `auto_death` 실격이 통째로 사라졌다. **판정이 관대해지는 방향으로** 틀렸다.
- ★**codex 도 한 건 틀렸다** — `make -i` 우회가 「metrics 증거를 훼손한다」고 했는데,
  **실행해 보니** recipe 재검사가 compose 를 막고 `metrics-wipe` 는 writers 가 살아 있어
  SKIP 이었다(워커 command 불변으로 확인). 남는 건 exit code 거짓말뿐이고 이건 기존
  `assert-main-checkout` 와 같은 잔여다. **§7.3 대로 코드·실행으로 대조한 것이 갈랐다.**
