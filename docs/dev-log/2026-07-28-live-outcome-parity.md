## 한 줄

11스프린트에 걸쳐 "라이브가 백테스트대로 **주문하는가**" 를 고쳤고 직전 회차에 닫혔다. 이번엔 **"버는가" 를 물을 수 있는 자**를 만들었다. 판정이 아니라 자다.

## 무엇을 만들었나

라이브 세션의 **실적**을 엔진(pine_v2)이 그때 **기대한 값**과 나란히 놓고, 격차를 두 층으로 쪼갠다.

```
엔진 기대 gross  +  체결 격차  +  비용  =  거래소 확정 net
```

- **기대치** = `live_signal_events.realized_pnl` (엔진이 그 청산에서 벌었다고 본 값. **비용이 한 번도 적용된 적 없다**)
- **실적** = 확정(`realized_pnl_synced_at IS NOT NULL`) `Order.realized_pnl`
- **체결 gross** = 거래소 청산 원장의 평균가에서 파생 (**수수료를 가정하지 않고 파생한다**)
- 전부 **read-time 파생**. 저장하는 것 없음.

## 핵심 발견

### ★★★게이트가 전부 green 인데 화면을 열자 기능에 도달할 수 없었다

BE 3372 · FE 1198 · 변이 전건 판별 · 오라클 일치. 그 상태에서 브라우저를 열었더니
`GET /live-sessions` 가 **`{"items":[],"total":0}`** 였다. 서비스가 `list_active_by_user` 를 쓰고 프론트도
`is_active` 로 한 번 더 거른다. **세션 7건과 그 위의 매칭 청산 21건이 전부 도달 불가**였다.

회고용 표면인데 **세션이 도는 동안에만** 열 수 있었고, 그때는 비교할 청산이 거의 없다.
**만든 기능에 도달할 수 없으면 만들지 않은 것과 같다.** `include_inactive=true`(기본값 불변)로 열었다.

### ★★★`Order.realized_pnl` 은 확정값이 아니다 — 필터를 빼면 화면이 동어반복이 된다

`tasks/live_signal.py` 가 주문 생성 시점에 `realized_pnl=event.realized_pnl` 즉 **엔진 추정값**을 그 컬럼에 쓴다.
확정은 나중에 백필이 `realized_pnl_synced_at` 을 세울 때 일어난다.

즉 미동기 상태의 `Order.realized_pnl` 은 이 기능의 `expected_gross` 와 **문자 그대로 같은 숫자**다.
필터 없이 렌더했다면 **격차가 영원히 0 인 완벽한 동어반복 화면**이 됐을 것이다. 스프린트 전체가 무의미해질 뻔했다.

### ★★★분해가 하나도 안 됐는데 커버리지 100%

```
매칭 21 | 분해가능 0 | undecomposed 21  ->  coverage_pct = 100
```

`covered_count = matched + expected_only + actual_only` 가 undecomposed 를 분모에서 빼지 않는다.
청산 원장은 `now - 7일` 부터만 적재되므로(`_EXIT_WINDOW_MS`) **7일 지난 세션은 전부 이 상태가 된다.**
가설이 아니라 예정된 사건이었다. 커버리지를 **매칭/분해 2종**으로 쪼갰다.

### ★★표본 게이트가 표본이 가장 작을 때 오히려 열렸다

사후 선택된 임계 20 을 버리고 "필요 N 을 표본 자신에서 유도" 로 바꿨는데, 실데이터에서 **반대 방향으로 뚫렸다**:

```
n=3  sd=0.1593  mean=-0.9210  ->  required_n = ceil(0.1197) = 1  ->  sufficient = True
```

세 청산이 우연히 비슷하면 sd 가 작아져 필요 표본이 1 로 떨어진다. 공식은 **평균의 정밀도**를 재는데
n 이 작으면 **sd 추정 자체가 못 믿을 값**이고, 같은 1시간 안의 세 청산은 iid 도 아니다.
하한을 데이터가 아니라 **추정량의 요구조건**(CLT)에서 가져왔다 — `MIN_OBSERVATIONS_FOR_VARIANCE = 30`.

### ★★편도 요율을 왕복 가정과 비교하고 있었다

`effective_cost_pct = cost / round_trip_notional` 인데 분모가 두 leg 합이라 이 값은 **편도**다.
그런데 화면은 이것(0.06%)을 `implied_round_trip_pct`(0.30%, **왕복**)와 나란히 놓았다. **2배 어긋난 비교**이고,
그 비교가 정확히 이 스프린트가 존재하는 이유였다. 편도/왕복을 분리해 왕복끼리 비교하게 고쳤다.

### ★★빈 상태가 최악을 "아무 일 없음" 으로 보여줬다

`matched_count === 0` 이면 버킷을 통째로 렌더하지 않았다. `expected_only = 51` 인 상태 —
**"엔진은 51번 청산했다고 믿는데 거래소 확정이 0건"** 이 화면에는 **"아직 대조할 청산이 없습니다"** 로 떴다.
이 저장소가 -2179% 실행에 샤프 +0.029 를 띄웠던 것과 같은 계열이다.

### ★★같은 함정이 층을 바꿔 세 번 나타났다 — 픽스처 원칙

적대 검토가 설계 단계에서 "항등식이 잔차 정의라 아무것도 못 잡는다" 를 지적했고 설계를 고쳤다.
그런데 **똑같은 함정이 테스트 안에서 다시 나타났다** — 테스트가 항등식만 단언하는데 `execution_gap` 이
그 피연산자에서 파생되니 어떤 값이든 통과했다. 변이 M19 가 12개 테스트를 전부 통과했다.

같은 유형이 세 번:

| 단계 | 픽스처에 없던 것       | 결과                          |
| ---- | ---------------------- | ----------------------------- |
| W1   | 파생값 직접 단언       | 항등식이 항상 성립            |
| W2   | `entry` 이벤트         | close 필터가 no-op            |
| W3   | 미동기 주문            | 확정 필터가 no-op             |
| W9   | 세션 창 **밖** 원장 행 | 시간창이 양쪽 경계 모두 no-op |

★**네 번째는 이 원칙을 이미 문서에 적은 뒤에 났다.** 규칙을 아는 것과 픽스처를 그렇게 만드는 것은 다른 일이다.
변이를 돌리지 않았다면 네 번 다 "테스트가 있으니 검증됐다" 로 넘어갔을 것이다.

★**일반 원칙 — 어떤 규칙이 무언가를 배제한다면, 배제되는 그것이 픽스처에 있어야만 그 규칙이 증명된다.**
생성자가 쓰는 픽스처는 자연히 happy path 만 담으므로, **무언가를 제외하는 규칙은 구조적으로 검증되지 않는다.**

### ★계측기가 세 번 틀렸다 — 대상보다 계측기를 먼저 의심하라

1. **테스트 동어반복** (위)
2. **평가자 스펙 결함** — 합계는 전 관측, 격차·비용은 분해 가능분만으로 정의해 **화면 워터폴이 5만큼 안 닫혔다**
3. **오라클 스코프 누락** — `actual_only` 를 6 으로 적었는데 구현은 2 를 냈다. 확인하니 **내 SQL 이 `SessionScope` 를 적용하지 않았다**(확정 27건 중 세션 창 안은 23건)

세 번 다 "시스템이 고장났다" 로 갈 뻔했다.

### ★★G6 최종 리뷰가 9세션 연속 P1 — **내가 "처분했다" 고 적은 것이 처분되지 않았다**

`actual_only` 는 **로컬 확정 `Order`** 에서만 만들어진다. 그런데 거래소 네이티브 TP/SL 은 entry 주문에
파라미터로 붙어 거래소가 실행하므로 **대응 로컬 주문이 없을 수 있다.** 그런 청산은 원장에는 있는데
표면의 **어떤 금액에도 안 잡히고**, 커버리지 분모에도 안 들어가 **커버리지가 실제보다 좋아 보인다.**

★이건 앞선 codex 라운드가 D5 로 지적했고 내가 "`actual_only` 가 net 금액도 갖게 한다" 로
**처분했다고 문서에 적은** 항목이다. 그런데 `actual_only = A \\ M` 이고 `A` 는 확정 **주문** 집합이라
주문이 없는 청산은 애초에 A 에 없었다. **처분 문장은 처분의 증거가 아니다.**

수리 — `ledger_only` 버킷 신설(합계에 병합하지 않고 별도 노출) + **커버리지 분모에 포함**.
★단 이 1차 수리는 dedup 키와 스코프가 둘 다 틀렸고 **재리뷰가 그것을 잡았다**(아래).

같은 리뷰가 함께 잡은 것 — 기존 상세 테스트의 `vi.mock` 팩토리에 새 API export 가 없어 **그 테스트가
패널의 에러 경로를 지나며 통과**하고 있었다(정상 경로를 한 번도 통과한 적 없다). 그리고 수용 기준이
약속한 성과 비율(엣지율·비용/엣지 배수)이 **출하되지 않았고**, FE 픽스처가 전부 `sample_sufficient=false` 라
게이트가 열린 뒤의 누락을 아무도 못 잡는 상태였다.

### ★★그 수리가 새 P1 을 세 개 만들었다 — 재리뷰가 두 번째 HOLD

가장 뼈아픈 것은 **레포가 이미 배우고 문서화한 버그를 되살린 것**이다.
ledger-only dedup 을 `max(closed_pnl)` 로 썼는데, `providers.py` 의
`aggregate_closed_pnl_by_order` docstring 이 **정확히 그 실패 모드**를 이미 설명하고 있었다:

> "Bybit 는 한 청산 주문을 여러 closedPnl 행으로 쪼개 낼 수 있다. **마지막 행만 취하면 부분 손익이
> 저장되고** ... 그 부분값이 **영구 고정**된다."

건수는 1 로 맞아 커버리지는 정상처럼 보이고 **net 만 조용히 틀린다.** 올바른 규칙은
`(account, exchange_order_id)` 별 **SUM** 이고, 그건 이 레포에 **이미 있던 답**이다.

나머지 둘 — `order_link_id` 가 **entry** 로 해석되면 브래킷 청산이 다시 제외돼 **같은 결함이 다른 문으로 돌아왔고**,
`ledger_only` 에 시간창·전략 경계가 없어 **다른 전략·과거 청산이 이 세션의 net 과 커버리지 분모를 바꿨다**.

★**수정은 새 표면을 만든다. 리뷰를 한 번 더 돌려야 보인다.**

★★**그리고 내가 "수정이 작동했다" 는 증거로 보고한 숫자가 사실은 다음 결함이었다.** P1 수리 직후 화면에서
**"원장에만 있는 청산 3건, net -0.04367079"** 를 확인하고 성공 근거로 적었다. 시간창을 넣고 다시 재니 **0건**이었다.
SQL 로 확인하니 그 세 행은 전부 **2026-07-24** 이고 가장 이른 세션은 **07-26** 시작이다 —
**세션이 존재하기도 전의 청산이 모든 스코프에 계상되고 있었다.** 숫자가 나온 것과 그 숫자가 맞는 것은 다른 일이다.

### ★3차 재리뷰 수리 — 귀속 신뢰도와 성과 표본을 분리했다

`attributed_strategy_id`는 `attribution_confidence=exact`일 때만 ledger-only 스코프에 쓴다.
`inferred`는 같은 계정·심볼에 다른 전략이 공존하면 틀릴 수 있는 검정력 없는 추정이므로, net과
커버리지 분모에는 넣지 않고 별도 진단 건수로만 노출한다. 직접 주문 연결로 스코프에 들어온 경우도
최종 집계 전에 제외한다.

성과 비율은 gross와 왕복 notional이 모두 있는 주문의 net 표본으로 별도 `ratio_sample` 판정을 한다.
따라서 모든 매칭 주문의 순손익 기술통계 표본이 충분하더라도, 분해 가능한 주문이 적으면 엣지율과
비용/엣지 배수는 화면에서 차단된다. 계정 진단의 범위도 "이 심볼 · 계정 기준, 기간 무관"으로
정정하고 다른 심볼의 미귀속 청산이 제외됨을 명시했다.

수리분 정적 검증은 `ruff check .`, `mypy src/`(212 파일), `pnpm typecheck`, `pnpm test`
(203 파일 1,213건), `pnpm lint`를 통과했다. 백엔드 pytest는 평가자 게이트로 남겼다.

### ★★수용 기준을 적어놓고 이행 안 된 것이 **두 번** — 3차 HOLD

3차 리뷰가 잡은 P1: ledger scope 가 `attributed_strategy_id` 를 **`attribution_confidence` 확인 없이** 썼다.
그 컬럼은 `attribute_exit` 이 `inferred` 를 낼 때만 채워지고, 그 함수는 주석으로 명시적으로 봉인한다 —
"검정력이 없다. **리스크 게이트 입력으로 절대 쓰지 않는다.**" 결과적으로 **다른 전략 청산이 무라벨로
이 전략의 net 과 커버리지 분모에 들어갔다.**

★내 G1 §4.3 은 이미 **"`inferred` 는 별도 라벨로 격리한다"** 고 적고 있었다. 적어놓고 이행되지 않았다.
같은 일이 이번 스프린트에서 **두 번**이다(브래킷 청산 편입 · `inferred` 격리). **수용 기준 문서는 자기 집행되지 않는다** —
G3 코드 대조에서 수용 기준을 한 줄씩 짚어 확인하는 것을 규칙으로 승격했다.

### ★탈출이 약한 테스트를 뜻하지 않은 사례 — 이중 가드

`inferred` 가드를 변이했더니 green 이었다. 다섯 번째 탈출이라 픽스처를 의심했는데, **틀렸다.**
가드가 **두 겹**이었다(스코프 술어 + `attribution_confidence IS DISTINCT FROM inferred`). 실측:

| 변이           | 결과    |
| -------------- | ------- |
| 가드1만 제거   | green   |
| 가드2만 제거   | green   |
| **둘 다 제거** | **red** |

즉 테스트는 **동작에 대한 진짜 게이트**이고 코드는 머니-패스 불변식을 이중으로 막고 있었다.
§7.2 실패유형 2("두 가드가 같은 대역을 공유")가 그대로 재현됐다.
**"탈출 = 약한 테스트" 로 바로 갔으면 오진이었다.**

### ★반증된 의심도 있다

`ExchangeExit.side` 매핑이 틀렸다는 의심은 **틀렸다.** 적대 검증이 ccxt 실제 응답으로 산술 검증해
`Buy` = 숏 청산이 **옳다**고 확인했다. 고치지 않았다. 다만 `else` 가 catch-all 이라 OKX 소문자
`"buy"` 가 전부 롱이 되는 것은 별건으로 막았다.

## 신규 BL 후보

- **`trade_id` 재사용 + catch-up 다중 emit** — `pnl_by_trade` 가 재사용되는 Pine 진입 이름으로 키를 잡는다. 그 코드 주석의 정당화("마지막 bar 만 발행")는 catch-up 이 정상 경로가 되면서 **이미 거짓**이다. 오염은 실데이터에서 재현되지 않았다(잠재).
- **세션 창 밖 확정 청산 4건(net -0.5463)이 어느 표면에도 안 잡힌다** — 반열림 창이 세션 종료 후 늦은 체결을 어디에도 넣지 않는다. 크기를 처음 계량했다.
- **거울 계정 중복** — 같은 Bybit uid 를 두 계정 행이 스윕해 같은 청산이 2행 적재된다. 세션 단위에선 무해하고 전략 누적에서만 부풀려진다.
- **`expected_only` 51건(청산 유실)** — 이 스프린트는 **크기를 보이게** 했을 뿐 고치지 않았다.
- **READ COMMITTED 경합** — 한 요청 안 두 쿼리 사이에 dispatch 가 커밋되면 같은 청산이 두 버킷에 세어질 수 있다(활성 세션 한정).

## 파이프라인 4회차 기록

**작동했다.** 검증 4겹이 각각 다른 것을 잡았다:

| 검증             | 잡은 것                                                     |
| ---------------- | ----------------------------------------------------------- |
| G1 codex 플랜 2R | 설계 2안을 REJECT. `Order.realized_pnl` 동어반복(코드 전에) |
| 표적 변이        | 테스트가 게이트가 아닌 곳 3건                               |
| G3 적대 3렌즈    | 커버리지 100% 거짓말 · 표시 계약 P1 5건 · 시간축 P1 4건     |
| **G4 화면**      | **기능 도달 불가** · 편도/왕복 2배 오비교                   |

★**렌즈를 다르게 준 것이 결정적이었다.** 같은 렌즈 3기였다면 중복이었을 것이다 — 시간축 렌즈는 표시 계약을 못 봤고, 표시 계약 렌즈는 거래소 실상을 못 봤다.

★**그리고 화면 검증이 나머지 셋이 전부 놓친 것을 잡았다.** 게이트·변이·오라클·적대 리뷰가 모두 통과한 뒤에도, 사용자가 그 기능에 **도달할 수 없다**는 사실은 브라우저를 열기 전까지 아무도 몰랐다.
