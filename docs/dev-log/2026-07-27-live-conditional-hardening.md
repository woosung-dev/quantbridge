## ★핵심 발견

### 1. preflight 가 스코프를 줄였다 — BL-498 은 백엔드 청산 경로를 새로 만들 필요가 없었다

`ClosePositionService.close_position` 은 세션 `is_active` 를 **요구하지 않는다.** 즉 **비활성 세션 id 로도 청산이 된다.** 막혀 있던 것은 코크핏 §03 이 **활성 세션만 순회**하는 것뿐이었다.

→ 신규 청산 경로 0. **계정 스코프 읽기 엔드포인트 1개 + 화면**으로 닫혔다. 청산은 기존 `POST /live-sessions/{id}/positions/close` 를 그대로 재사용한다.

또 ccxt `bybit.fetch_positions()` 는 심볼 인자 없이 `settleCoin=USDT`·`category=linear` 로 계정 전체를 **1콜**에 준다(설치본 소스 확인). 계정당 REST 1회면 된다.

### 2. ★★preflight 결론 자체가 틀렸다 (codex G0.5 가 반박)

나는 "취소된 조건부 진입 16건이 **전부** `exchange_order_id` 를 보유하므로 DB-only 취소 경로는 프로덕션에서 한 번도 안 탔다" 고 결론냈다. **성립하지 않는다.**

경합에 **패배한** 호출은 `rowcount=0` 이라 행에 아무것도 쓰지 않는다. 그 뒤 dispatch 가 `exchange_order_id` 를 붙이고(`tasks/trading.py:518-526`) 다음 tick 이 거래소 취소로 마무리하면 **최종 행은 정확히 그 16건과 같은 모습**이 된다. 즉 그 관측은 패배 경합과 **양립한다.**

내가 증명한 것은 **"DB-only 취소 _성공_ 0건"** 뿐이다. 호출·패배 횟수는 별도 metric 없이는 알 수 없고, 이번에 넣은 `stage="cancel_raced"` 가 정확히 그것을 센다. 성공 경로와 시도 횟수를 혼동한 추론이었다.

★다만 preflight 의 **다른** 관측 하나는 살아남는다 — 48h 워커 로그의 `cancel_failed` **0** · `concurrent_transition_submitted` **0**. 오늘 코드에서 경합 패배는 `RuntimeError` 를 남기므로 이 0 은 **"관측된 패배 0"** 의 증거로 유효하다. 원장(최종 행)이 침묵하는 것과 로그가 침묵하는 것은 증명력이 다르다.

### 3. ★★dogfood 가 결함을 하나 더 찾았다 — 같은 거래소 계정을 가리키는 API 키가 둘

계정 스코프 표에 **같은 포지션이 두 행**으로 나왔다. raw HMAC `/v5/user/query-api` 로 확인하니 등록된 두 계정이 **같은 Bybit uid `558689281`** 이었다(BL-477 과 같은 사실). 게다가 그중 하나는 **`readOnly=1`** 이라 그 행의 청산 버튼은 누르면 권한 오류로 실패한다.

이번엔 무음 중복을 **고지**로 바꾸는 데까지만 했다(계정 2개 이상이면 각주). 근본 해결(uid 캐시로 접기 + readOnly 청산 불가)은 **BL-501** 로 등재했다 — 마이그레이션이 필요해 이번 스코프 밖이다.

### 4. ★★★e2e 게이트가 **거짓 red** 를 냈다 — dev 서버의 Turbopack CSS 캐시가 stale

`e2e:authed` 가 `/orders` 캐논 하드 실패 1건을 냈다(`scrollWidth 490 > innerWidth 375`, `.pager-nums` 계산값 `flex-wrap: nowrap`). 직전 스프린트가 BL-495 로 고친 바로 그 증상이다.

## 무엇을 했나

### BL-498 ✅ Resolved — 활성 세션이 없어도 보이고 닫힌다

- `providers.fetch_all_open_positions(creds)` 신설. 심볼 없는 `fetch_positions()` 1콜. 응답의 `BTC/USDT:USDT` 를 우리 canonical 로 되돌리는 `_from_bybit_linear_symbol`(inverse 는 뭉개지 않고 원문 유지). 기존 `fetch_open_positions` 의 파싱 블록을 `_position_snapshot_from_ccxt` 로 추출해 **양쪽이 공유**한다.
- `list_by_account(account_id, *, user_id)` — **활성 여부 무관**. `user_id` 도 건다(두 FK 의 소유자 일치를 보장하는 DB 제약이 없다).
- `PositionService.get_account_positions` — IDOR 선차단 → 지원 판정 → 1콜 → 귀속 세션 매칭. 캐시는 `qb_acct_pos_snapshot:` 로 **세션 캐시와 네임스페이스 분리**(같은 키를 쓰면 계정 조회가 세션 대조의 근거를 덮어쓴다).
- ★**청산 가능 판정을 서버에서** 한다. 귀속 세션 없음 → `no_owning_session`, leg 2개 이상이거나 `position_idx ∉ {0, None}` → `hedge_unsupported`. `close_service` 가 409 로 거부할 행에 버튼을 주지 않는다.
  - ★`no_owning_session` 은 표시 정책이 아니라 **원장 제약**이다. `Order.strategy_id` 가 **NOT NULL FK**(`models.py:163-169`, `ondelete=RESTRICT`)라 귀속 전략이 없으면 청산 주문을 원장에 기록할 수조차 없다. 그래서 사용자 결정은 "행은 보여주되 버튼 대신 사유를 표기" 였다 — **보이지 않던 노출이 최소한 보이게는 된다.**
- 화면 = `account-positions-table.tsx` 를 §03 의 세션별 대조 **위**에. 청산은 기존 `useClosePosition` 재사용. 쿼리 키를 `positionsPrefix` **아래** 두어 청산 성공 시 두 표가 함께 무효화된다.
- 조회 범위(USDT 정산 linear 전용)를 응답 필드 `settle_coin` 과 화면 각주로 고지한다.

### BL-499 🟡 부분 완화 — Resolved 가 아니다

근본 경합은 사용자 결정(마이그레이션 0)으로 남는다. 한 것은 **패배와 진짜 실패의 구분**이다.

- `rowcount=0` → `get_state_and_exchange_id_fresh`(식별맵 우회 컬럼 select)로 재조회 → 비-`pending` 이면 `RuntimeError` 대신 metric + 로그.
- ★**경합과 제출 중단을 라벨로 가른다.** `submitted` 인데 `exchange_order_id` 가 없으면 그건 경합이 아니라 dispatch 가 상태만 커밋하고 죽은 **영구 고착**이고, 그 행은 매 tick 이 분기를 타 세션 등재를 영구 정지시킨다. `stage="cancel_stalled"` + `logger.error`. 안 가르면 영구 장애가 1회성 경합 카운터로 강등된다(적대 검증).
- ★**패배해도 그 tick 의 `to_place` 는 건너뛴다.** 처음 플랜은 "무해한 등재를 살리자" 였는데 codex 가 반박했다 — `current_position` 은 취소 루프보다 **먼저** 찍은 스냅샷이라, 패배한 주문이 그 사이 체결되면 낡은 포지션 위에서 사이징한 주문이 나간다. fail-closed 를 유지한다.
- 거래소 취소 성공 후의 `transition_to_cancelled` rowcount 0 은 **기존대로 실패**다. 의미가 다르다.

### BL-500 ✅ Resolved — 거래소 부재가 로컬 행을 이긴다

- 거래소 open-order 응답에 없는 로컬 행에 대해 **`fetch_order(exchange_order_id)` 로 직접 물어** terminal(`filled`/`cancelled`/`rejected`)임을 확인한 뒤에만 `actual` 에서 제거한다. 확인 못 하면 그대로 둔다(fail-closed).
- ★**중간에 나이 게이트(3분)를 넣었다가 폐기했다.** 적대 검증이 그게 **잘못된 시계**임을 증명했다 — reconcile 은 60초마다가 아니라 **bar 마다** 돌고(`no_new_bar` 조기 return), `submitted_at` 은 **주문의 나이**이지 **부재의 나이**가 아니다. 조건부 진입은 정의상 몇 시간 resting 하다 트리거되므로, 막겠다던 창의 주문은 거의 전부 이미 늙어 있어 게이트가 늘 열려 있었다. 1h 세션에서는 보호값이 정확히 0이다.
- ★**체결이 확인되면 그 tick 은 등재하지 않는다.** 포지션 스냅샷이 그 확인보다 앞서 찍혔을 수 있다.
- ★**상태 전이는 하지 않는다** — watchdog·`Reconciler` 책임이다. 단 그 한계 서술도 틀렸다(아래 §내가 틀린 것).

### ★★dogfood — 3중 대조 종단 증명

활성 세션 **0건** 상태에서, 우리 앱을 거치지 않고 raw HMAC 으로 거래소에 포지션을 만들었다.

```
진입(앱 밖)  d74c5206  Buy  0.002 @65331.1  reduceOnly=False  orderLinkId 없음
   ↓ 코크핏 §03 렌더된 화면에 "계정 잔여 포지션" 표로 표시 (활성 세션 0건인데도)

청산        bedc278b  Sell 0.002 @65315.1  reduceOnly=True   orderLinkId=a8765854…

우리 원장  a8765854 (Order.id)  = 거래소 orderLinkId          ✅
          exchange_order_id bedc278b = 거래소 orderId        ✅
          filled_price 65315.1       = 거래소 avg            ✅

```

★"화면에서 확인" 은 렌더된 페이지에서 했다. DB 행·API 응답이 아니다.

### ★2차 dogfood — 1차가 못 밟은 15초 캐시 창

적대 검증이 잡은 캐시 무효화 결함은 **1차 dogfood 를 통과했다.** 청산 후 raw HMAC·DB 확인을 거치느라 30초 넘게 지나 TTL 이 이미 만료됐기 때문이다. 수정 후 기전 수준에서 다시 쟀다.

```
페이지 로드 → Redis db3 에 두 계정 키 생성 (qb_acct_pos_snapshot:19a8166a…, :0277c150…)
화면 청산(19a8166a) → 체결
  t=1s  19a8166a 키 없음 ✅ (DEL 이 돌았다)
  t=1~6s 0277c150 키 잔존 → TTL 만료로 소멸
거래소 legs=0 (독립 raw HMAC)
```

★**그 잔존 키가 BL-501 의 세 번째 귀결이다** — 무효화는 `exchange_account_id` 단위인데 두 자격증명이 **같은 거래소 계정**을 가리키므로, 다른 쪽 키는 안 지워지고 최대 15초 동안 이미 닫힌 포지션을 계속 보여준다. 백로그에 추가했다.

★**"dogfood 통과" 를 커버리지로 읽으면 안 된다.** 1차는 이 창을 밟지 않았을 뿐이지 안전을 증명하지 않았다.
