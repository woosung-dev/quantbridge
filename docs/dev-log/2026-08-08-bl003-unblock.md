## 4. 갈래 B — 게이트가 「측정 못 했다」를 숨기던 경로

### 4.1 기전

`scripts/soak-gate.sh` 가 워커 로그 경계를
`docker logs --timestamps ... 2>&1 | head -1 | cut -d' ' -f1` 로 뽑는다. 컨테이너가 없으면 `2>&1` 이
에러 메시지의 첫 토큰(`Error` · `Cannot`)을 **타임스탬프 자리**에 넣고, 유일한 가드는 「비어 있지
않다」뿐이었다. 그 아카이브가 판정기를
`ValueError: Invalid isoformat string: 'Error'` 로 죽였고 — **크래시의 exit 1 은 FAIL 과 구분되지
않는다.** 운영자는 「실격이 났다」로 읽지만 실제로는 **아무것도 측정되지 않았다.**

★★**이것은 과거의 흔적이 아니라 진행 중인 과정이었다.** 맥 launchd `dev.quantbridge.soak-gate` 가
`StartInterval 1800` 으로 **30분마다** 돌면서 스택 부재 구간마다 오염본을 하나씩 찍었다 —
실측 09:44~13:30 **오염 8벌** / 14:00~17:01 **정상 9벌**(워커 생존 구간) / 17:31 **다시 오염 1벌**.
서버는 아직 **0벌**이지만 `soak-watch.timer` 가 같은 주기로 돌고 `soak-restart.sh` 의 `down` 창이
정확히 같은 조건을 만든다. ⇒ **[BL-635] 는 복구가 아니라 예방이다.**

### 4.2 수리 전후 대조 — 4행

| 판정식                              | 수리 전                                                 | 수리 후                                                                 | 판별자                                |
| ----------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------- |
| **G-B7** 오염 없는 페이로드 1벌     | `FAIL 실격` (C1 0.0 / C2 0.0 / C3 2건)                  | **동일 — byte-identical**                                               | `diff` exit 0                         |
| **G-B8** `unattributed_hours`       | **0.0**                                                 | **0.0** (비감소)                                                        | 판정 JSON `detail.unattributed_hours` |

수리 지점 — `scripts/soak-gate.sh` 가 `docker logs` **반환 코드**와 **ISO 8601 형식**을 둘 다 검사해
실패 시 커버리지를 비우고 `log_note` 를 싣는다. `backend/scripts/soak_gate_predicate.py` 에
`parse_log_coverage` · `summarize_unreadable_log_coverage` 를 추가해 **판독 불가 구간의 시간을 절대
credit 하지 않고** `UNKNOWN 측정불가` 로 낸다. 판정기 테스트 **37 → 41 passed**.

★★**UNKNOWN 은 C3 실격 뒤에 둔다 — 래칫이다.** 오염된 아카이브 한 건이 진짜 실격을 UNKNOWN 으로
덮으면 「죽었는데 안 죽은 걸로 보인다」가 된다. 실격은 무엇에도 덮이지 않는다.

### 4.3 ★이 회차의 재확인에서 한 가지가 더 나왔다 — 동결 페이로드의 이름이 오해를 부른다

동결된 `gate-baseline/payload-*-nodisq.json` 두 벌은 이름과 달리 **실격이 없지 않다.** 세션에
`last_evaluated_bar_time` 이 없고 `samples` 가 비어 있어 `tick_stall`(「평가 기록 없음」)이 발화하고,
C3 가 UNKNOWN 보다 **먼저** 이기므로 판정은 `FAIL 실격` 이 된다 — 즉 그 페이로드로는 UNKNOWN 갈래에
도달할 수 없다. **G-B9 의 1차 측정이 「수리가 안 됐다」로 읽힌 원인이 정확히 이것**이고, 측정 도구가
틀렸던 것이지 수리가 안 된 것이 아니었다.

실격이 실제로 없는 페이로드를 새로 만들어(세션에 `last_evaluated_bar_time` 을 붙여) 재측정했다 —

```
오염 없음 → verdict UNKNOWN · reason_word "진행중"   · exit 2
오염 있음 → verdict UNKNOWN · reason_word "측정불가" · exit 2 · unreadable_log_coverage.count = 1
```

★**exit code 만으로는 두 UNKNOWN 이 구분되지 않는다**(둘 다 2). 판별자는 `reason_word` 와
`unreadable_log_coverage` 다. 수리가 산 것은 「exit 2 를 얻은 것」이 아니라
**「exit 1(크래시 = FAIL 과 동일) 을 잃은 것」**이다. 이 구분을 표에 못 박아 둔다.

### 4.4 같은 커밋이 함께 닫은 것

- `soak-stack.sh` `_status()` 가 「`origin/main` 의 조상인가: YES」만 답하던 것을 **빠진 커밋 목록**을
  내도록 바꿨고, `_pin()` 은 빠진 커밋이 있으면 거부한다(`QB_SOAK_OVERRIDE=1` 탈출은 기존 관례 재사용).
  ★후속 커밋에서 **측정 전에 `fetch`** 를 넣었다 — 낡은 remote ref 가 조용히 「0 missing」으로 통과했고,
  그것이 애초에 pin 이 [BL-622] 수리를 놓친 것과 **같은 모양**이다.
- `soak-restart.sh` 가 `down` 이 컨테이너를 지우기 **전에** 워커 로그와 원장 4테이블을 덤프한다
  (fail-closed · `COPY ... TO STDOUT` 이라 CSV 가 호스트에 떨어진다).
- `soak-logs-follow.sh` — [BL-619] 가 서버에서 돈다고 가정했던 `nohup` 추종기는 **실재하지 않았다**.
  lingering 을 갖춘 systemd user unit 으로 승격하고, 같은 파일을 쓰는 레거시 추종기 위에 설치하는 것을 거부한다.
- systemd unit 에 `SuccessExitStatus=1 2` — UNKNOWN=2 가 매 실행 `failed` 로 남아 status 를 건강 신호로
  못 쓰던 것을 고쳤다.
- `live_session_admin.py` `status` 가 `FLAT` 옆에 `RESTING_CONDITIONAL` · `FOREIGN_RESTING` ·
  `EXCLUSIVE` · `QUIET` 를 함께 낸다. 판별자는 `order_link_id` **소유권**이다 — 우리 것까지 「남의 것」으로
  세면 정상 재기동이 영원히 거부되고, 그 오탐이 이 가드의 가장 큰 위험이다.
- `soak-restart.sh` 가 `EXCLUSIVE != YES` 면 멈춘다. ★그리고 **`EXCLUSIVE=` 줄이 아예 없으면
  `YES` 로 읽지 않고 exit 2 로 「못 쟀다」를 낸다** — 낡은 CLI 를 쓰는 체크아웃에서 fail-open 이 열리는
  자리였다(G-C1 세 번째 케이스).

   **계정 결합**을 한 번도 묻지 않았다. ★「무관하다」의 근거 목록에 **묻지 않은 축**이 있는지부터 봐라.

3. **「서버 `.soak` 아카이브가 이미 오염됐다」.** 서버는 **0벌**, 오염은 로컬만 8벌(+1).

   실격은 C1·C2 를 **함께** 0 으로 되돌린다.
5. **`status.md` 의 「`.soak/logs` 가 있다」.** 서버엔 없다([BL-619] 의 추종기가 실재하지 않았다).

### 5.2 ★CONTROL 자신의 오류 (5건)

6. **G-A4′ 의 분모가 판별력 0.** 「미조인 6건」의 필터는 전량 27/27 을 고른다. 「6」은

    `tick_stall` 이 먼저 발화해 애초에 판별 자리가 아니었다(§4.3).

### 5.3 이 10건에서 반복되는 형태

- **4 · 5 · 7 · 8 은 같은 병이다** — 「검증되지 않은 산문이 정본 자리에 앉아 있었다」.

## 8. 절차에서 나온 것

### 8.1 ★★★서브에이전트 10기 중 9기가 세션 한도로 죽었는데 **파일은 이미 쓰여 있었다**

레포는 이 함정을 **이미 알고 있었다** — `gates-and-traps.md` 에
「`codex exec` 는 10분을 넘겨 Bash 상한(600000ms)에 걸리는데, **그때도 파일은 이미 쓰여 있을 수 있다**
— 죽었다고 재실행하기 전에 `git status` 부터 봐라」가 적혀 있다.

이번에 같은 모양이 **워크플로 계층에서 재발했다.** 죽은 것은 Bash 호출이 아니라 **에이전트 세션**이었고,
결과는 동일하다 — **생성물은 남고 검증이 통째로 날아간다.** 그리고 이쪽이 더 위험하다.
파일이 존재한다는 사실이 「그 에이전트가 자기 판정식을 돌려 통과시켰다」로 조용히 읽히기 때문이다.
실제로 이번에 살아남은 산출물 중 일부는 **자기 검증 단계를 한 번도 밟지 않았고**, 그것을 CONTROL 이
동결 원자료로 다시 재는 것 말고는 구분할 방법이 없었다.

★규율 — **한 계층에서 배운 함정은 계층 이름만 바꿔 재발한다.** 「도구가 죽었다」와 「산출이 없다」는
같은 말이 아니고, 「산출이 있다」와 「검증됐다」도 같은 말이 아니다. 회차 계약에
**「검증 산출물의 존재」를 별도 항목으로** 요구해야 한다 — 결과 파일의 존재는 그 증거가 아니다.

### 8.2 ★★Generator(codex) / Evaluator(claude) 분리가 값을 했다 — 평가자가 **오케스트레이터를** 잡았다

이 파이프라인의 원래 의도는 「생성자의 코드를 평가자가 시험한다」였다. 이번에 실제로 일어난 것은
**평가자가 CONTROL 이 동결한 판정식 2개를 반증한 것**이다(G-A4′ 판별력 0 · G-A6 항진명제).

★그리고 **교체판이 원안보다 강했다.** 원안은 「값이 맞았다」만 보고했고, 교체판은 반사실을 함께
낸다 — 서버 체결만으로 계산하면 **0/4**, 로컬 체결만으로도 **0/4** 로 떨어진다.
**적합은 검증이 아니다**(LESSON 계열의 재확인). 반사실이 떨어지지 않는 식은 무엇도 가르지 못한다.

★★이 값이 나온 조건은 **평가자가 CONTROL 의 결론을 입력으로 받지 않았다**는 것이다. 판정식과
동결 원자료만 받았기 때문에 「분모가 뭔가」를 되물을 수 있었다. 결론을 먼저 주면 평가자는
**그 결론에 맞는 검증**을 한다.
