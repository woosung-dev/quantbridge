## 왜 했나

직전 5개 스프린트(#474~#478)가 **라이브 머니-패스**의 정직성을 복구했다. 남은 것은 **백테스트가 화면에 내놓는 숫자**였고, 실측으로 두 개의 구멍이 확인됐다.

1. **Sharpe 가 Sharpe 가 아니었다.** `_sharpe` 는 bar 수익률의 `mean/std × √N` — 위험조정수익이 아니라 **t-통계량**이다. 같은 리포트의 Sortino 는 이미 TV 컨벤션이라 한 화면에서 두 척도가 병존했다.
2. **레버리지가 받아들여지고 무시됐다.** `leverage` 1~125 를 검증하고 DB 에 저장한 뒤 **엔진 참조가 0건**. 응답으로 노출되고 `mdd-caption` 은 "leverage Nx 가정" 캡션까지 그릴 준비가 돼 있었다.

## ★★설계 전환 — 레버리지 시맨틱을 TV/MT5 컨벤션으로

핸드오프와 최초 설계는 "사이징 × leverage"(리테일 직관: 10x = 10배 포지션)였다. 사용자가 **TV 정렬**을 지시했고, 1차 출처 조사 결과 **곱하기 모델은 업계 어디에도 없었다**.

| 플랫폼           | 레버리지가 수량을 바꾸나 | 표현                                                                           | 청산                                     |
| ---------------- | ------------------------ | ------------------------------------------------------------------------------ | ---------------------------------------- |
| TradingView      | ❌                       | `margin_long/short` = 포지션 중 자기 자금 비율(%). 25% → 자본의 400% 까지 진입 | **부분** 청산. 에뮬레이터는 필요액의 4배 |
| MT5              | ❌                       | 계좌 레버리지 1:N → 필요증거금 = notional/N                                    | Stop Out, 손실 큰 것부터                 |
| QuantConnect     | ❌                       | `SetLeverage` = 매수여력 상한                                                  | 마진콜                                   |
| 거래소 UI(Bybit) | △                        | **증거금** 입력 × N = notional                                                 | 격리 **전량** 청산                       |

**핵심**: 어디서도 레버리지가 _notional 입력_ 을 곱하지 않는다. 거래소 UI 조차 곱하는 대상은 **증거금** 입력이다. 우리 `percent_of_equity` 는 notional 기준이라 곱하면 두 컨벤션을 섞는 것이었다.

**이 전환이 설계를 줄이면서 강하게 만들었다.**

|                           | 곱하기 모델(폐기) | TV/MT5(채택)                                             |
| ------------------------- | ----------------- | -------------------------------------------------------- |
| `compute_qty`             | 수정 필요         | **무변경**                                               |
| 레버리지>1 TV parity      | 깨짐              | **유지**                                                 |
| 마진 게이트 위상          | 부가 기능         | **레버리지의 작동 기제 자체**                            |
| "사이징+청산 원자성" 우려 | 필수              | **소멸**(포지션이 안 커지므로 판타지 equity 자체가 없음) |

★함께 **내 보고 오류 1건 정정** — "사이징 상한 100% 때문에 레버리지 노출을 표현 못 한다" 는 틀렸다. `position_size_pct`(`le=100`)는 **Live 미러 전용**이고 일반 수동 사이징 `default_qty_value` 는 **상한이 없다**. 상한 완화 작업은 불필요했다.

### codex G0 — 설계 결함 적발

**마진 게이트를 `entry()` 에만 걸면 stop 진입이 뚫린다.** `check_pending_fills` 가 `entry()` 를 우회해 `Trade(...)` 를 직접 만들기 때문이다(`Trade(` 생성 site 2곳). 같은 구조가 청산가 캐시에도 적용되므로 **단일 chokepoint 통합**으로 두 결함을 한 번에 닫았다.

내 주장 하나도 정정됐다 — `sharpe_convention` 마커는 정렬을 **고치지** 않는다. `repository.py:75` 는 원시 JSONB 숫자만 캐스팅하므로 마커는 혼재를 **보이게** 할 뿐이다(→ FE 고지 + BL-462).

### 최종 codex 누적 diff — BLOCKING 2 + P1 2 + P2 2

- **BLOCKING ①** `entry()` 가 flip/close 를 게이트보다 먼저 실행 → 증거금 거부 시 **역전이 조용히 전량청산으로 바뀜**(실거래소는 주문 전체 거부). → `_can_afford_entry()` **pre-flight** 신설. flip 부작용 전에 "청산 예정분의 실현손익 + 해제 증거금" 을 반영한 사후 상태로 판정하고, 불가하면 flip 자체를 하지 않는다
- **BLOCKING ②** 청산 metrics 가 `cfg.leverage > 1` 로 판정해 **단일 게이트 술어 우회** → `is_leverage_active()` 로 교체
- **P1 ①** `assumptions-card` 가 Nx 실행에도 "1x · 롱/숏 / 강제 청산 미반영" 표시 = **엔진과 정반대 고지**. ★S7 스펙에서 내가 누락했다 — 이 스프린트가 없애려던 바로 그 형태의 거짓말

## ★스스로 찾은 한계 — 마진 게이트는 gross 자본으로 판정한다

## 함정 (다음 세션용)

- **★★`codex exec` 는 백그라운드에서 stdin 이 열려 있으면 무한 대기한다.** `Reading additional input from stdin...` 만 찍히고 CPU 0% 라 "생각 중" 으로 오인하기 딱 좋다. **`< /dev/null` 필수.** 이번에 워커 2기가 각각 52분/38분을 산출물 0으로 태웠다
- **`| tail -N` 파이프는 완료 전까지 아무것도 안 보여준다**(버퍼링). `> file 2>&1` 로 직접 리다이렉트해야 위 정체를 조기에 잡는다
- **`codex exec` 의 쓰기 루트 = 실행 시점 cwd.** 셸이 `backend/` 인 채로 FE 워커를 띄우면 `frontend/` 를 못 건드린다
- **`pnpm test --run` 은 `Unknown option` 으로 죽으면서 exit 0** 이다. `pnpm test` 가 정답(`package.json` 이 이미 `vitest run`)
- **`getattr(t, 'field', False)` 는 미구현 필드를 "정상 False" 로 위장한다.** 청산 카운트가 전부 0으로 나와 오판할 뻔했다(원인 = `RawTrade` 전파가 아직 없었음). 검증에 기본값 있는 `getattr` 를 쓰지 말 것
- **워커 부분 스위트 green ≠ 전체 green.** codex 샌드박스가 로컬 DB 포트를 막아 워커는 API 통합 테스트를 못 돌린다. 실제로 `test_backtests_list.py` 회귀를 전체 실행이 잡았다
