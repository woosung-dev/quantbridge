## 1차 가설 (코드 대조) — 맞았지만 프로덕션의 그것이 아니었다

아래 연쇄는 코드상 실재하고 결정론적 테스트로 재현된다. `broker_filled` 수정은 **유지한다** —
시뮬레이션 상 플립에서 중복 close 를 막는 것은 실제 개선이다. 다만 **실주행에서 관측된 병리는
이것이 아니었다**(§soak).

### 주석의 논리가 절반만 적용돼 있었다

| #   | 연쇄                                                                                                | 근거                                    |
| --- | --------------------------------------------------------------------------------------------------- | --------------------------------------- |
| 1   | 조건부 진입은 `abs(target_position − current_position)` **1장**으로 등재                            | `conditional_entry_planner.py:444`      |
| 2   | 트리거되면 거래소가 **한 번에 플립**. 엔진은 다음 봉에서야 안다(1m → +50~104초)                     | soak 실측 6/6                           |
| 3   | `check_pending_fills` 가 반대편을 **`action="close"`**, 새 leg 를 **`event_action="fill"`** 로 기록 | `strategy_state.py:825-899`, `:654-678` |
| 4   | `run_live` 가 **`fill` 만 거르고 `close` 는 통과**시킨다                                            | `event_loop.py:504-507`                 |
| 5   | 그 close 가 `buy` + `reduce_only=True` 로 나가 `110017 same side`                                   | `live_signal.py:196-208`, `:2862`       |

> `# entry / close 만 dispatch 대상 (fill 은 broker 측 pending stop 체결)`
> — broker 가 이미 체결한 것은 `fill` leg 뿐 아니라 **그 병합 주문에 포함된 close leg 도 마찬가지**다.

**수정** = `TradeEvent.broker_filled` 신설 → `check_pending_fills` 발 close 에 표시 → dispatch 필터에서 제외.
`to_report()`·PnL·백테스트 결과 **불변**(`TradeEvent` 소비처는 `event_loop.py:488,493` 한 곳뿐 — CONTROL 대조).
**시장가 반전(`process_market_intents`)의 close 는 계속 dispatch 된다** — 그 경로는 엔진이 먼저
결정하고 거래소가 뒤따르므로 close 시점에 거래소는 아직 반대편을 들고 있다.

  `-e PYTHONPATH=/app -w /app` 를 줘라.
- ★**`pnpm e2e` 는 자기 dev 서버를 띄우려다 죽는다** — 같은 디렉터리에 `next dev` 가 이미 떠 있으면
