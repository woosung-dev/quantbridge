### LESSON-091 — **성분 통제를 순서대로 돌리면 앞 성분이 뒤를 가린다.** 배경을 통일해야 통제다 (1/3)

- **상황:** 같은 회차 [BL-598]. 「ANTLR 캐시가 원인」까지 좁힌 뒤 성분을 갈랐다 — 한 프로세스

  **15.0 / 1.0 / 1.1 배**를 얻었고, 「비용을 지는 것은 **파서 DFA 하나뿐**」으로 적었다.
- **반증:** 그 루프는 회차마다 `→ warm` 으로 **다시 데운다.** 그래서 `shared_ctx` 를 비울 차례가
  왔을 때 parser DFA 는 **이미 워밍돼 있었다.** 1.0배는 「shared_ctx 가 무관하다」의 증거가 아니라
  **「parser DFA 가 데워져 있으면 나머지가 추가 비용을 안 진다」**의 증거일 뿐이다. 두 문장은
  다르고, 앞의 것은 **과대 진술**이었다.
- **재측:** 성분마다 **새 프로세스**를 띄워 리셋 직전 배경을 셋 다 「cold 1회 + warm 1회」로

  cold/warm 은 셋 다 51.2s/3.8s. **순서의 산물은 아니었다** — 결론은 살고 **문장이 좁아졌다.**
- **해결:** ⑴ 성분 A/B/C 를 비교하려면 **각 측정의 배경 상태가 같아야 한다.** 같은 프로세스에서
  순차로 돌리면 배경은 「앞 성분이 남긴 것」이라 **매 회차 다르다** ⑵ 배경을 통일하는 가장 싼
  수단은 **프로세스를 갈아 끼우는 것**이다(상태가 프로세스 전역이면 특히) ⑶ 그래도 **못 재는
  것을 적어라** — 여기서는 「셋 다 비어 있는 완전 cold 에서 각 성분의 단독 몫」이 미측정이고,
  캐시를 **끈 채로** 파싱할 수단이 없어 실험 설계 자체가 없다.

### LESSON-094 — **「보호해야 한다」는 규칙은 보호 대상이 실제로 결합돼 있는지부터 확인해라** (1/3)

  ⑵ **비용이 큰 보호일수록 먼저 의심해라.** 6회차 × 「가장 아픈 것을 못 고침」은 근거를 재확인할

### LESSON-097 — **이벤트가 안 왔으면 리스너가 아니라 「이벤트를 쏘는 쪽의 거부권」을 먼저 봐라** (1/3 · [BL-698] 승격)

- **상황:** 백테스트 폼 제출이 죽었다. 증상은 「`POST /api/v1/backtests` 가 브라우저를 **아예 떠나지 않는다**」였고 422 도 에러도 로그도 없었다. 앞선 조사가 후보 넷(`.next` 캐시 · 버튼-폼 배선 · 하이드레이션 · RHF 검증)을 실측으로 기각했고, 회차 지시는 **「1순위 후보 = 토큰 획득」**이었다 — `mutationFn` 이 `getToken()` 을 await 하므로 거기서 멈추면 증상과 맞는다는 추론이다.
- **반증:** 고장은 그보다 **훨씬 상류**였다. `<form>` 에 `noValidate` 가 없어 native constraint validation 이 살아 있었고, 기본값 `fees_pct=0.00055`·`slippage_pct=0.00014` 가 `step="0.0001"` 격자를 어겨 폼이 **constraint-invalid** 였다. 이때 브라우저는 **submit 이벤트를 발화조차 하지 않는다.** ⇒ `handleSubmit`·`onSubmit`·`mutate`·`getToken` 이 **전부 안 돈다.** 토큰은 **요청조차 되지 않았다.** 제출 버튼이 `<form>` 밖에 `form={id}` 로 붙어 있어 native 경고 UI 도 안 떴다.
- **해결:** 「X 가 안 일어났다」를 디버깅할 때 **X 를 일으키는 쪽이 거부권을 가진 층**을 먼저 열거해라. 여기서는 `handleSubmit` 의 코드가 아니라 **HTML 폼 제출 알고리즘**이 거부권자였다. 후보를 `mutate`→`getToken`→네트워크 순으로 **하류로** 쫓으면 영원히 안 나온다 — 이벤트 부재는 **상류 거부**의 지문이다. 값싼 판별법: `form.checkValidity()` 와 각 입력의 `validity.*` 를 한 번 찍어 보는 것(1회 호출로 갈렸다).
- **1차 누적.** ★부수 — 원장이 적어 둔 「권장 접근」(실패 지점 = 422 **응답 문구** assertion)이 거짓이었다. 실제 실패는 그보다 앞선 `waitForRequest` 타임아웃이라 문구는 도달조차 안 했다. **남이 좁혀 둔 후보 집합을 코드 대조 없이 상속하지 마라** — 이 회차는 그 셋을 다 버리고 이겼다. ★**축 판정 (2026-08-14 재계수)** — 「착수 전제·상속 사실이 반증됐다」는 `dev-log/INDEX.md` 2026-08-07~08-12 **22줄 중 12줄**이다. 다만 이 축은 이미 [generator-evaluator-pipeline.md](./development/workflows/generator-evaluator-pipeline.md) **§8.1**(=[LESSON-037])로 승격돼 있으므로 **다시 승격하지 않는다** — 이 카드는 그 축의 개별 사례로 남는다(`lessons.md:12` 규약).

### LESSON-098 — **검증을 우회하는 테스트는 초록으로 결함을 덮는다 — 테스트는 사용자가 밟는 경로를 밟아야 한다** (1/3 · [BL-698] 승격)

- **상황:** 백테스트 폼 단위 테스트 17건이 **전부 초록**인 채로 제출이 프로덕션에서 죽어 있었다. `753f4bf6`(2026-08-07) 이후 **212 커밋 동안** 어떤 게이트도 못 잡았다.
- **반증:** 17건 전부가 `fireEvent.submit(form)` 으로 **submit 이벤트를 직접 디스패치**한다. 이는 브라우저의 native constraint validation 을 **통째로 우회하는 경로**다 — 사용자는 버튼을 누르고, 그 경로에서는 폼이 invalid 면 이벤트가 애초에 안 난다. 즉 테스트는 **결함이 사는 층을 건너뛴 지점부터** 시작하고 있었다. 422 케이스들은 한술 더 떠 `capturedOpts.current.onError?.(err)` 를 **손으로 호출**한다 — 제출이 `mutate` 에 도달하는지 재는 케이스가 **하나도 없었다.**
- **해결:** 「이 테스트는 사용자가 밟지 **않는** 지점에서 시작하는가」를 물어라. 시작점을 한 칸 앞으로 (`submit` → `click`) 옮기는 것만으로 red 가 됐다. ★**함정: jsdom 이 못 잡는다고 단정하지 마라** — jsdom 25.0.1 은 `stepMismatch` 도 novalidate 게이트도 **정확히 구현한다**(폼 밖 `form=` 버튼의 소유자 해석까지). e2e 로 올리기 전에 **단위 층에서 먼저 재라**(이번엔 e2e 예산 0 으로 red→green 을 다 냈다).
- **1차 누적.** ★부수 — 수리 중 넣은 `vi.waitFor` 가 **유일한 실패 표면**이 될 뻔했다(`mutate` 는 `await act` 안에서 동기 호출이라 waitFor 는 폴링 타임아웃만 추가한다). 리뷰가 1회 flake 를 관측해 잡았고, 직접 단언으로 바꾸자 변이 시 실패 시간이 **~1030ms → ~17ms** 로 떨어졌다. **상시 red 게이트를 없애는 회차가 새 flake 를 심을 뻔했다.**

### LESSON-105 — **결함을 고치는 코드가 새 항진명제를 만든다 — 「전건 통과」가 좋아 보이면 판별력부터 재라** (1/3)

### LESSON-106 — **복구 안전망은 「무엇을 되살리는지」로 판정해라 — PR 복원 버튼은 브랜치 팁이 아니라 PR head sha 를 되살린다** (1/3)

- **상황:** 같은 회차. 원격 브랜치 267건 삭제의 안전 근거는 「PR 이 있으므로 GitHub 이 sha 를 보관하고 복원 버튼이 살아 있다」였다(프롬프트가 준 전제). 브랜치명 ↔ PR head ref 로 맞추면 후보 276건이 전부 그 근거를 갖는 것처럼 보였다.
- **반증:** 복원 버튼이 되살리는 것은 **PR 의 `head.sha`** 이지 브랜치의 **현재 팁**이 아니다. 팁 sha ↔ PR head sha 를 맞추자 **9건이 불일치**했다 — PR 이 머지된 뒤 커밋이 더 쌓인 브랜치들이고, 지웠으면 그 커밋들이 안전망 밖에서 사라졌다. 이름축만 썼으면 못 봤다. 뒤이어 codex 적대 리뷰가 「그 9건의 커밋 **전부**가 밖」이라는 내 문장도 반증했다(실제 72개 중 **62개**).
- **해결:** ⑴ 안전망은 **이름이 아니라 해시**로 판정해라 — 이름이 다른데 sha 가 같은 짝도 있었다. ⑵ 「안전망이 있다」를 쓰기 전에 **그 안전망이 정확히 무엇을 되살리는지** 한 문장으로 적어라. 적을 수 없으면 아직 모르는 것이다. ⑶ 안전망 확인은 **표본이 아니라 전건**으로 — 표본 5/5 로 넘어갔다가 지적받고 121건 전건 조회했다(121/121 OK). ⑷ 되돌리기가 어려운 삭제는 **삭제 전에** 복구 원장(대상·sha·근거)을 파일로 남겨라.
- **1차 누적.** ★[LESSON-094]「「보호해야 한다」는 규칙은 보호 대상이 실제로 결합돼 있는지부터 확인해라」의 파괴적 작업판이다. 그때는 보호 대상이 결합돼 있지 않았고, 여기서는 **보호 수단이 내가 생각한 것을 보호하지 않았다.**

### LESSON-110 — **「반증했다」고 적기 전에, 그 관측이 무엇을 재는지부터 확인해라** (1/3 · [BL-737] 승격)

- **상황:** 2026-08-15 soak-watch-restore. 소크 감시자가 죽어도 알리도록 `OnFailure=` 알람 유닛을 신설했다(인라인 `curl`, `.env.local` 을 그 자리에서 소싱). 강제 발화 실증에서 알람 유닛이 `Finished` 로 끝나는 것을 보고 **「AC-2 성공」으로 보고했다.** codex 적대 리뷰는 「systemd 가 `${TELEGRAM_*}` 를 bash 실행 전에 확장해 알람이 무력하다」를 P1 으로 냈고, 나는 `systemctl show -p ExecStart` 를 찍어 **변수가 리터럴로 남아 있으니 phantom** 이라고 판정했다.
- **반증:** 둘 다 틀렸다. ⑴ `systemctl show -p ExecStart` 의 출력은 systemd 의 **파싱 결과(확장 _전_ 문자열)** 이고 확장은 실행 시점에 일어난다 — 내가 「확장 안 된다」의 증거로 쓴 것이 그 질문에 답하는 관측이 아니었다. ⑵ `curl` 에 `--fail` 을 붙이자마자 알람 유닛이 **exit 22** 로 뒤집혔고, 진단은 텔레그램 **HTTP 404**(빈 토큰으로 `…/bot/sendMessage`)였다. **`Finished` 는 알림 도착의 증거가 아니었다** — `--fail` 이 없으면 404 에도 curl 은 rc=0 이다. ⇒ **codex 의 결론은 옳았고 근거만 달랐다.** systemd 에서 리터럴 `$` 는 `$$` 이고, `$${TELEGRAM_CHAT_ID}` 로 고친 뒤에야 알람 유닛이 `Result=success`(= HTTP 200)를 냈다.
- **해결:** ⑴ **반증은 「내 관측이 그 질문에 답하는가」를 통과한 뒤에만 성립한다.** 도구가 무엇을 출력하는지(파싱 결과인가 실행 결과인가)를 모르면 그 초록도 빨강도 무증거다. ⑵ **성공/실패가 목적과 일치하도록 도구를 세워라** — `--fail` 을 붙이는 순간 유닛 상태가 「도착했나」의 증인이 됐다. 그 전까지 유닛 상태는 「프로세스가 끝났나」만 말했다. ⑶ **적대 리뷰를 반박할 때가 가장 위험하다** — 채택할 때는 코드를 다시 읽지만, 반박할 때는 한 번 본 것으로 끝낸다.
- **1차 누적.** ★[LESSON-092]「검사기가 보는 표면 < 실제 실패 표면」의 판인데, 이번에는 **그 검사기가 내 반증 자신**이었다. ★그리고 이 회차의 주제였던 「돌았다 ≠ 발화했다」(2026-08-13 소크 감시자가 41시간 `rc=127` 로 죽는 동안 타이머는 정상 `waiting` 이었다)가 **내 검증 절차 안에서 그대로 재현됐다** — 같은 회차에서 그 병을 고치면서 같은 병에 걸렸다.

### LESSON-112 — **「기계가 못 가린다」와 「아무도 판정하지 않았다」는 다른 말이다** (1/3 · [BL-703] 계열 승격)

### LESSON-114 — **「가드가 읽는 값」을 아무도 쓰지 않으면 그 계층은 없는 것이다 — 소비자가 아니라 생산자를 재라** (1/3)

- **상황:** 2026-08-17 auth-selfhost. geo-block 은 문서·코드·테스트가 모두 갖춰진 **3계층 방어**였다. [LESSON-087]「변이가 파일에 도달해도 그 경로가 안 돌면 무증거」·[LESSON-109]「한 번도 발화한 적 없는 안전망은 있다가 아니다」와 같은 가족이고, 여기서 새로 드러난 것은 **결손이 소비자 쪽이 아니라 생산자 쪽**이라 코드 grep 으로는 「구현돼 있다」로 보인다는 점이다. ★같은 회차에서 두 번째 판도 나왔다 — 구 `test_clerk_auth.py` 는 SDK 를 `MagicMock` 으로 바꿔 `is_signed_in=False` 를 돌려줬다. **서명·만료·`iss`·`aud` 중 무엇도 검증된 적이 없었고**, 그 사실은 실제 키로 서명한 토큰을 처음 먹였을 때 드러났다.

### LESSON-116 — **표적 테스트와 변이를 전건 통과한 구현이 전량 회귀 5건을 품고 있었다 — 낡은 mock 은 표적 범위 밖에서만 보인다** (1/3)

### LESSON-120 — **실행 축이 초록인 것은 선언이 옳다는 뜻이 아니다 — 무관한 전이 import 가 손 목록의 구멍을 가린다** (1/3)

- **상황:** 2026-08-17 [BL-788]. `tests/conftest.py` 의 모델 import 손 목록에 `optimizer` 가 없다. 그 목록이 곧 `create_all` 범위인데도 `optimization_runs` 는 늘 만들어졌고, **세션 스코핑 프롬프트**는 그 이유를 「`tests/optimizer/` 9파일이 수집 단계에서 우연히 import 하므로 **수집 순서 의존**」이라고 적었다. ★출처를 정확히 적는다 — **원장이 아니다.** `docs/backlog.md` 의 BL-788 은 `auth_*` 축을 적었고 그 서술은 이번 회차로 반증되지 않았다(적대 리뷰 지적).
- **반증:** 수집과 무관했다. 실측 — conftest 의 `from src.main import create_app` 이 `src/main.py:447` 의 `app = create_app()` 을 태우고, 그것이 stress_test router → dependencies → service 를 지나 `src.optimizer.models` 를 끌어온다. **5홉짜리 무관한 배선**이 범위를 채우고 있었다. 그래서 실행 축 검사면(자식에서 `tests.conftest` 만 import 해 실제 등록 표를 덤프)은 수리 **전에도 초록**이었고, 변이 4종 중 `waitlist`·`stress_test` 제거 **2종도 초록**이었다 — 둘 다 같은 배선이 대신 등록해 준다. red 를 낸 것은 **선언 축**(손 목록 ⊇ `src/**` 표 census) 하나뿐이다.
- **2차 반증(같은 회차, 적대 리뷰).** 그 선언 축 자신이 **소스 텍스트만 보고 있었다.** `ast.walk` 로 import 를 세니 `if TYPE_CHECKING:` 안이나 함수 본문의 import 도 「명시 import 했다」로 셌고, conftest 의 그 한 줄을 `TYPE_CHECKING` 블록으로 옮기자 **런타임 등록이 사라졌는데 세 다리 전부 초록**이었다. census 파서도 `ast.Assign` 만 봐서 `__tablename__: str = "…"`(AnnAssign)로 선언한 실동작 테이블이 census 에서 통째로 빠졌다 — 프로브로 재현(그 모듈을 아무도 import 안 하면 `3 passed`).
- **3차 반증(같은 회차, 적대 리뷰 2라운드).** 남은 두 다리도 **자기가 검사한다고 적은 것을 검사하지 않았다.** ⑷ 다리는 「alembic 의 `target_metadata` 를 본다」고 적고서 자식에서 `SQLModel.metadata` 를 덤프했다 — `alembic/env.py:48` 이 `target_metadata = SQLModel.metadata` 라 **우연히 같은 객체**였을 뿐이다. 그 줄만 빈 `MetaData()` 로 바꾸면 실제 `alembic check` 는 DB 의 모든 표를 removed 로 보는데 **네 다리 전부 초록**이었다(실측 `4 passed`). 같은 회차에 census 파서는 이름이 글자 그대로 `Table`·`table=True` 인 것만 봐서 `from sqlalchemy import Table as SATable` 로 만든 표(런타임 등록 `['probe_alias']`)와 `class X(SQLModel, table=FLAG)`(등록 `['escapedprobe']`)를 못 봤다 — 그런 모듈을 아무도 import 안 하면 실행 축도 못 보므로 **역시 네 다리 전부 초록**이었다(실측 `4 passed` ×2).
- **해결:** ⑴ 손 목록이 「범위」인 구조에서는 **선언을 재라 — 결과를 재면 남의 import 그래프가 답을 대신 낸다.** 결과 축은 보조로만 둔다. ⑵ 기대치는 손 목록끼리 대조하지 말고 `src/**` **AST census**(`table=True` 클래스 + `Table("…", SQLModel.metadata, …)`)에서 뽑아라 — 그래야 목록이 하나 더 생겨도 늙지 않는다. ⑶ 「누락 방지용 explicit import」라 적힌 `test_migrations.py` 의 세 번째 목록은 넉 달간 4개를 빠뜨린 채였다. **이름이 성질을 주장하는 목록은 그 성질을 검사받은 적이 없다.** ⑷ 변이 실측 — census 를 비우고 비어있음 가드를 무력화하자 차집합(선언) 두 다리가 **초록**이 됐다. 양방향 비교(실행) 다리만 red 다. ⑸ ★**선언 축의 판정 기준은 「소스에 구문이 있는가」가 아니라 「실행이 보장된 자리에 있는가」다** — `tree.body` 직계만 세면 조건부·지연 import 가 자동으로 빠진다. ⑹ census 파서는 **선언 형태를 좁게 잡지 마라**(AnnAssign · `__tablename__` 생략 시 클래스명 소문자). 좁으면 **막으려던 결함군이 그대로 통과**한다. ⑺ ★**검사기는 대상 자체를 읽어라 — 「지금은 값이 같은 대리 객체」를 읽지 마라.** 지금 같다는 것은 앞으로도 같다는 뜻이 아니고, 갈라지는 순간 검사기는 조용히 항진명제가 된다. 여기서는 `context.configure()` 가 심고 autogenerate 가 꺼내는 바로 그 `opts["target_metadata"]` 를 잡는다(alembic `runtime/environment.py:912` → `autogenerate/api.py:371`). 한 번도 configure 되지 않았으면 **ABORT** — 빈 캡처가 「일치」로 읽히는 길을 남기지 않는다. ⑻ ★**「두 축이 서로의 사각을 덮는다」는 주석은 증명하기 전까지 희망이다.** 여기서는 거짓이었다 — 실행 축이 보는 것은 **누군가 import 한** 모듈뿐이라, 파서가 못 보는 모듈은 실행 축도 못 본다. 상호 보완이 깨진 자리에서 파서는 「못 보면 넘어간다」가 아니라 **「결정 못 하면 멈춘다」**여야 한다.
- **1차 누적.** ★[LESSON-087]「변이가 파일에 도달해도 그 경로가 안 돌면 무증거」의 **반대 판**이다 — 그쪽은 경로가 안 돌아 무증거였고, 이쪽은 **경로가 두 갈래라** 한 갈래를 끊어도 증거가 안 났다. ★[LESSON-111]「원장이 적은 처방의 대상이 코드에 없었다」와도 같은 가족인데, **이번엔 그 병을 내가 저질렀다** — 반증했다고 적은 인과의 출처를 원장으로 잘못 지목해 존재하지 않는 줄을 CONTROL 에게 고치라고 넘길 뻔했다.

### LESSON-121 — **생성자가 남긴 `xfail(strict=True)` 는 「결함 보고」다 — 픽스처가 도메인 의미를 뒤집으면 옳은 코드가 결함으로 원장에 박힌다** (1/3)

- **상황:** 2026-08-21 밤샘 루프 1차, lane `ops2-stack-migrate`. 무인 러너가 `soak-stack.sh migrate` 테스트를 쓰면서 「적용 대기 개수가 delimiter 행까지 세어 3을 센다」를 `xfail(strict=True)` 로 박았다. AC 는 초록이었고 변이도 red 였다 — **판정 계층 전부가 통과시켰다.**
- **반증:** 픽스처가 alembic 출력의 화살표 의미를 **뒤집어** 놨다. 실측(`uv run alembic history -r 20260815_0004:head`) — 형식은 `<부모> -> <자식> (head), 메시지` 이고 **최신순**이다. `-r cur:head` 는 cur 를 포함하므로 맨 아래에 「cur 를 **만든** 전이」(= 이미 적용분)가 한 줄 더 붙는다. 스크립트의 `awk '{print} $1==c && $2=="->" {exit}'` 는 **`cur -> …`(= 대기분)를 포함하고 그 아래를 자른다** — 옳다. 세션의 픽스처는 `head -> pending / pending -> current / current -> base` 라 head 가 current 의 **조상**이 되는 불가능한 계보였고, 그래서 3줄이 다 남아 「3을 센다」가 나왔다.
- **왜 아무 게이트도 못 잡았나:** ⑴ AC 는 「그 파일의 테스트가 rc=0 인가」만 보고, `xfail` 은 rc 를 **0으로 유지한다**. ⑵ 변이 축은 **다른 축**(published port 대조)을 겨눴다 — 그 축은 실제로 red 였다. ⑶ 대상 스크립트 무변경이라 diff 가 「테스트만 늘었다」로 보인다. ⇒ **세 층 전부가 「테스트가 늘었다」는 재고 「그 테스트가 참인가」는 안 잰다.**
- **해결:** ⑴ ★**`xfail(strict=True)` 는 코드 변경과 같은 등급의 주장**이다 — 「이 제품 코드는 지금 틀렸다」를 원장에 박고, 나중에 누가 고치면 XPASS 로 red 를 낸다. 그래서 **codex finding 과 같은 바(코드 대조)를 통과해야 한다**(`AGENTS.md` §메타-방법론 「codex finding 은 **코드 대조 후에만** 채택 — phantom finding 차단」의 확장이고, 그 규칙이 **사람이 읽는 finding 뿐 아니라 세션이 코드에 남기는 마커에도** 걸린다는 것이 이 카드다). ⑵ 대조 방법은 문서가 아니라 **그 도구를 한 번 돌려 보는 것**이었다 — 이 건은 `alembic history -r A:B` 한 줄이 갈랐다. ⑶ 픽스처가 **도메인 출력 형식을 모사**할 때는 그 형식을 실측해서 주석에 좌표와 함께 박아라(이 회차 수리에 그 6줄 주석을 넣었다). ⑷ 수리 뒤 **그 축 자신에 변이를 걸어 판별력을 재라** — awk 트림을 제거하니 `1 failed`(제거 전에는 `12 passed`).
- **1차 누적.** ★같은 회차에 나온 두 `xfail` 중 **나머지 하나는 진짜였다**(`soak-restart.sh --help` 가 `sed '2,40p'` 로 34행 헤더를 넘겨 실행 코드를 찍는다 — 4회차 `db-backup.sh --help` 의 반대 방향). **비율이 아니라 개별 대조가 답이다 — 「하나가 참이니 나머지도」가 이 병의 입구다.** ★[LESSON-111]「원장이 적은 처방의 대상이 코드에 없었다」와 같은 가족이고, 이번엔 **생성자가 그 자리에 새 거짓을 만들어 넣었다.**

### LESSON-122 — **step 파일에 적은 「이렇게 나올 것이다」는 사실상 AC 다 — 재지 않은 기대가 옳은 세션을 죽인다** (1/3)

- **상황:** 2026-08-21 밤샘 루프 2차, lane `fe2-builtin-hints`. 내가 쓴 step0 이 「프로토타입 키(`toString`·`__proto__`)를 넣으면 **fallback 이 나와야 한다**」를 기대로 적었다. 무인 세션은 시킨 대로 `category: "noop"` 을 단언했고 **AC 가 3회 red 로 `error`** 를 냈다. 8 lane 중 유일한 실패다.
- **반증:** 틀린 것은 테스트가 아니라 **내 기대**였다. `_HINTS` 는 객체 리터럴이라 `Object.prototype` 을 상속하고, 조회가 `_HINTS[name]` 직접 인덱싱이라 **상속 키가 truthy 로 잡혀** `if (meta)` 를 통과한다. 그런데 그 값은 함수라 `{ name, ...meta }` 가 **own enumerable 0개**를 퍼뜨려 결과가 `{ name }` 뿐이 된다 — `hint` 도 `category` 도 없다(실측 5종 전건). ⇒ 진짜 결함이었고 [BL-814] 로 올렸다.
- **왜 위험한가:** 러너는 「AC 가 재실행된다」만 보증하는데, **step 파일의 산문은 세션에게 AC 와 구별되지 않는다.** 세션이 순종적일수록 내 오류가 그대로 단언으로 굳는다. 이번엔 red 로 멈춰서 잡혔지만, **기대가 우연히 참인 방향으로 틀렸으면 초록으로 굳었을 것이다**(그쪽이 더 흔하다).
- **해결:** ⑴ ★**재지 않은 기대는 step 에 쓰지 마라.** 값을 적으려면 **먼저 돌려 보고 실측표로** 박아라(이번 복구가 그것이다 — 실측표 삽입 → `pending` 복귀 → 재실행 → green). ⑵ 재기 어려우면 값을 쓰지 말고 **「관측한 것을 박아라 + 예상과 다르면 `summary` 에 적어라」**로만 지시해라. ⑶ 복구 절차 정본 = `.claude/commands/harness.md` §4 「AC 자체가 틀렸다면 AC 를 먼저 고쳐라」.
- **1차 누적.** ★[LESSON-121]「생성자가 남긴 `xfail` 은 결함 보고다」의 **거울상**이다 — 그쪽은 **세션이** 옳은 코드를 결함으로 박았고, 이쪽은 **내가** 결함 있는 코드를 옳다고 박았다. 둘 다 뿌리는 같다: **자연어로 적은 기대가 검증되지 않은 채 판정에 들어간다.**

### LESSON-123 — **착수 전 프로브의 값은 「된다」를 확인하는 데 있지 않고 「안 된다」를 무인 실행 전에 만나는 데 있다** (1/3)

- **상황:** 2026-08-21 밤샘 루프 2차 저작 단계. 8 lane 중 셋이 프레임워크 경계를 물어(`server-only` · pg 커넥션 풀 · `next/server`) 착수 전에 import 한 줄씩을 실제로 돌려 봤다.
- **실측:** 둘은 됐다 — `@/lib/auth` 는 `new Pool()` 이 **지연 연결**이라 DB 없이 import 되고 훅이 `auth.options.databaseHooks.user.create.before` 로 도달 가능했고, `@/proxy` 는 3케이스가 실제 green 이었다. **셋째가 안 됐다** — `src/lib/auth-server.ts` 의 `import "server-only"` 는 패키지 exports 맵이 `react-server` 조건에서만 빈 모듈을 주므로 **vitest 에서 top-level throw** 다.
- **★그리고 `vi.mock("server-only", () => ({}))` 로는 안 막힌다** — CJS 로 외부화돼 **Node 의 require 가 먼저 실행**하므로 vitest 의 mock 레지스트리를 지나간다(실측 FAIL). 해결은 `vitest.config.ts` 의 `resolve.alias` → 빈 스텁(실측 PASS · 기존 1,497 케이스 무영향).
- **왜 중요한가:** 이 lane 은 **AC red 측정을 통과한다**(파일이 없으니 rc=1). 판별력 측정으로는 절대 안 잡히고, 무인 실행에서 세션이 3회 retry 를 태우고 `error` 로 죽었을 것이다. **그리고 그 수리는 공유 설정(`vitest.config.ts`) 변경이라 lane 안에서 하면 8 lane 이 같은 파일을 고쳐 병합 충돌이 난다** — 저작 단계에서만 고칠 수 있는 종류다.
- **해결:** ★**대상이 프레임워크 경계(`server-only` · `next/**` · DB 풀 · 네이티브 확장)를 물면, lane 을 쓰기 전에 그 모듈을 실제로 import 해 봐라.\*\* 「AC 가 red 다」는 「그 테스트를 쓸 수 있다」를 뜻하지 않는다.
- **1차 누적.** ★[LESSON-087]「변이가 파일에 도달해도 그 경로가 안 돌면 무증거」와 같은 가족 — 그쪽은 **측정이 대상에 안 닿았고**, 이쪽은 **대상에 닿을 길이 아예 없었다.**

### LESSON-124 — **CONTROL 의 검사기가 여섯 번 무증거를 냈고 여섯 번 다 셸이었다 — 판정 도구는 python 으로 써라** (1/3)

- **상황:** 2026-08-21 밤샘 루프 2·3차(FE 16 lane). 코드를 쓴 것은 무인 세션이고 **판정한 것은 나**였다. 그 판정 도구가 여섯 번 틀렸다.
- **실측 6건:** ⑴ AC red 루프에서 `eval "$ac"` 의 `cd apps/web` 이 **잔류**해 뒤 7 lane 조회가 깨졌고 **빈 문자열 `eval` 이 rc=0** 이라 「초록」으로 보였다. ⑵ 워크트리 생성 루프가 **zsh 단어분할**로 lane 8개를 한 덩어리로 읽어 **0개 생성**. ⑶ **macOS bash 3.2 에 연관 배열이 없다** — `declare -A` 실패 후 `T[key]=v` 가 **산술 첨자 0** 으로 해석돼 전부 index 0 을 덮었고 **PR 7건이 같은 제목·본문**으로 올라갔다. ⑷ 같은 이유로 **`mapfile` 부재**(bash 4+) — 검사기가 조용히 「테스트 0파일 · clean」을 출력했다. ⑸ AC 생성기가 경로를 `\"` 로 감싸 **파일이 생겨도 `bash -c` 에서 죽을 AC** 를 만들었다. ⑹ 변이를 `as undefined`(**타입 소거**)로 심어 런타임에 닿지 않았는데 초록을 「안 잡혔다」로 읽을 뻔했다.
- **공통 뿌리:** 여섯 다 **셸의 조용한 실패**다 — 빈 값·미분할·없는 문법이 **에러가 아니라 「아무 일도 안 일어남」**으로 나오고, 그 결과가 **원하는 답과 구별되지 않는다.** ⑶⑷ 는 특히 `set -e` 로도 안 잡힌다(assignment 는 성공하고 builtin 부재는 rc≠0 이지만 파이프 안에서 삼켜진다).
- **해결:** ⑴ ★**판정·집계·대조 도구는 python 으로 써라** — 없는 이름은 `NameError` 로 죽고 빈 리스트는 `0` 으로 보인다. ⑵ 셸을 써야 하면 **각 단계를 서브셸**(`( cd … && eval … )`)에 넣고 **`bash -c` 로 명시 호출**해라(zsh 아님). ⑶ ★**macOS 는 bash 3.2 다** — `declare -A`·`mapfile`·`${var^^}` 는 없다. ⑷ **검사기가 「전건 통과」나 「0건」을 내면 그것부터 의심해라** — 양 극단은 필터가 죽은 두 모양이다.
- **1차 누적.** ★이 레포는 `| tail` 이 rc 를 삼킨 것을 **여섯 번** 겪었고 zsh 단어분할을 **세 번** 겪었다. 이번 회차는 그 계열이 **한 세션 안에서 여섯 번** 나온 첫 사례다 — 도구를 바꾸지 않으면 반복된다.

### LESSON-125 — **판정 도구를 셸에서 python 으로 바꿔도 「엉뚱한 축을 재는」 병은 안 낫는다 — 한 회차에 세 번 틀렸다** (1/3)

- **부수 반증(내 것):** `git checkout -b stage/n7-truth` 가 「already exists」로 실패했는데 **`| tail -2` 가 rc 를 삼켜** `&&` 뒤의 `git merge` 가 통과했고, lane 병합이 **로컬 `main` 에** 붙었다(즉시 `git branch -f main origin/main` 으로 복구, push 0건). **레포에서 11번째 같은 함정** — 「판정 명령에 파이프를 붙이지 마라」가 `AGENTS.md` §5 에 이미 박혀 있다. ★교훈의 갱신형: **rc 를 읽는 자리에 파이프가 없어야 하는 것은 테스트 러너뿐이 아니다 — `checkout`·`merge` 처럼 「성공했나」로 분기하는 모든 git 명령이 대상이다.**

### LESSON-130 — **「ANTLR DFA 는 프로세스 안에서 1회만 낸다」가 거짓이었고, 그 한 문장이 회차 방향 둘을 잘못 세웠다** (1/3)

- **상황:** 2026-08-25. 원장의 살아 있는 `다음 행동` 이 「파스 콜드 비용 수리」의 방향 후보를 **둘**로 적어 두었다 — ⑴ 기동 시 대표 스크립트로 DFA 워밍 ⑵ `s3_rsid` 가 `adaptivePredict` 를 7배 더 부르게 만드는 문법 모호성 축소. 둘 다 「콜드 비용은 프로세스당 1회」라는 전제 위에 서 있었다.
- **사슬:** ⑴ corpus 당 **새 프로세스** + median-of-3 로 재니 스프레드가 **1.013~1.065×** 로 안정됐다(같은 프로세스에서 순서대로 재던 종전 방식은 1.8~2.6배 흔들렸다). ⑵ 새 프로세스에서 X 를 파싱한 뒤 **미지의** Y 를 파싱하면 Y 는 자기 콜드 대비 **24.7~70.2% 만** 줄고 **자기 웜값의 33~254배**로 남았다. ⑶ corpus **8벌 전량**(비용 33.8~66.3초)을 워밍해도 홀드아웃이 자기 웜의 **9.2~11.4배**였다. ⑷ 코드에서 이유가 나왔다 — full-context(LL) 재시도 경로는 **DFA 에 아무것도 쓰지 않는다**(`antlr4/atn/ParserATNSimulator.py:418` → `:441-445`, `execATNWithFullContext` 본문 `:558-659` 에 `addDFAEdge`/`addDFAState` 0건). 결과가 `outerContext` 에 의존하므로 원리상 캐시 가능하지도 않다.
- **반증:** **DFA 는 「프로세스당 1회」가 아니라 「(프로세스 × 새 문법 표면) 당 1회」다.** 그래서 후보 ⑴ 은 「콜드 창을 없앤다」가 아니라 **「33.8~73.7% 줄이고 그 비용을 child 기동 지연으로 옮긴다」**이고, 후보 ⑵ 의 유일한 근거였던 **7.19배는 모호성이 아니라 크기**였다 — 두 파일의 줄 수 비가 208/27 = **7.70배**다.
- **무엇이 갈랐나:** **비율의 분모를 의심한 것**이다. 「s3 가 7배 더 부른다」를 읽고 「s3 가 7배 이상하다」로 넘어가기 전에 `wc -l` 을 쳤다. 그리고 워밍 효과를 **한 쌍이 아니라 4쌍**으로 재서 25.3~70.3% 라는 **범위**를 얻었다 — 한 쌍만 재면 어떤 숫자든 나오고, 그 숫자가 그 쌍의 문법 겹침을 재고 있다는 것을 못 본다.
- **해결:** 원장의 후보 ⑴⑵ 를 취소선으로 내리고, 실측에서 나온 **세 번째 축**(백테스트 1회가 같은 소스를 4번 파싱 — 전부 동일 sha1)을 주력으로 세워 n13 lane 으로 돌렸다. 콜드 자체를 줄이는 유일한 축(SLL 2단계)은 [BL-829] 로, 창 빈도 축은 [BL-828] 로 유예 등재했다.
- **1차 누적.** ★[LESSON-129] 가 「목표를 적는 것과 잴 수 있게 만드는 것은 다른 일」이었다면, 이 카드는 그 다음이다 — **잰 뒤에도 그 측정의 프로세스 경계를 의심해라.** 같은 회차에서 종전 픽스처가 「코드 속도」가 아니라 **실행 순서**를 재고 있었음이 드러났다([BL-830]): 20줄 `s1_pbr` 의 `ratio_to_fastest` 8.43 이 42줄 `s4_hma_curvature` 의 2.19 보다 나쁘다.

### LESSON-132 — **원장 항목의 「지배 성분」 귀속이 틀렸다 — 코드 읽기는 맞았고 그 경로가 안 도는 것을 아무도 안 쟀다** (2/3)

- **상황:** 2026-08-26. `status.md` 의 살아 있는 `다음 행동` 이 [BL-829](SLL 2단계 예측)를 **「콜드 파스 자체를 줄이는 유일한 축이므로 최우선」**으로 지목하고 있었다. 그 항목의 증상 절은 「콜드 파스의 **지배 성분**인 full-context(LL) 재시도 경로는 DFA 에 기록되지 않는다」였고, `antlr4/atn/ParserATNSimulator.py:418` → `:441-445` · `execATNWithFullContext` 본문 `:558-659` 에 `addDFAEdge` **0건**이라는 **정확한 좌표**를 달고 있었다.
- **사슬:** ⑴ lane 저작 전에 `adaptivePredict` 와 `execATNWithFullContext` 를 monkeypatch 로 세었다. ⑵ 그 경로는 `s5_ema_trend` **0회** · `s3_rsid` **29회**(3,672 중) · `i3_drfx` **204회**(27,652 중 **0.7%**)였다. ⑶ SLL 2단계를 실제로 조립해 **204→0** 으로 만들자 49.91→48.06초 = **3.7%**, `s3_rsid` 는 10.79→**10.84초**(차이 없음)였다. AST digest 는 3벌 전부 동일 — **정확성은 성립했는데 이득이 없었다.** ⑷ cProfile 이 진짜 성분을 냈다: `closure_` cumtime **35.77/36.96초(96.8%)** · `PredictionContext.merge` 15.6초, 6,555B 소스에 함수 호출 **1억 6,963만회**.
- **반증:** **코드 읽기는 옳았고 귀속이 틀렸다.** 「그 경로가 캐시를 안 남긴다」는 참이고, 「그래서 그것이 지배 성분이다」는 거짓이다 — 그 사이에 있어야 할 **「그 경로가 몇 번 도는가」를 아무도 안 쟀다.** 좌표가 정확할수록 그 다음 문장이 검증된 것처럼 읽힌다.
- **무엇이 갈랐나:** **제거해 보고 시간을 잰 것**이다. 호출 횟수(204→0)만 봤으면 「없앴다」로 끝났을 것이다. 제거의 **효과**를 재서 3.7% 를 얻었고, 그때 비로소 분모를 찾으러 갔다(cProfile). ⇒ **최적화 축은 「그것이 존재하는가」가 아니라 「그것을 0 으로 만들면 얼마가 줄어드는가」로 판정해라.**
- **해결:** [BL-829] 를 **본문 삭제 + 기각 tombstone**(되살리려면 「full-context 가 지배 성분이 되는 코퍼스」를 먼저 실측하라는 조건 부착). 같은 preflight 가 대체 축을 냈다 — pynescript AST 가 **pickle 왕복에서 digest 를 보존**하므로(`i3_drfx` 53.38초 → **0.0048초**) 프로세스 밖 캐시가 성립한다 ⇒ [BL-832] 등재. **lane 을 한 줄도 안 쓰고 방향이 바뀌었다.**
- **2차 누적.** ★[LESSON-130] 의 재발이다 — 그 카드가 「한 문장(『DFA 는 프로세스당 1회』)이 방향 둘을 잘못 세웠다」였는데, **그 카드를 쓰면서 등재한 항목이 같은 형태로 또 틀렸다.** 공통 형태 = **관측된 사실(코드 구조) + 안 잰 귀속(그래서 이것이 원인)** 이 한 문장에 붙어 원장에 들어가고, 다음 세션이 그 문장을 진입점으로 읽는다. ★그래서 이 레포에 없는 것이 하나 드러났다 — 원장 **lint**(모순·죽은 앵커·미검증 귀속의 정기 점검). `ledger-vitals.sh` 는 **행 수와 개수만** 재고 내용 정합은 아무도 안 본다. 같은 세션에서 ⓪ 표가 [BL-827](ACTIVE·도래)을 **누락**하고 있던 것도 함께 나왔다.

   원장(deactivate · publish · alert · prometheus 델타)뿐이었다.
   표준 reference: `apps/api/tests/tasks/test_live_signal_tick_oracle.py`.
2. **새 순수 함수를 만들면 「그 함수」가 아니라 「그것을 쓰는 경로」를 재는 케이스를 최소 1개 둬라.**
   단위 테스트가 순수 함수를 직접 호출하면 **호출부에서 그 함수를 떼어내는 변이가 red 0** 을 낸다.
   순수 함수 정확성 ≠ 배선.
3. **테스트 페이크는 프로덕션의 제약 축을 그대로 흉내내라.** `row_hash` 단독으로 dedup 하는
   페이크는 실제 UNIQUE 축 `(exchange_account_id, row_hash)` 를 재현하지 못해, **재현하려던 결함
   자체를 페이크 안에서 소멸**시켰다.

**판별 절차 (셋 다 이걸로 잡혔다):** 변이를 심는다 → **그 변이가 도달했는지 따로 확인한다** →
red 가 나는지 본다. **가운데 단계를 빼면 셋 다 놓친다** — 도달 못 한 변이의 red 0 은 무증거다.

★★**「도달」은 파일 내용이 아니라 실행 여부다** ([LESSON-087] 3/3 승격, 2026-08-15). 확인은 3층이다:

1. **앵커가 1건인가** — 0건이면 못 심었고, 2건 이상이면 어디가 바뀌었는지 모른다.
2. **치환이 파일에 들어갔는가** — sha256 스냅샷으로 심고 되돌려라(`git checkout` 금지).
3. ★**그 줄을 실행하는 입력이 테스트 집합에 있는가** — 3 이 빠지면 1·2 를 다 지켜도 무증거다.
   2026-08-15 에 계획서가 ★★로 표시한 가드(`interpreter.py` 의 `and limit is None`)를 지운
   변이가 **파일 도달 확인까지 통과하고 전건 초록**이었다. 그 분기는
   `fill_timing == "next_bar_open"` 일 때만 지나는데 엔진 기본값이 `bar_close` 라 어떤
   테스트도 그 줄을 실행하지 않았다.
   ⇒ **분기 조건에 기본값이 아닌 설정**(`fill_timing`·feature flag·env)**이 걸려 있으면
   그 설정을 명시로 켜는 케이스를 최소 1건 둬라.**

★**판정 명령에 파이프를 붙이지 마라** — `uv run pytest ... | tail -3` 은 **pytest 가 아니라
tail 의 rc** 를 읽는다. 2026-08-15 에 이 함정이 「7종 전부 초록(판별력 0)」이라는 **정반대
전건**을 냈다(출력에는 `6 failed` 가 찍혀 있었다). rc 를 먼저 잡고 텍스트는 나중에 잘라라.
게이트 rc 에서도 같은 것을 밟은 적이 있다(2026-08-15 harness-readopt).

★**주석에 적는 근거 문장도 실측 대상이다** — 「기본값이 X 라서 이 분기를 지난다」 같은
문장은 코드로 확인한 뒤에 써라. 같은 회차에서 그 문장 자체가 거짓이었다.

### 10.1 가드는 「있다」가 아니라 「그 경로가 지나는가」로 재라 (2026-08-10 [BL-451])

`_assert_disposable_database` 는 2026-07-25 실사고 직후 붙었고 2년 가까이 「있다」고 여겨졌다.
실측하니 그것은 `tests/test_migrations.py` **파일 안에만** 있었고, 사본 하나는
`tests/real_broker/conftest.py` 에 있었지만 그 파일은 **그 디렉터리를 수집할 때만** 로드됐다.
`DATABASE_URL`(개발 DB) 하나만 있는 셸에서 `pytest tests/trading/` 이 rc=0 으로 1088건을
수집했고, 그 경로의 세션 픽스처는 `SQLModel.metadata.drop_all` 을 돈다.

- **가드는 그 판정이 필요한 모든 진입점보다 위에 둬라.** pytest 라면 하위 conftest 가 아니라
  루트 `tests/conftest.py::pytest_configure` 다.
- **가드가 못 보는 표면을 주석으로 적어라.** `alembic/env.py` 의 방향 가드는 `config.cmd_opts`
  가 `None` 인 프로그램 호출 경로를 감지하지 못한다 — 그 사실을 코드 옆에 남겨야 다음 사람이
  그 초록을 「전부 막혔다」로 읽지 않는다.
- **막는 가드에는 「안 막는 것」의 음성 대조를 붙여라.** 방향을 안 보는 가드는 파괴를 막는 대신
  `mise run migrate`·entrypoint·CI 를 죽인다. 그 대조는 **역방향 변이**(가드를 더 넓게 만드는 변이)
  로만 판별력이 증명된다 — 정방향 변이만 돌리면 「너무 넓은 가드」가 초록으로 통과한다.
