# ADR-022: 엔진 포지션 SSOT — 원장을 진실로, 거래소는 거부권만 (veto + 관망)

> **상태:** 확정 (Accepted)
> **일자:** 2026-08-04
> **출처:** 2026-08-04 engine-position-ssot ([BL-591] §설계 축 4개 질문의 사용자 확정)
> **관련:** [`tasks/live_signal.py:2528`](../../apps/api/src/tasks/live_signal.py) (`run_live` 재생) · `live_signal.py:2248` (동어반복 금지 제약) · `live_signal.py:494-516` (발산 분류기) · [`pine_v2/event_loop.py:192`](../../apps/api/src/strategy/pine_v2/event_loop.py) (주입점) · [`pine_v2/strategy_state.py:331-357`](../../apps/api/src/strategy/pine_v2/strategy_state.py) (`seed_positions_from_ledger`)

---

## 배경

**엔진 포지션에는 SSOT 가 없다.** `run_live` 는 매 tick 봉을 처음부터 재생해 포지션을 **도출**하며
(`live_signal.py:2528`), 정상 운행 중엔 현실로 **보정되지 않는다.** `last_strategy_state_report` 는
발산 스트라이크 플래그와 보고용일 뿐 엔진 상태를 이어받지 않는다. ⇒ **엔진에 「쓸」 자리가 없다.**

그래서 시스템이 어긋남에 대해 할 수 있는 일은 **죽이는 것**뿐이고, 실제로 `direction`(양쪽이 정반대)
갈래만 fail-closed 종료시킨다. 이 축에서 증상 BL 을 16건 Resolved 했으나 소크는 **스스로 죽을 때
늘 2시간 안에 죽는다**(가드 머지 후 자동 종료 6/6). 기전은 매번 달랐고 뿌리는 하나다.

## 결정

**엔진 포지션 SSOT = 원장(`trading.orders`). 거래소는 값을 주지 않고 거부권만 행사한다.**

```
매 tick:
  ① 원장에서 포지션 유도            (값의 유일한 출처)
  ② 거래소 스냅샷 조회              (이미 매 tick 한다 — 게이트 비용 0)
  ③ ①≠② → veto                     (거래소는 "넣지 마"만 말한다)
       veto 아님 → 엔진이 flat 이면 주입
       veto      → 주입 ✖ + 발주 ✖ (관망) + 버팀 카운터 +1
                   상한 초과 시 오늘처럼 fail-closed 종료
  ④ 주입/veto/버팀 내역을 tick 상태(jsonb)에 영속
  ⑤ 주입 후 남는 발산은 현행대로 `direction` 만 킬
```

**상한은 `interval` 비례**로 둔다(`max(절대 하한, interval × N)` 류 혼합형).
**계수는 계측 실측으로 정하고, 그 전에는 켜지 않는다.**

## 근거

**1. 거래소를 값의 출처로 쓰면 안전망이 사라진다** — `live_signal.py:2248` 이 이미 적고 있다:
「seed 를 거래소에서 가져오면 아래 대조가 **동어반복**이 되어 가드가 통째로 사라진다」.
veto 는 거래소가 **막을 수만 있고 값을 주지 못하므로** 이 제약에 걸리지 않는다. 사후
「엔진 vs 거래소」 대조는 값의 출처가 원장이라 **여전히 독립**이다.

**2. 원장 구멍은 실재하나 앱의 결함이 아니다** — `trading.exchange_exits` 실측(2026-08-04):
청산 103건 중 원장 밖(`external_manual`) **12건 = 11.7%**, 6일에 걸쳐 상시. **그러나 12건 중 10건이
「활성 세션 없음」 구간**이고, `src/` 에는 원장을 건너뛰는 청산 경로가 **없다**
(`ClosePositionService` → `OrderService.execute` → `Order` 행). 범인은 운영자 스크립트다([BL-593]).
⇒ 구멍을 먼저 메우는 선행 슬라이스보다 **veto 게이트가 정확한 대응**이다.

**3. 게이트 비용이 0 이다** — `_detect_position_divergence`(`live_signal.py:537`)가 매 tick
`fetch_open_positions`(:570)를 이미 호출한다. 거래소 스냅샷은 이미 손에 있다.

**4. 관망이 지연을 흡수한다** — 원장이 거래소 청산을 아는 지연 실측(n=90):
p50 **7초** · p90 **266초** · max **1925초**. **82.2% 가 1 tick 안**에 해소되지만 **15.6% 가 2 tick 을
넘긴다.** 현행 유예는 1회(=2 tick)뿐이라 그 15.6% 를 못 덮는다. 관망 중엔 발주가 없으므로
**돈이 새지 않고**, 잃는 것은 기회뿐이다.

**5. 상한이 절대 시간이면 안 된다** — `list_active_due` 가 `last_evaluated_bar_time + interval <= now`
로 due 를 정하므로 **tick 주기 = interval** 이다(1m/5m/15m/1h → 60/300/900/3600초).
⇒ 「2 tick 유예」는 1분봉이면 2분, 1시간봉이면 2시간이다. ★**현행 `direction_transient` 1회 유예도
이미 interval 비례**이며 아무도 명시한 적이 없었다. 단 **순수 비례도 안 된다** — 지연의 원인은
절대 시간(WebSocket 왕복 · 폴링 300초)이고 관망의 비용은 봉 개수(interval 비례)라 **비대칭**이다.
그래서 혼합형이고, 계수는 추정이 아니라 실측으로 정한다.

## 대안 (거부됨)

- **B. 거래소 SSOT** — 매 tick 거래소 포지션을 엔진에 복사. **가드 소멸**(근거 1). 게다가 포지션
  크기만으로는 진입가·`trade_id`·pending order 를 복원하지 못한다.
- **D. 조정 연산 정의** — 엔진에 쓸 자리가 없으므로 결국 같은 주입점을 쓴다. **C 의 부분집합.**
- **구멍부터 메우는 선행 슬라이스** — 수집기가 `external_manual` 청산에 합성 `Order` 행을 쓴다.
  머니-패스 원장에 **「발주한 적 없는 주문 행」**이 섞이고, 수집이 300초 주기라 최대 5 tick 구멍이
  어차피 남는다. veto 가 그 구간을 이미 덮는다.
- **게이트 없이 주입** — [BL-591] 이 경고한 「C 가 지금보다 나쁘다」가 정확히 이 경우다.
  오주입 → 반대 주문 발주 → **그 뒤에야** 가드 발화. **돈이 먼저 나간다.**
- **주입만 건너뛰고 발주는 그대로** — C 의 효과가 82% tick 에만 미치고, 지연이 긴 15.6% 구간은
  오늘과 똑같이 발산·사망한다.
- **veto 면 즉시 킬** — 체결 직후 tick 의 17.8% 에서 즉사. 지금 1회 유예로 살아나던 사례가 전부
  사망으로 바뀌어 **P0([BL-003])의 달력 시계를 오히려 말린다.**
- **원장으로 전면 덮어쓰기**(주입 범위 확대) — `engine_only` 314 · `size` 28 까지 사정권에 들지만
  **멱등성이 깨진다**(재생이 스스로 만든 포지션과 원장이 섞여 이중 계상). 재생 포지션을 지우는
  로직이 새로 필요하고, 원장 구멍 11.7% 에 훨씬 크게 노출된다.
- **킬 대상을 `engine_only`·`size` 로 확대** — 314+28 규모로 사망해 소크가 사실상 못 돈다.
  분류기 주석이 이미 「양쪽을 죽이면 이 스프린트가 고치려는 상태에서 세션이 상시 사망」이라 경고한다.

## 결과

**기대 효과를 정확히 적는다 — C 는 교정이 아니라 예방이다.**

`seed_positions_from_ledger` 는 `if not legs or self.open_trades: return ()` 로 **엔진이 완전히
비었을 때만** 주입한다(`strategy_state.py:357`). 분류기와 대조하면 주입이 닿는 것은 엔진 flat 인
**`exchange_only` 21건뿐**이고, `engine_only` 314 · `size` 28 · `direction` 3 · `transient` 23 은
`open_trades` 가 차 있어 **주입 자체가 일어나지 않는다.**

★★★**주입과 `direction` 킬은 같은 tick 에 공존할 수 없다** — `direction` 은 양쪽 non-flat,
주입은 엔진 flat 이 조건이다. ⇒ **C 는 소크를 죽이는 그 발산을 고치지 못한다.** 진입을 놓친
상태를 미리 메워 **나중에 `direction` 으로 발전하는 것을 막을 뿐**이다. 이 구분을 지우면 다음
사람이 「314건짜리 수리」로 읽고 효과를 과대평가한다.

**작업량도 정확히 적는다 — 유도 로직은 신설이다.**

「순수 함수(`_ledger_gap_seed`)가 이미 있으니 발화 조건만 넓히면 된다」는 **틀렸다.** 그 함수의
채택 조건은 「창 안 체결이 전부 같은 방향 + reduce-only 하나도 없음」(`live_signal.py:405-407`)이라
상시 주입에서는 `since` 를 어떻게 잡아도 legs 가 빈다(세션 시작 → 진입+청산이 섞여
`inadmissible` / 직전 tick → 체결이 없어 `no_basis`). **Pine `trade_id` 단위로 진입/청산을 상쇄해
열린 trade 만 남기는 유도 함수를 새로 써야 한다.** 순수 함수라 단위 테스트로 전량 검증 가능하다.

**켜는 순서 — 계측이 먼저다.**

슬라이스 1 은 판정을 **계산만** 하고 기록한다(판정·발주 경로 무변경). ★단 **거래소 조회가
tick 당 1회 늘어 2회가 된다** — `_detect_position_divergence` 는 `engine_position`(= `run_live`
**결과**)이 필요해 뒤로 갈 수밖에 없고 veto 는 주입 **직전**에 판정해야 하므로, 두 조회는
**구조적으로 합칠 수 없다.** 「동작 변경 0」이라고 적으면 다음 사람이 이 비용을 못 본다.
거기서 ① 주입 가능 tick 수
② veto 발동률 ③ **veto 해소까지 tick 분포**(상한 계수의 직접 근거) ④ **`exchange_only` →
`direction` 발전율**(= 본 결정의 기대 효과 그 자체) ⑤ 유도 함수 `None` 비율을 잰 뒤 슬라이스 2 를
착수한다. ★**④가 0 이면 본 결정의 근거가 무너지므로 슬라이스 2 를 착수하지 않는다.**

**재현성 — 라이브는 더 이상 「전략+OHLCV」만으로 재현되지 않는다.**

백테스트 골든은 안 깨진다(`ledger_seed_legs` 를 채우는 곳은 `live_signal.py:2512` 하나뿐 —
★줄번호만 2026-08-04 에 갱신했다, 주장은 손대지 않았다. 검증 결과는 §슬라이스 1 후속 실측 참조).
다만 그 격리가 **관례로만** 유지되므로 회귀 테스트를 신설한다. 라이브 쪽은 주입 후 그 시점
원장이 있어야 재현되므로, `live_signal_states.last_strategy_state_report`(기존 jsonb,
**마이그레이션 0**)에 `ledger_seed{applied, vetoed, hold_ticks}` 를 영속한다.

**본 ADR 은 B 안(거래소 SSOT) 재제안을 차단한다** — 거부 근거는 취향이 아니라 코드에 적힌
동어반복 제약이다.
