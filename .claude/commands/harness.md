다단계 작업을 **무인 러너**로 실행한다. 러너는 step 마다 코딩 에이전트를 1회 호출하고,
**Acceptance Criteria(AC)를 직접 재실행해 exit code 로만 판정한다.**

## 호출

```
/harness [parallel [N]] [<phase>|<대상>…]
```

- **`parallel`** — 워크트리 병렬 실행. 생략하면 순차
- **`N`** — 동시 실행 상한. 생략하면 대상 전부
- **`<phase>|<대상>…`** — 아래 규칙으로 갈린다. 생략하면 `pending` 전량

| 준 값                                        | 해석                                     |
| -------------------------------------------- | ---------------------------------------- |
| `phases/` 에 있는 디렉터리명                 | **그 phase 를 실행한다**                 |
| 그 밖의 값 (티켓 ID · 이슈 번호 · 자유 서술) | **그것을 재료로 새 회차를 설계한다**(§1) |
| 생략                                         | `pending` 전량                           |

둘이 섞이면 실행할지 설계할지 되묻는다.

인자를 모두 생략했을 때: **pending 이 없으면** 무엇을 할지 묻고, **1개면** 그대로 실행하고,
**여럿이면** 무엇을 어떻게 돌릴지 제시해 승인받는다.

```
/harness                          # pending 전량 — 알아서
/harness parallel 2               # 동시 2벌 상한
/harness runner-ac                # 그 phase 만
/harness parallel BL-11 BL-42     # 두 티켓으로 회차를 설계해 병렬로
```

★**실행 전에 항상 한 번 보고한다.** 무인 러너는 되돌리기가 비싸다.

받은 인자: $ARGUMENTS

러너: !`ls tools/harness/execute.py scripts/execute.py 2>/dev/null | head -1 || echo "(찾지 못했다)"`

현황: !`jq -r '.phases[] | "  \(.status)  \(.dir)"' phases/index.json 2>/dev/null || echo "  (회차 없음)"`

## 개념

| 용어      | 뜻                                                                                  |
| --------- | ----------------------------------------------------------------------------------- |
| **phase** | `phases/<dir>/` 하나. **브랜치 1개 = PR 1개**에 대응한다                            |
| **step**  | phase 안의 작업 단위. **순차**이고 앞 step 의 `summary` 가 다음 프롬프트에 누적된다 |
| **AC**    | step 의 통과 조건. **실행 가능한 셸 커맨드 배열**이며 rc=0 만 통과다                |
| **lane**  | 병렬 실행 시의 phase. lane 안은 순차, **lane 사이가 병렬**이다                      |

**러너가 대신 해 주는 것** — step 파일에 다시 적을 필요가 없다:

- 브랜치 생성·checkout · 규칙 파일 주입(없으면 시작 거부) · 완료된 step 의 `summary` 전달
- 실패 시 재시도(직전 실패 사유를 프롬프트에 피드백) · **AC 전건 재실행 판정** · 통과 시에만 커밋
- 타임스탬프 기록. 실패로 정지하면 **코드를 커밋하지 않고** 작업 트리를 검시용으로 남긴다

★**AC 로 판정할 수 없는 작업은 이 도구의 대상이 아니다.** 판정 불가를 무릅쓰고 돌리면 러너는
「돌았다」만 보증하고 「됐다」는 보증하지 않는다.

## 워크플로우

### 1. 설계

작업 대상과 좌표를 **코드로 확인한다** — 이슈·설계 문서의 처방을 그대로 믿지 않는다. 기술 결정이
필요한 것은 추천도와 함께 사용자와 합의한다. 미확정 결정을 step 에 넘기면 에이전트가 임의로 정한다.

대상이 여럿이면 **몇 개의 phase 로 묶을지도 여기서 정한다** — 개수가 아니라 §5 의 묶음 기준이
정하고, **배분을 먼저 제시해 승인받는다.**

step 분할 원칙:

1. **한 step = 한 레이어/모듈.** 여러 모듈을 건드리면 쪼갠다
2. **자기완결성** — step 은 문맥 없는 세션에서 실행된다. 「앞서 논의한」 같은 외부 참조 금지.
   단 **에이전트가 읽을 수 있는 것은 경로로 준다** — 파일 내용을 복사하면 낡은 사본이 된다
3. **시그니처 수준 지시** — 인터페이스를 제시하고 구현은 세션 재량. 단 벗어나면 안 되는
   계약(경계·불변식·보안)은 명시한다
4. **금지사항은 이유와 함께** — 「조심해라」가 아니라 「X 를 하지 마라. 이유: Y」
5. step name 은 kebab-case slug

### 2. AC 작성 — 이 도구의 전부

★**러너는 AC 가 재실행되는 것만 보증한다. AC 가 옳은지는 판정하지 않는다.**

| 규칙                        | 왜                                                                                                                             |
| --------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **대상을 좁혀라**           | 부재 단언이 소스와 테스트를 함께 덮으면, 부재를 단언할 테스트가 그 토큰을 못 써서 **세션이 우회로를 만든다**                   |
| **구조는 파싱으로 재라**    | 문자열 검색은 별칭·재export·포매팅으로 우회된다. 경계·금지된 의존은 AST 로                                                     |
| **양성 대조를 붙여라**      | 「0건이니 통과」는 **대상에 닿지 않아도 참**이다. 「대상을 N개 이상 찾았다」를 함께 단언해라                                   |
| **착수 전 red 를 확인해라** | 작업 전 AC 는 실패해야 한다. 그 측정 없이 난 초록은 아무것도 증명하지 않는다                                                   |
| **`xfail` 은 주장이다**     | `xfail(strict=True)` 는 「제품 코드가 틀렸다」를 원장에 박는다. **코드 대조 없이 쓰지 마라** — AC·변이·diff 가 전부 통과시킨다 |
| **최소만 넣어라**           | 전체 스위트를 step AC 에 넣으면 에이전트와 러너가 두 번 돌린다. 광역 회귀는 CI 와 사람에게                                     |

커맨드는 **그 프로젝트의 표준 러너**(테스트·린터·타입체크·빌드)만 쓴다. 서버 기동이나 외부 상태를
건드리는 검증은 AC 가 아니다.

### 3. 파일 생성 (사용자 승인 후)

**`phases/index.json`** — 전체 목록. `{ "phases": [{ "dir": "<phase-dir>", "status": "pending" }] }`

**`phases/<phase-dir>/index.json`**

```json
{
  "project": "<프로젝트명>",
  "phase": "<phase-name>",
  "steps": [
    { "step": 0, "name": "<slug>", "status": "pending", "ac": ["<셸 커맨드>"] }
  ]
}
```

★**저작 시 넣는 것은 `step`·`name`·`status:"pending"`·`ac` 넷뿐이다.** `ac` 는 의무이고, 없으면
러너가 시작을 거부한다. 나머지 필드는 러너가 쓴다:

| 전이          | 기록되는 필드                   | 쓰는 주체                                                       |
| ------------- | ------------------------------- | --------------------------------------------------------------- |
| → `completed` | `completed_at` · `summary`      | **러너**. `summary` 는 에이전트가 써 둔 값이 있으면 그것을 쓴다 |
| → `error`     | `failed_at` · `error_message`   | **러너** — 재시도 한도를 소진했을 때                            |
| → `blocked`   | `blocked_at` · `blocked_reason` | 사유는 **에이전트**, 타임스탬프는 러너                          |

★**에이전트가 직접 쓸 수 있는 것은 `summary` 와 `blocked`(+`blocked_reason`) 둘뿐이다.**
`status` 를 `completed` 로 바꾸는 것은 러너의 권한이다 — 코드를 쓴 쪽이 자기 채점을 하면 판정이
무너진다. `summary` 는 다음 step 에 누적 전달되므로 **다음 step 에 쓸모 있는 것**을 담아야 한다.

**`phases/<phase-dir>/step{N}.md`**

```markdown
# Step {N}: {이름}

## 읽어야 할 파일

- {정본 문서 · 이전 step 산출 경로}

## 작업

{구체 지시 — 파일 경로 · 시그니처 · 벗어나면 안 되는 계약}

## Acceptance Criteria

{index.json 의 ac 와 동일한 커맨드}

## 자기 점검

1. 위 AC 를 직접 실행해 green 을 확인한다. ★최종 판정은 러너가 재실행해 내린다 —
   `status` 를 `completed` 로 바꾸지 마라.
2. 프로젝트 규약을 벗어나지 않았는지 확인한다: 디렉터리 구조 · 허용된 스택 · 규칙 파일의 필수 항목.
3. 사람 개입이 필요하면(자격증명·외부 인증·수동 설정) `status:"blocked"` 와 `blocked_reason` 을
   쓰고 **즉시 중단**한다.

## 금지사항

- {「X 를 하지 마라. 이유: Y」}
- 커밋하지 마라(커밋은 러너 소관).
```

### 4. 실행

```bash
python3 <러너 경로> <phase-dir> [--push]
```

**중단 복구** — 둘은 절차가 다르다:

- **`error`** — 작업 트리를 **사람이 검시**한 뒤 `status` 를 `"pending"` 으로 되돌리고
  `error_message` 를 지운다. AC 자체가 틀렸다면 AC 를 먼저 고쳐라
- **`blocked`** — `blocked_reason` 의 **사유를 먼저 해결**하고 되돌린다

### 5. 병렬 (`parallel`)

러너는 phase 하나만 처리한다. 병렬은 **러너 밖에서 프로세스를 N벌 띄워** 만든다.

**묶음 기준** — 대상 개수가 아니라 이 넷이 lane 을 정한다:

1. **lane 간 파일 겹침 0.** 병렬의 유일한 구조적 비용이다
2. **의존 있는 것은 같은 lane 안으로.** lane 사이에는 의존을 표현할 수단이 없다
3. **AC 가 lane 끼리 자원을 다투지 않아야 한다** (포트·DB·캐시)
4. **소요를 대략 맞춰라.** lane 하나가 길면 나머지가 논다

**순서**:

1. **`phases/index.json` 에 lane 항목을 전부 등록해 머지한 뒤** 워크트리를 판다 — 모든 lane 이
   갱신하는 유일한 공유 파일이라, 나중에 각자 추가하면 배열 끝 같은 위치를 고쳐 충돌한다
2. lane 마다 워크트리 생성 — **브랜치 이름은 러너가 checkout 할 그 이름**이어야 한다
3. 각 워크트리를 실행 가능 상태로 (의존성·가상환경이 워크트리마다 필요하다)
4. 러너를 **분리 기동**(`nohup … &`) — 대화 세션의 타임아웃이 러너를 죽인다.
   ★띄우는 셸의 환경이 AC 에 상속된다
5. `phases/<dir>/index.json` 폴링
6. **lane 별 diff 를 사람이 읽고** PR — ★AC 초록은 AC 가 옳다는 뜻이 아니다

★**저작이 끝난 lane 을 실행만 할 때는 §1~3 을 건너뛴다.**

## 실패 모드

| 증상                         | 원인                              | 대응                               |
| ---------------------------- | --------------------------------- | ---------------------------------- |
| AC 는 초록인데 결과가 틀렸다 | 우회 가능한 단언                  | §2. 사람 diff 대조가 최종 검출자다 |
| 테스트 없이 통과             | 판별력 없는 AC                    | §2 — 착수 전 red 확인              |
| AC 가 간헐 red               | 타임아웃 여유 부족 · 자원 경합    | AC 를 가볍게 · §5 묶음 기준 3      |
| 러너가 도중에 사라졌다       | 세션 타임아웃이 프로세스를 죽였다 | §5 순서 4 — 분리 기동              |
| lane 머지 충돌               | 공유 파일을 lane 이 각자 추가     | §5 순서 1 — 사전 등록              |

완주 후 PR 생성·머지는 **사람이 한다.** `--push` 는 브랜치 push 까지다.
