다단계 작업을 무인 러너로 실행한다 — step 마다 코딩 에이전트를 호출하고, Acceptance Criteria 를 러너가 재실행해 exit code 로 판정한다.

구현: `tools/harness/execute.py` · 회차 정의: `phases/` (규약은 `phases/README.md`)

---

## 1. 무엇을 위한 도구인가

|            |                                                                                                       |
| ---------- | ----------------------------------------------------------------------------------------------------- |
| **적합**   | 작업이 **여러 step 으로 갈리고**, 각 step 의 완료를 **커맨드 하나의 exit code 로 판정**할 수 있을 때  |
| **부적합** | 단건 수정 · 설계 결정이 미확정 · 판정이 사람 눈에 의존 · 외부 상태(서버·거래소·수동 조작)를 건드릴 때 |

★**AC 로 판정할 수 없는 작업은 이 도구의 대상이 아니다.** 판정 불가를 무릅쓰고 돌리면
러너는 「돌았다」만 보증하고 「됐다」는 보증하지 않는다.

## 2. 개념

| 용어      | 뜻                                                                                                                                                                 |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **phase** | `phases/<dir>/` 하나. **브랜치 1개 = PR 1개**에 대응한다. 이 디렉터리는 러너 회차의 공인 킥오프 자리다 — 「킥오프 파일을 만들지 마라」는 러너 밖 회차에만 적용된다 |
| **step**  | phase 안의 작업 단위. **순차** 실행이고 앞 step 의 `summary` 가 다음 프롬프트에 누적된다                                                                           |
| **AC**    | step 의 통과 조건. **실행 가능한 셸 커맨드 배열**이며 rc=0 만 통과다                                                                                               |
| **lane**  | 병렬 실행 시의 phase. lane 안은 순차, **lane 사이가 병렬**이다                                                                                                     |

**러너의 동작**: 브랜치 checkout → step 마다 [가드레일 + 이전 `summary` 누적 + 직전 실패 사유]
프리앰블로 에이전트 1회 호출 → **AC 전건 재실행** → 통과 시 커밋(코드/상태 2단 분리) →
`MAX_RETRIES` 회 실패 시 정지 — **코드는 커밋하지 않고** 상태만 기록해 작업 트리를 검시용으로 남긴다.

**에이전트가 쓸 수 있는 것은 둘뿐이다** — `summary`(산출 한 줄) · `blocked`+`blocked_reason`
(사람 개입 요청). `status` 를 `completed` 로 바꾸는 것은 러너의 권한이다.

## 3. 워크플로우

### 3.1 대상 확정

작업 대상과 그 좌표를 **코드로 확인한다.** 원장·이슈·설계 문서의 처방을 그대로 믿지 않는다 —
「고칠 것이 이미 없다」가 착수 후에 드러나면 회차 전체가 낭비된다.

### 3.2 논의

기술 결정이 필요한 것을 **추천도와 함께** 사용자에게 제시하고 합의한다. 러너는 설계 결정을
대신하지 않는다 — 미확정 결정을 step 에 넘기면 에이전트가 임의로 정한다.

### 3.3 step 설계

1. **한 step = 한 레이어/모듈.** 여러 모듈을 건드리면 쪼갠다
2. **자기완결성** — 각 step 은 **문맥 없는 세션**에서 실행된다. 「앞서 논의한」 같은 외부 참조
   금지. 다만 **에이전트가 읽을 수 있는 것은 경로로 준다** — 파일 내용을 복사하면 낡은 사본이 된다
3. **사전 준비 명시** — 읽어야 할 파일과 이전 step 의 산출 경로를 적는다
4. **시그니처 수준 지시** — 인터페이스를 제시하고 구현은 세션 재량에 둔다. 단 **벗어나면 안 되는
   계약**(경계·불변식·보안)은 명시한다
5. **금지사항은 이유와 함께** — 「조심해라」가 아니라 「X 를 하지 마라. 이유: Y」
6. **네이밍** — step name 은 kebab-case slug

### 3.4 AC 작성 — 이 도구의 전부

★**러너는 AC 가 재실행되는 것만 보증한다. AC 가 옳은지는 판정하지 않는다.**
저작 결함은 그대로 통과한다. 아래는 그 결함을 막는 규칙이다.

| 규칙                                  | 왜                                                                                                                                                                       |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **a. 부재 단언은 대상을 좁혀라**      | 소스와 테스트를 함께 덮으면, 부재를 단언하는 테스트가 그 토큰을 쓸 수 없어 **세션이 우회로를 만든다**(문자열 분할 등). 대상 파일을 지목하거나 테스트 디렉터리를 제외해라 |
| **b. 구조적 계약은 파싱으로 재라**    | 문자열 검색은 별칭·재export·포매팅으로 우회된다. 레이어 경계·금지된 의존은 **AST 로 파싱하는 테스트**를 정본에 두고 검색은 보조로만                                      |
| **c. 부재 단언에 양성 대조를 붙여라** | 「0건이니 통과」는 **대상에 닿지 않아도 참**이다. 경로 오타 하나로 항진명제가 된다. 「대상을 N개 이상 찾았다」를 함께 단언해라                                           |
| **d. 착수 전 판별력을 측정해라**      | 작업 전 AC 는 **red 여야 한다.** 그 측정 없이 난 초록은 아무것도 증명하지 않는다. 측정값을 기록해라                                                                      |
| **e. 실행 시간의 여유를 확보해라**    | AC 가 러너 타임아웃에 근접하면 부하로 위양성 red 가 난다. 여유가 3배 미만이면 타임아웃을 올려라                                                                          |
| **f. 판정에 필요한 최소만 넣어라**    | 전체 스위트를 step AC 에 넣으면 에이전트와 러너가 **두 번** 돌린다. 광역 회귀는 CI 와 사람의 통합 검수에 맡겨라                                                          |

### 3.5 파일 생성 (사용자 승인 후)

**`phases/index.json`** — 전체 목록

```json
{ "phases": [{ "dir": "<phase-dir>", "status": "pending" }] }
```

**`phases/<phase-dir>/index.json`**

```json
{
  "project": "<프로젝트명>",
  "phase": "<phase-name>",
  "steps": [
    {
      "step": 0,
      "name": "<kebab-case-slug>",
      "status": "pending",
      "ac": ["<실행 가능한 셸 커맨드>", "..."]
    }
  ]
}
```

- ★**`ac` 배열은 step 마다 의무다** — 없으면 러너가 시작을 거부한다
- `status` 초기값은 전부 `"pending"`. 타임스탬프와 완료·오류 표시는 러너가 쓴다
- `phase` 값이 **브랜치 이름을 정한다**(§5 바인딩 표)

**`phases/<phase-dir>/step{N}.md`**

```markdown
# Step {N}: {이름}

## 읽어야 할 파일

- {정본 문서 · 이전 step 산출 경로}

## 배경

{왜 이 step 이 필요한가 — 2~4줄}

## 작업

{구체 지시 — 파일 경로 · 시그니처 · 벗어나면 안 되는 계약}

## Acceptance Criteria

{index.json 의 ac 와 동일한 커맨드 — 세션이 스스로 돌려 보게}

## 금지사항

- {「X 를 하지 마라. 이유: Y」}
- 커밋하지 마라(커밋은 러너 소관).
```

### 3.6 실행 — 순차

```bash
python3 tools/harness/execute.py <phase-dir>          # 실행
python3 tools/harness/execute.py <phase-dir> --push   # 완주 후 브랜치 push
```

**중단 복구**: 원인을 해결하고 해당 step 의 `status` 를 `"pending"` 으로 되돌린 뒤
(`error_message`/`blocked_reason` 삭제) 다시 실행한다.

### 3.7 실행 — 병렬 (`parallel`)

러너는 **phase 하나만** 처리한다. 병렬은 러너 안이 아니라 **밖에서 프로세스를 N벌 띄워** 만든다.

**묶음 기준** — 대상 개수가 아니라 이 넷이 lane 을 정한다:

1. **lane 간 파일 겹침 0.** 병렬의 유일한 구조적 비용이다. 파일은 갈리는데 호출만 결합돼 있으면
   「그 시그니처를 바꾸지 마라」를 금지사항에 박아 분리할 수 있다
2. **의존 있는 것은 같은 lane 안으로.** lane 사이에는 의존을 표현할 수단이 없다
3. **AC 는 lane 끼리 자원을 다투지 않아야 한다.** 격리된 테스트 러너·린터·빌드만 쓴다
4. **lane 하나가 지나치게 길면 나머지가 논다.** 소요를 대략 맞춰라

**순서**:

| #   | 단계                                                    | 주의                                                                                                                                                                                      |
| --- | ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `phases/index.json` 에 lane 항목을 **전부 등록해 머지** | 모든 lane 이 갱신하는 **유일한 공유 파일**이다. 나중에 각자 추가하면 배열 끝 같은 위치를 고쳐 충돌한다. 미리 등록하면 서로 다른 줄의 `status` 만 바뀌어 자동 병합된다                     |
| 2   | lane 마다 워크트리 생성                                 | **브랜치 이름을 러너가 checkout 할 이름으로** 만들어라(§5). 다르면 워크트리에 브랜치가 둘 생긴다                                                                                          |
| 3   | 각 워크트리를 실행 가능 상태로                          | 의존성·가상환경이 워크트리마다 필요하다. 없으면 AC 가 전건 red 다                                                                                                                         |
| 4   | 러너를 **분리 기동**                                    | 대화 세션의 도구 타임아웃이 러너를 죽인다. `nohup … &` 로 떼어내라. ★**띄우는 셸의 환경이 AC 에 상속된다** — 러너는 AC 를 비로그인 셸로 돌리므로 PATH 에 러너·패키지 매니저가 있어야 한다 |
| 5   | `phases/<dir>/index.json` 폴링                          | 진행은 파일이 말한다                                                                                                                                                                      |
| 6   | **lane 별 diff 를 사람이 읽고** PR                      | ★AC 초록은 AC 가 옳다는 뜻이 아니다(§3.4)                                                                                                                                                 |

★**저작이 끝난 lane 을 실행만 할 때는 §3.1~3.5 를 건너뛰고 §3.7 에서 시작한다.**

### 3.8 랜딩

완주 후 PR 생성·머지는 **사람이 한다.** `--push` 는 브랜치 push 까지다.

## 4. 실패 모드

| 증상                         | 원인                                   | 대응                                              |
| ---------------------------- | -------------------------------------- | ------------------------------------------------- |
| AC 는 초록인데 결과가 틀렸다 | AC 저작 결함(우회 가능한 단언)         | §3.4 a~d. 사람 diff 대조가 최종 검출자다          |
| 「테스트 없이 통과」         | 판별력 없는 AC                         | §3.4 d — 착수 전 red 측정                         |
| AC 가 간헐 red               | 타임아웃 여유 부족 · 자원 경합         | §3.4 e · §3.7 묶음 기준 3                         |
| 러너가 도중에 사라졌다       | 대화 세션 타임아웃이 프로세스를 죽였다 | §3.7 4 — 분리 기동                                |
| lane 머지 충돌               | 공유 파일을 lane 이 각자 추가          | §3.7 1 — 사전 등록                                |
| 에이전트가 즉시 중단         | 인증 만료 · 사람 개입 필요             | 코딩 에이전트 로그인 확인 · `blocked_reason` 확인 |

## 5. 이 프로젝트의 바인딩

★**이 절만 프로젝트 고유다.** 다른 저장소로 옮길 때 바꿀 것은 여기와 러너 상수뿐이다.

| 축                 | 값                                                                                                                |
| ------------------ | ----------------------------------------------------------------------------------------------------------------- |
| BE 테스트 AC       | `cd apps/api && uv run --env-file .env.local pytest <대상> -q`                                                    |
| BE 린터 AC         | `cd apps/api && uv run ruff check <대상>`                                                                         |
| FE 테스트 AC       | `cd apps/web && pnpm test -- --run <대상>`                                                                        |
| FE 타입·빌드 AC    | `cd apps/web && pnpm tsc --noEmit` · `pnpm build`                                                                 |
| 브랜치 규약        | `feat/harness-<phase>` — `feat/` 접두는 push 가드 화이트리스트라 협상 불가                                        |
| 가드레일 주입 파일 | `CONTEXT.md` · `AGENTS.md` · `apps/api/AGENTS.md` · `apps/web/AGENTS.md` (하나라도 없으면 러너가 시작을 거부한다) |
| 워크트리 준비      | `git worktree add <경로> -b feat/harness-<phase>` → 그 안에서 `tools/scripts/worktree-bootstrap.sh --adopt-env`   |
| 러너 타임아웃      | 에이전트 호출 `QB_HARNESS_CODEX_TIMEOUT` · AC `QB_HARNESS_AC_TIMEOUT`                                             |
| 산출물             | `phases/<dir>/runs/` (gitignore)                                                                                  |

**AC 에 넣으면 안 되는 것** (이 저장소의 구조적 제약):

- **서버 기동을 요구하는 검증** — 포트가 lane 사이에서 충돌한다
- **celery 경유 검증** — worker 컨테이너가 메인 체크아웃의 소스를 mount 하므로 워크트리에서는
  **내 코드가 아니라 메인 코드가 돈다**(침묵 실패)
- **`mise run up|down|migrate|seed`** — 컨테이너와 앱 DB 는 1벌 공유라 함께 깨진다
- **환경 변수 통째 소싱 없는 pytest** — DB 가드가 거부한다

**러너가 도는 동안** 같은 체크아웃에서 다른 세션이 작업하면 안 된다(공유 작업 트리).
